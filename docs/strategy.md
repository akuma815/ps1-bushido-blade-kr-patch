# 일본판 한글화 전략

## 결론

현재 가장 현실적인 전략은 다음 혼합형이다.

1. **메뉴·인명·무기명 등 그래픽 텍스트를 우선 교체한다.**
2. **실제 문자열 렌더 경로가 확인된 화면만 기존 일본어 코드·글리프
   경로 재사용을 검토한다.**
3. **음성만 존재하는 스토리 장면은 일반 텍스트와 분리해 자막 PoC를
   통과한 뒤 범위를 결정한다.**
4. **초기 빌드는 파일 크기와 LBA를 유지하는 제자리 교체를 우선한다.**

일본판에 한자 글리프가 있다는 이유만으로 한글 완성형을 바로 덮어쓰지
않는다. 코드표, 글리프 공급자, VRAM 상주량, 모든 참조자를 확인한 뒤에만
미사용 슬롯을 공급량으로 계산한다.

## 미국판의 활용

공식 미국판 `SCUS-94180`을 사용자가 합법적으로 제공할 수 있다면,
일본판의 빌드 기준으로 쓰지 않고 **분석용 대조군**으로만 사용한다.

- 같은 경로·같은 크기 파일의 일본판/미국판 diff
- 메뉴·인명·무기명 그래픽이 바뀐 `DAT` 식별
- 실행 파일에서 지역화용 renderer, 문자표, 폭 계산 변경점 식별
- 음성·STR·자막 유무와 파일 대응 확인
- 일본판에 적용할 최소 변경 범위 산정

이는 가장 비용 대비 효과가 큰 조사 가속 수단이다. 단, 미국판 주소·폰트
규칙을 일본판에 그대로 이식하지 않고 일본판 소비자에서 다시 검증한다.

## 단계별 계획

### 0. 기준선 고정

- 일본판 BIN/CUE 해시를 빌드 입력으로 고정한다.
- CUE의 상대 BIN 이름과 단일 Mode 2/2352 트랙을 검사한다.
- `dumpsxiso` 또는 `psximager`로 XA/STR를 보존하는 전체 추출본과
  재빌드 메타데이터를 만든다.
- 무변경 재빌드가 부팅, XA 음성, STR 영상, 대표 전투를 통과하기 전에는
  번역 빌드 경로로 채택하지 않는다.

### 1. 화면 텍스트 카탈로그

아래를 서로 다른 렌더 경로로 분리해 화면과 원본 자산을 연결한다.

- 타이틀·메인 메뉴·옵션
- 캐릭터·무기 선택
- 전투 UI·승패 메시지
- 스토리 모드 대화·연출
- 엔딩·크레디트
- 메모리카드 저장 제목

각 항목에 화면, 원문, 파일/블록 후보, TIM/문자열/영상 여부, 상태를 기록한다.
조사하지 않은 항목과 텍스트가 없는 항목을 구분한다.

### 2. 유효 TIM·커스텀 그래픽 파서

- `DAT`를 무작정 TIM 스트림으로 자르지 않고 컨테이너 레코드 경계를 먼저
  확인한다.
- TIM이면 CLUT·픽셀 블록·VRAM 좌표를 검증해 PNG와 메타데이터로 추출한다.
- 무수정 decode→encode가 바이트 동일하거나 선언한 의미 동등성을
  만족해야 한다.
- 번역 이미지는 원본 비트 깊이·팔레트·크기·VRAM 좌표를 유지한다.

### 3. 그래픽 텍스트 PoC

대표 메뉴 라벨 하나를 선택한다.

- 같은 크기 블록 안에서 일본어 픽셀만 한글로 교체
- 원본 팔레트 인덱스와 투명/STP 의미 보존
- `DAT` 전체 크기 불변
- ISO 파일 크기와 LBA 불변
- 타이틀 진입, 메뉴 이동, 해당 화면 진입·이탈 확인

이 PoC가 통과하면 메뉴·선택 화면 번역을 같은 경로로 확대한다.

### 4. 문자열·폰트 경로 조사

런타임에 표시되는 실제 문자열 한 개를 앵커로 잡는다.

1. 화면 원문을 원시 바이트 또는 RAM 패턴으로 찾는다.
2. 그 버퍼를 쓰는 파일 읽기/해제 경로와 읽는 renderer를 추적한다.
3. 코드 단위, 종료자, 제어 코드, 폭 계산, 글리프 주소 계산을 확인한다.
4. 글리프 저장 자산→RAM→VRAM→primitive 소비를 연결한다.

그 뒤 다음 세 후보를 비교한다.

| 후보 | 채택 조건 | 주요 위험 |
| --- | --- | --- |
| 기존 한자 슬롯을 한글에 재할당 | 모든 참조와 코드표를 전수 확인하고 필요한 고유 한글 수가 공급 안에 듦 | 원문 충돌, 슬롯 부족 |
| 필요한 한글만 정적 서브셋 | 번역 원장이 고정되고 코드표·폰트 빌드가 같은 매핑을 사용 | 번역 변경 때 글리프 증가 |
| 동적 글리프 캐시/새 renderer | 기존 공급량이 부족하고 훅·VRAM·수명 관리가 입증됨 | MIPS 훅, 캐시, VRAM, 성능 |

첫 후보가 성립하면 가장 단순하지만, 현재는 어느 후보도 승인되지 않았다.

### 5. 스토리 자막 분기

관찰한 한 완료 루트에서는 스토리 본편 대사가 음성으로만 재생됐고 화면
자막은 없었다. 다른 캐릭터·분기까지 동일하다고 아직 일반화하지는 않지만,
해당 대사를 한글화하려면 다음을 별도 비교한다.

#### STR에 자막을 구워 넣기

- 대상: 미리 렌더된 영상 내부 대사
- 장점: 게임 코드 훅이 작거나 불필요할 수 있음
- 위험: MDEC/STR 재인코딩 품질, XA 동기, 파일 크기와 섹터 배치

#### 게임 렌더러에 자막 오버레이 추가

- 대상: 인게임 연출과 반복 가능한 음성 장면
- 장점: 한글 폰트와 타이밍 데이터를 여러 장면에 재사용 가능
- 위험: MIPS 훅, VRAM 예산, 화면 상태 판정, 음성 타이밍, 중단/재시작

한 장면·두 문장으로 가시성, 동기, 진입·이탈 회귀를 확인하기 전에는
전체 자막 스크립트를 만들지 않는다.

### 6. 추출·번역 원장

번역 항목은 최소한 다음을 가진다.

- 안정 ID
- 원본 파일/블록/오프셋
- 원문과 원시 바이트 또는 원본 이미지 bounds
- 번역문
- 화면·모드·화자
- 길이·셀·줄 제한
- 제어 토큰
- 상태와 검증 결과

그래픽 텍스트와 문자열 텍스트는 원장을 분리하되 용어집은 공유한다.

### 7. 빌드와 배포

- 첫 단계는 동일 크기 파일의 기존 extent 제자리 교체를 우선한다.
- 파일 성장이나 이동이 필요해지면 모든 ISO 디렉터리 필드와 숨은
  LBA/크기 참조를 확인한 뒤 `mkpsxiso` 계열 재빌드로 전환한다.
- Form 1/Form 2, XA, STR 섹터를 원형대로 보존한다.
- 모든 수정은 Expected Write 목록으로 검증한다.
- 최종 배포는 원본 BIN이 아니라 xdelta 패치, 지원 해시, 적용법,
  결과 해시만 포함한다.

## PoC 승인 순서

1. 무변경 디스크 왕복
2. 메뉴 그래픽 한 항목
3. 실제 런타임 문자열 한 항목(해당 경로가 존재할 때)
4. 대표 스토리 자막 한 장면(필요할 때)
5. 대표 E2E: 추출→번역→삽입→빌드→실행

앞 게이트가 다음 설계의 전제가 아닐 때는 독립적으로 조사할 수 있지만,
실패한 게이트를 성공으로 간주해 전량 작업을 시작하지 않는다.

## 현재 판정

**조건부 진행 가능**이다.

- 메뉴·그래픽 한글화는 기술적으로 유망하다.
- 일본어 글꼴 슬롯 재사용은 아직 증거 부족이다.
- 전체 스토리 한글화 난도는 원문이 텍스트인지 음성 전용인지에 따라 크게
  달라지므로 런타임 카탈로그가 우선이다.
- 첫 구현 목표는 “메인 메뉴의 일본어 라벨 한 개를 동일 크기로 한글
  교체하고 일본판에서 정상 표시”로 정한다.

## 1차 캡처 반영 결정 (2026-07-29)

실제 화면 근거로 그래픽 우선 조사는 유지하되, 모든 문구를 고정 이미지로
간주하지 않는다. 장식된 화면 헤더와 선택에 따라 내용이 바뀌는 무기 정보는
서로 다른 경로일 수 있다.

첫 그래픽 PoC 후보는 옵션 화면의 정적 헤더 `オプション`이다. 짧고 접근이
쉬우며, 한글 `옵션`으로 바꾼 뒤 동일 화면에서 즉시 비교할 수 있다. 다음
캡처에서는 메인 메뉴의 다른 선택 상태와 다른 무기 한 개를 확보해 선택
하이라이트만 바뀌는지, 글자 픽셀 자체와 제원 데이터가 함께 바뀌는지
분리한다. 그 비교를 마친 뒤 디스크 자산 후보와 화면 좌표를 연결한다.

### 상태 비교 결과

무기 비교는 완료됐다. 화면 헤더와 항목 라벨은 고정되고, `打刀`에서
`レイピア`로 바꿀 때 무기명·제원 수치·무기 그림이 바뀌었다. 따라서 무기
화면은 고정 UI와 선택별 또는 동적 요소가 합성되는 경로로 조사한다.
`オプション` 정적 헤더 PoC 후보는 유지한다.

메인 메뉴는 두 캡처 모두 `ストーリー・モード` 선택 상태여서 상태 비교가
미완료다. 다른 메뉴 항목을 선택한 화면 한 장을 추가 확보한 뒤, 선택
하이라이트와 라벨 자산의 상태 변형 수를 확정한다.

### 메뉴 비교 완료

추가 캡처에서 `対戦モード`를 확인했다. `ストーリー・モード`와 비교하면
공통 선택 프레임은 유지되고 내부 문구만 교체된다. 메뉴별 전체 화면 교체보다
공통 배경 위에 선택 라벨을 합성하는 구조를 먼저 조사한다.

상태 비교 캡처 게이트는 대표 표본 기준으로 완료했다. 다음 단계는
`ストーリー・モード`, `対戦モード`, `オプション`을 화면 앵커로 삼아
DAT/TIM 후보와 실행 중 소비 경로를 연결하는 자산 조사다. 첫 변경 PoC는
여전히 접근·검증이 쉬운 정적 헤더 `オプション`을 `옵션`으로 교체하는
것으로 유지한다.

### 자산 조사 결과와 다음 게이트

대표 화면과 일치하는 표준 4bpp TIM이 확인되어 그래픽 우선 전략을
실제 자산 단위로 좁혔다. 첫 PoC 입력은 `DATA3/O04.DAT`의
`0x3CCC`에 있는 232×16 `オプション` TIM이다.

PoC는 다음을 동시에 검증한다.

1. 원본 TIM 디코드→인코드 무변경 라운드트립
2. 기존 팔레트·크기·TIM 전체 길이 유지
3. `옵션` 조판 뒤 허용 픽셀 영역 밖 바이트 불변
4. 원본 DAT 크기와 ISO 파일 extent 유지
5. DuckStation에서 옵션 진입 시 실제 한글 표시
6. 옵션 이동·복귀와 대표 메뉴·전투 진입 회귀

이 PoC가 통과하면 같은 DATA3 계열의 메뉴·선택·무기 정보판을 그래픽
번역 트랙으로 확대한다. 런타임 문자열·스토리 대사는 별도 조사 트랙으로
유지한다.

### 2026-07-29 런타임 중간 판정

수정 CUE를 DuckStation 0.1.11621에서 실행해 옵션 화면에 진입했고,
`옵션` 한글 헤더가 실제 게임 화면에 정상 표시되는 것을 캡처했다. 기존
팔레트와 주변 목판형 UI도 유지됐다. 따라서 `O04.DAT` 안의 표준 4bpp TIM을
고정 크기로 교체하고 Mode 2 Form 1 섹터를 재생성하는 경로는 대표 메뉴
그래픽 번역 방안으로 사용할 수 있다.

사용자가 옵션 이탈, 메인 메뉴 복귀, 옵션 재진입이 정상임을 확인했다.
따라서 `BBJ-POC-GFX-001`은 최종 통과이며, 같은 방식을
`DATA3/O12.DAT`의 메인 메뉴와 `DATA3/O02.DAT`의 선택·무기 UI로
확대한다. 이 판정은 고정 크기 표준 4bpp TIM 경로에 한정되며 동적 문자열,
다른 픽셀 포맷, 성장·재배치는 별도 게이트를 유지한다.

### 타이틀 PoC 완료와 다음 조사

사용자 편집본 `무사도의 검`을 `DATA3/O12.DAT`의 480×128 4bpp TIM으로
변환해 실제 화면 표시, 영문명·TM·배경 보존, 메뉴 선택 이동·복귀를
확인했다. `BBJ-POC-GFX-002`는 최종 통과다.

로딩 화면 우하단의 소형 일본어 로고는 `O12` 타이틀 로고를 한글로 바꾼
빌드에서도 일본어로 남았으므로 수정된 `O12` 공유 소비 가설을 기각했다.
DATA3 전수 목록에서 발견한 별도 전체 로고 `O01.DAT @ 0x7CB18`은
`BBJ-POC-GFX-003-CLUT`와 `BBJ-POC-GFX-003-PIXELS` 두 진단 빌드에서 모두
화면 변화가 없었다. 따라서 이 TIM의 로딩 화면 소비 가설도 기각했다.

DuckStation 텍스처 덤프를 이용해 실제 로딩 순간의 136x32 P4 로고를
확보했다. 정적 TIM 전수 목록과 대조한 결과 크기와 형태가 맞는 유일한
자산은 실행 파일의 `SLPM_860.20 @ 0x7657C`였다. 런타임 덤프와 정적 PNG는
16색 구성과 글자 형태가 일치한다. `BBJ-POC-GFX-004`는 이 TIM의 CLUT와
헤더를 보존하고 픽셀 인덱스만 반전했으며 정적 재삽입·EDC/ECC 검증을
통과했다. 실제 실행 화면도 검은 배경과 흰 로고로 반전되어 런타임
도달성을 확인했다. 이제 같은 136x32·4bpp·16색 제약으로 한글 편집본을
재삽입하고 타이틀 메뉴 진입 회귀를 확인한다.

사용자가 반전 변경을 확인하고 스크린샷을 남겨 `BBJ-POC-GFX-004`를
최종 통과 처리했다. `workspace/scripts/build_loading_logo_patch.py`는
136x32 불투명 편집 PNG를 원본 16색 CLUT에 매핑하고, TIM 이미지 payload와
해당 Mode2 Form1 섹터의 EDC/ECC만 재생성한다. 현재 편집 PNG는 원본과
동일하므로 빌드는 의도적으로 중단된다. 한글 편집본이 들어오면 실제 CUE/BIN
생성과 DuckStation QA를 진행한다.

스토리 1개 완료 루트에서 본편은 음성 전용, 마지막 엔딩 문구는
`DATA3/O15.DAT`의 베이크된 TIM 합성으로 판정됐다. 엔딩 캡처의 본문은
`0x3388`, 서명은 `0x6888`과 정확히 일치한다.

다음 우선 단계는 다음 두 트랙을 분리해 진행한다.

1. `O15.DAT`의 세로 엔딩 문구 5개와 서명 1개를 편집·재삽입할 수 있는
   엔딩 그래픽 PoC를 만든다.
2. 전체 TIM 3,696개를 디코드 픽셀 기준 2,261개로 중복 제거한 목록에서
   DATA3 일본어 후보 125개의 블록 경계와 런타임 도달성을 확정한다.
3. 다른 캐릭터·분기에서도 본편 자막 부재와 엔딩 자산 선택 방식을 표본
   확인한다.
4. 음성 대사까지 한글화할지 범위를 결정한 뒤, 필요하면 한 장면·두 문장의
   신규 자막 오버레이 PoC를 별도 착수한다.
