## 2. 검증 완료 — 여기는 다시 파지 말 것

파이프라인의 **모든 링크를 실측으로 확인했고 전부 정상**이다.

### 2.1 토큰

디스크의 `DATA7/V03.DAT @0x2C6D1`:

```
00301ACEGICKMOQCSUCWYB...
```

`00301` = 프레임 30 / 1줄. 이어지는 17글자가 셀 코드이고 번역문 17자
(공백 4개 포함)와 정확히 1:1 대응한다.

| # | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 | 9 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 글자 | 내 | ␠ | 뜻 | 과 | 는 | ␠ | 상 | 관 | 없 |
| 셀 | A | C | E | G | I | C | K | M | O |

| # | 10 | 11 | 12 | 13 | 14 | 15 | 16 | 17 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 글자 | 이 | ␠ | 베 | 고 | ␠ | 말 | 았 | 어 |
| 셀 | Q | C | S | U | C | W | Y | B |

**RAM에서도 동일하다** — `0x801786D1`에서 바이트 단위로 같은 문자열을
찾았다. 즉 게임이 읽는 문자열 자체는 정확하다.

### 2.2 글리프 아틀라스

K1US 섹션은 `DATA7/V03.DAT @0x2C72C`, 레코드 6개. 문제의 레코드는
인덱스 4 (`col1 = 섹션+0x1B00`, `col2 = 섹션+0x2180`, `clut = 섹션+0x2780`).

- COL1 13칸 = `내 ␠ 뜻 과 는 상 관 없 이 베 고 말 았` — 순서 정확,
  **슬롯 1(공백)은 실제로 비어 있다**
- COL2 12칸 = 0번에 `어`, 나머지 빈칸

### 2.3 VRAM (자막 표시 중 실측)

디스크의 스트립과 VRAM 내용을 **슬롯별로 바이트 비교 → 25/25 전부 일치**.

- COL1 → `(950, 256)`부터 16씩, 13칸
- COL2 → `(954, 256)`부터 16씩, 12칸

### 2.4 문자 → 인덱스 매핑

두 경로 모두 확인했다. 인덱스 = `문자 - 0x34`.

| 경로 | 점프 테이블 | 결과 |
| --- | --- | --- |
| 텍스트 렌더러 `0x80036EF4` → per-char `0x8003727C` | `0x800110CC` | 셀 문자 A~Y 전부 기본 경로 |
| **자막 드로어 `0x8003C5A8`** (자막이 쓰는 쪽) | **`0x80011574`** (`$s4`에 로드) | 셀 문자 A~Y 전부 기본 경로 |

두 테이블에서 특수 처리되는 문자는 `! " ' , - . ? \`` 8개뿐이고 우리
셀 문자와 겹치지 않는다. 따라서 `C` → 인덱스 15로 확정.

### 2.5 살아있는 템플릿 (RAM 덤프)

`0x80083774 + idx*16`의 엔트리 13~37을 전부 읽었다 — **25/25 정확**.
UV·CLUT(`0x7838`)·tpage(`0x003E`)가 모두 스톡 값이고, 계산된 VRAM 좌표가
2.3의 스트립 위치와 정확히 일치한다. 예: 셀 `C`(idx 15) → `(950, 272)`
= COL1 슬롯 1 = 빈칸.

### 2.6 advance(폭) 패치

`WIDTH_PATCH_FIRST=3`, `WIDTH_PATCH_COUNT=36` → 엔트리 3~38을 16으로 패치.
우리가 쓰는 셀 13~37이 전부 포함된다. 누락 없음.

## 3. 기각된 가설

| 가설 | 기각 근거 |
| --- | --- |
| 폰트가 16px에서 뭉개져 오독 | **오진이었다.** 프레임버퍼 열별 잉크를 세면 16px 빈칸이 4개여야 하는데 1~2개뿐 — 글자가 실제로 다르다 |
| `LoadImage` 비동기 DMA 충돌 (이름판 때의 원인) | VRAM이 25/25 일치하므로 업로드는 완벽 |
| 스트립 rect가 미국판 폰트 배치와 안 맞음 | 스톡 셀 좌표를 EXE에서 계산해 rect와 일치 확인 |
| 셀 문자가 드로어에서 특수 처리됨 | 두 점프 테이블 모두 기본 경로 |
| 워퍼가 템플릿 UV를 망가뜨림 | 살아있는 템플릿 25/25 정확 |
| 빌더가 공백 셀을 예산 초과로 제거(`blank_char` 스퀴즈) | 토큰에 `C`가 4개 그대로 있고 span도 여유 |

## 4. 남은 모순

입력(RAM의 토큰)도 맞고, 출력 재료(VRAM 글리프 + 템플릿 UV)도 맞는데
화면 결과만 다르다. **정적 분석으로 좁힐 수 있는 범위는 소진했다.**

프레임버퍼 실측 보조 자료:

- 자막 잉크 범위 x ≈ 160~445 (285px). 17셀×16 + `...` ≈ 287px과 부합하므로
  **그려진 셀 수 자체는 맞다** (이중 그리기 아님)
- 그런데 그 안에서 16px 폭의 빈 구간은 1~2곳뿐

즉 "셀 개수는 맞는데 특정 셀이 빈칸 대신 글자를 그린다".

## 5. 다음 수 — 드로어 문자 루프 계측

이 프로젝트에서 같은 종류의 교착(이름판 스텁이 왜 매칭 실패하는가)을 뚫은
방법은 **디버그 슬롯 계측**이었다. 정적으로 완벽해 보이는데 런타임이 다를
때는 런타임이 실제로 무엇을 받았는지 적게 만드는 것이 유일한 길이다.

### 만들 것

자막 드로어 `0x8003C5A8`의 문자 루프에 훅을 걸어, **그린 문자 코드와 그때의
x 좌표(그리고 계산된 인덱스)를 순서대로 풀 버퍼에 기록**하는 계측 빌드.

- 기록 위치: 풀 안 빈 영역 (현재 풀은 `0x801FB000..0x801FDF2C`, 여유 4.3 KB)
- 포맷 제안: `u16 char, u16 index, s16 x, s16 y` × N, 앞에 카운터 1워드
- 훅 지점 후보: `0x8003C6A0`(문자 로드 직후) 또는 `0x8003C748`(인덱스 확정 후)
  — 후자가 인덱스까지 같이 찍을 수 있어 더 낫다
- 안전장치: 카운터 상한을 둬서 버퍼를 넘지 않게 할 것

### 판정 방법

그 자막이 뜬 상태에서 RAM 덤프를 받아 버퍼를 읽는다.

| 관측 | 결론 |
| --- | --- |
| 기록된 문자열이 `ACEGICKMOQCSUCWYB`와 다름 | 드로어가 받는 문자열이 우리 토큰이 아니다 → 토큰 포인터/오프셋 계산 문제 |
| 문자열은 같은데 `C`의 인덱스가 15가 아님 | 인덱스 계산 경로에 우리가 못 본 분기가 있다 |
| 문자·인덱스 모두 정확한데 화면이 다름 | GPU 프리미티브 생성 이후의 문제 → OT/프리미티브 버퍼를 덤프해서 봐야 한다 |

### 주의

- 계측 빌드는 **배포본과 분리**할 것. `dist/`는 이미 검증 완료 상태다.
- 빌드 순서는 `docs/build.md`의 "최종 빌드" 절 그대로
  (`build_usa_subtitle.py` → `build_usa_tim_patch.py` → `build_usa_ui_patch.py`).
  계측은 첫 단계 산출물에만 얹으면 된다.
- 대상 BIN을 DuckStation이 열고 있으면 빌드가 `PermissionError`로 죽는다.

## 6. 영향 범위 (배포 판단용)

- 이 결함은 **자막 내용이 아니라 표시**의 문제다. 디스크와 RAM의 번역문은
  정확하므로 데이터 재작업은 필요 없다.
- 얼마나 많은 줄이 영향받는지는 **아직 조사하지 않았다.** 이 줄은 COL1 13칸을
  꽉 채우고 COL2로 넘어간 몇 안 되는 레코드 중 하나라 특수한 조건일
  가능성이 있다. 조사하려면 전 파일의 레코드 중 `col2 != 0`인 것과 공백
  셀(`blank_char`)을 여러 개 쓰는 것을 집계해 보면 된다.
- 현재 배포본은 이 결함을 안은 상태다. 심각도 판단 후 재배포 여부를 정한다.

## 7. 2026-08-11 후속 조사 — 원인 확정 및 수정 후보

### 7.1 최초의 잘못된 상태

기존 RAM 덤프에서 텍스트 렌더러가 만든 28바이트 SPRT 프리미티브를
템플릿 바이트 `+4..+15`로 역추적했다. 실제 패킷은 15개였고 순서는 다음과
같았다.

```
ACEGIKEMOQESUWY
```

이 문자열은 `V03.DAT` 레코드 1의 표시 토큰(`0x8017864F`)과 정확히 같다.
화면의 `내 뜻과는상뜻관없이뜻베고말았`도 이 셀 코드를 **레코드 4
아틀라스**로 해석한 결과와 정확히 일치한다.

같은 덤프에서 풀의 `last_token @0x801FB4A0`도 `0x8017864F`였다. 즉 CPU의
토큰 선택과 프리미티브 생성은 둘 다 레코드 1로 일치하지만, 공유 VRAM
스트립에는 앞서 올라간 레코드 4 픽셀이 남아 있었다.

원인 사슬은 다음과 같다.

```
파일 스트립 LoadImage를 직접 호출
→ 비동기 DMA2 완료 전에 반환
→ last_token은 레코드 1로 갱신되어 재업로드가 차단됨
→ 레코드 1 프리미티브가 레코드 4 픽셀을 샘플링
→ 다른 한글 및 누락처럼 보이는 화면 결과
```

따라서 3절의 “VRAM 25/25 일치이므로 비동기 충돌이 아니다”는 기각 근거가
아니었다. 그 일치는 오히려 **새 레코드의 업로드가 아직 반영되지 않았음**을
보여 준 증거였다.

### 7.2 수정

`workspace/scripts/build_usa_subtitle.py`에 파일 스트립 전용
`build_wait_load_stub()`를 추가했다.

- 주소: `0x801FDBAC`
- 동작: DMA2 busy bit를 bounded wait → `LoadImage` → 다시 bounded wait
- 적용 범위: 파일 레코드의 COL1/COL2/DIG 스트립 업로드 3곳
- EXE 자막/이름판의 기존 per-glyph uploader는 그대로 유지
- 풀: `0x801FB000..0x801FE02C` (12,332 B)

기존 미국판 RAM 캡처에서 옛 풀 끝 `0x801FDF2C`부터 `0x801FF000`까지
4,308바이트가 모두 0이었다. 새 스텁은 그중 256바이트만 사용한다.

### 7.4 런타임 결과: DMA wait 단독 원인 가설 기각

사용자가 위 수정 후보를 같은 장면에서 실행했으나 증상은 동일했다. 따라서
7.1의 관측 자체(`last_token`/프리미티브는 레코드 1, 화면 해석은 레코드 4)는
유지하되, **DMA2 대기만 추가하면 고쳐진다는 원인 가설은 기각**한다.

수정 빌드의 라이브 RAM에서도 다음이 다시 확인됐다.

- `last_token @0x801FB4A0 = 0x8017864F`
- 프리미티브 15개 = `ACEGIKEMOQESUWY`
- 화면 결과는 기존과 동일

다음 판정점은 문자 루프가 아니라 파일 래퍼가 선택한 K1US 엔트리와 실제
업로드 분기다. `--trace-file-upload` 계측 빌드를 별도로 만들었다.

| 항목 | 값 |
| --- | --- |
| CUE | `build/usa_subtitle_render_trace/Bushido Blade (USA) [KO Subtitle Render Trace].cue` |
| BIN SHA-256 | `4875B1AC9BA91629A8ED372D93DFC9D906C4EE11AB146B3EAC7BD58C8070B2D1` |
| trace 주소 | `0x801FB05C` |
| wrapper | 1,040 B, cave 여유 145 B |

trace는 마지막 매칭의 토큰, 섹션, 엔트리, COL1/COL2/DIG 오프셋,
직전 `last_token`, 업로드 선택/완료 플래그, 매칭 횟수를 보존한다.
재현 뒤 다음 명령으로 읽는다.

```powershell
python .\workspace\scripts\read_usa_file_upload_trace.py `
  --address 0x801FB05C `
```

### 7.5 Trace 2로 확정한 근본 원인과 Fix 2

Trace 2 결과:

```
token          = 0x8017864F  (V03 record 1)
candidate_base = 0x80130430
record_index   = 4
section        = 0x8017872C
entry          = 0x80178784  (V03 record 4)
```

`0x80130430 + 0x482FC = 0x8017872C`이다. `0x482FC`는 **V02의 K1US
섹션 오프셋**이다. 즉 V03 레코드 1 토큰에서 V02 레코드 4 오프셋을 빼 만든
거짓 base에 V02 섹션 오프셋을 더했더니, 우연히 실제 V03 K1US 헤더에
도착했다.

기존 래퍼는 모든 파일에 공통인 첫 단어 `K1US`만 확인했다. 그래서 이
cross-file alias를 V02 레코드 4 매치로 오인했고, 실제 주소가 V03 섹션이므로
V03 엔트리 4의 아틀라스를 올렸다. 이것이 레코드 1 셀 코드와 레코드 4
글리프가 결합된 정확한 원인이다.

Fix 2 변경:

- K1US 헤더를 `magic, crc32(source_path), record_count, entries...`로 확장
- 파일 테이블에 같은 경로 태그 저장
- 후보 판정에서 `magic`과 `path_tag` 두 단어를 모두 비교
- 엔트리 시작 위치를 섹션 `+8`에서 `+12`로 갱신
- 실패한 DMA wait 변경은 제거
- 11개 대상 경로 태그의 고유성을 빌드 게이트로 검사
