# Bushido Blade 미국판(SCUS_941.80) 한글화 인수인계

> **신규 트랙.** 일본판 트랙(`HANDOFF_2026-08-01.md`, 1~47절)과 구분한다.
> 일본판 문서는 수정하지 않는다. 일본판에서 검증된 기술·주소는 이 문서에
> 필요한 만큼만 재기록한다.

## 0. 방향 전환의 이유 (2026-08-02)

일본판에서 엔딩 자막은 마지막 단계에서 막혔다:

- 조회 체인·타이밍·VRAM 배치·훅 시점까지 전부 검증 완료 (JP 문서 40~47절)
- 그러나 **영상 재생 루프 안에서 공식 렌더러를 호출하면 GPU가 웨지**된다
  (JP 47절: 전송 제거·업로드 제거로도 영상 정지 재현)
- 근본 원인: **일본판은 영상 위에 텍스트를 그리는 기능이 없는 판**이다.
  영상 버퍼가 폰트 셀 영역(x 0~960)을 덮는 VRAM 배치 자체가 그 증거.

**미국판은 영상 위 자막이 원래 동작한다** (갤러리 엔딩 실측, 스크린샷 확인).
우리가 만들려던 기능이 이미 존재하므로, 한국어 글리프만 얹으면 된다.

### 1.2 글리프 시스템 — 일본판과 완전 동일 (주소만 이동)

| 항목 | JP | **USA** |
|---|---|---|
| 텍스트 렌더러 | 0x80038B80 | **0x80036EF4** |
| 글리프 빌더 | 0x80038F3C | **0x8003727C** |

→ **JP에서 검증한 셀 하이재킹·CLUT 패치·폭 패치 기법이 그대로 적용된다.**

### 1.3 영상 자막 시스템 (JP에는 없는 것)

- 자막 그리기: **0x8003C5A8** (진입) → 0x8003C868 (렌더러 3회 호출, 다른 일 없음)
- 표시 상태 전역: **gp+0x424** = 현재 레코드 포인터, **gp+0x420** = 자체 프레임 틱
  - 드로어가 매 호출 +1 (0x8003C7E0), 세터가 레코드 시작 시 0으로 리셋
  - → **`gp+0x420 == 0` = "레코드 방금 시작" 무상태 트리거로 사용 가능**
- 레코드 형식(영상 파일 내, ASCII): `"%04d%d"` = 4자리 프레임 + 1자리 줄 수,
  이어서 줄 수만큼 null 종단 ASCII 문자열
  (우리 빌더 `collect_movie()`가 이미 이 형식을 파싱한다)
- 호출부: 0x800456F0 `lh gp+0x5CC`(활성 플래그) → beqz skip → jal 0x8003C5A8
- **영상 재생 중 이 경로 전체가 네이티브로 동작** — 렌더러 호출이 영상과
  충돌하지 않음이 게임 자체로 증명돼 있다 (JP에서의 GPU 웨지 문제 원천 부재)

## 2. 설계 (초안)

### 2.1 데이터
영상 파일(O05..O14 상당)의 ASCII 자막 텍스트를 **셀 코드 문자열로 교체**.
- 네이티브 형식(`"%04d%d"` + 줄들)을 유지하면 **타이밍·줄 분할·스케줄링을
  전부 게임이 해준다** (JP처럼 자체 스케줄러를 만들 필요 없음)
- 한국어 셀 코드는 원문보다 짧은 경우가 많아 in-place 교체 가능성 있음.
  안 되면 JP v37 재배치 파이프라인 이식 (로드 테이블 MSF 형식 확인 필요)
- 레코드별 한국어 글리프 아틀라스를 파일에 부가 섹션으로 추가

### 2.2 코드 (케이브 래퍼)
훅: **0x8003C868** (자막 텍스트 드로어) — 자막 활성 시에만 호출됨.
```
stub:
  if gp+0x420 == 0:            ; 레코드 방금 시작 (무상태 트리거)
      레코드 포인터(gp+0x424)로 아틀라스 탐색
      col1/col2/dig/CLUT 4블록 LoadImage   ; 레코드당 1회
  템플릿 CLUT/폭 패치
  jal 0x8003C868 원본 본체
  템플릿 복원
```
- 렌더러는 **게임이 부른다** — 우리는 앞뒤로 테이블만 패치/복원
- 업로드는 레코드당 1회 (초 단위) — 매 프레임 DMA 없음
- JP의 검증 기법 재사용: CLUT/tpage/폭 패치·복원 루프, 34셀 예산,
  'Z' 셀 제외 규칙, 레코드별 아틀라스 포맷

### 2.3 확정된 인프라 (2026-08-02 실측)

1. **코드 케이브 = `0x80011E34` .. `0x80012305` (1233바이트)**
   - JP 케이브(0x800118B4..0x80011D85)와 **바이트 단위 동일 내용**, +0x580 이동
   - 참조 79건은 전부 디버그 printf 문자열 포인터 — JP의 검증된 케이브도
     같은 성격의 참조 72건을 갖고 20여 빌드에서 무해했음 (동일 등급 안전)
   - 경계: 직후에 `CD_sync` 등 참조 데이터 (JP와 같은 구조)
2. **파일 로드 테이블**: JP와 동일 형식 (8바이트/{BCD MSF, size})
   - O05 엔트리 `0x80086D0C`, O14 `0x80086D54`, V00 `0x80086E5C`, V08 `0x80086E9C`
   - JP의 msf_word()·재배치 파이프라인(v37) 그대로 이식 가능
3. 영상 파일 경로: DATA3/O05..O14 (1.6절, JP 동일)

### 2.5 드로어 내부 구조 (0x8003C5A8 역어셈블, 2026-08-02)

```
[gp+0x424] = 레코드 슬롯 포인터
  slot+0 = 현재 토큰 포인터 ("%04d%d" ASCII, 파일 버퍼 내부)
  slot+4 = 다음 토큰 포인터 (대기 분기 0x8003C7C0에서 미리보기)
드로어 동작:
  토큰의 4자리 ASCII → 프레임 번호 (십진 변환)
  줄 수 = 5번째 자리
  tick(gp+0x420) < frame → 대기 (tick++만 하고 반환)
  tick >= frame → 줄 그리기:
    y = 0xC8(200) - (줄수-1)*8
    문자별 디스패치: char-0x21 < 0x40 이면
      jr [0x80011574 + (char-0x21)*4]   ← 문자 점프 테이블 (0x21~0x60)
    폭 테이블 0x80083D74 참조, sp+0x10 버퍼에 축적 → 렌더 헬퍼
```

- **셀 코드 문자('A'~'Z','0'~'9' 등)는 전부 0x21~0x60 범위 안** — 교체 안전
- 텍스트는 파일 내 ASCII 그대로 → **in-place 교체로 타이밍·스케줄링 무손실**

### 2.6 설계 확정 — 전역 아틀라스 + 템플릿 UV 패치 (런타임 DMA 제로)

번역 전체(259행)의 고유 음절 = **371자** → 4bpp 텍스처 페이지 2장
(페이지당 16×16 글리프 256자, 총 512 용량)에 전부 수용.

따라서 JP식 "레코드별 픽셀 업로드"가 불필요하다:

1. **부팅 시 1회** 전역 한글 아틀라스(371자)를 VRAM에 업로드
2. 레코드 표시 시작 시(gp+0x420==0) **템플릿 테이블(0x80083774)의
   U/V/tpage만 패치** (엔트리당 4~6바이트 메모리 쓰기 × ~34개)
   — 'A'→글리프#n 매핑을 레코드마다 바꿈
3. 레코드별 데이터 = UV 매핑 ~136B (픽셀 ~3KB 대비 1/20)
4. **게임플레이 중 DMA 전무** → JP를 좌초시킨 GPU 충돌 원천 차단

### 2.7 로더 전역 확정 (2026-08-02)

- 로드 테이블 베이스 = **0x80086A5C** (참조 로더 군집 0x80042950~0x80042C18)
- 로더 상태 블록 = 0x8013D0D0~0x8013D108
  - **마지막 파일 ID = 0x8013D0D4** (sh, JP 0x8013E6C0 상당)
  - **목적지 버퍼 포인터 = 0x8013D0EC** (sw, ID+0x18 — JP 0x8013E6D8과
    동일 간격. 런타임 검증 예정)
- → 레코드 키잉은 JP 검증 방식 그대로: base=[0x8013D0EC],
  word3=[base+0xC] 지문으로 파일 식별 + 토큰의 4자리 프레임 숫자로 레코드 식별

### 2.8 전역 아틀라스 기각 — VRAM 실측 (2026-08-02)

`vram_usa_ingame.png`(전투 중) × `vram_usa_ending.png`(영상 중) 교집합:
**완전히 빈 16행 밴드가 전체 VRAM에 단 1개** (960,112). 전투 텍스처가
후보 페이지를 85~100% 점유한다. → **영구 전역 아틀라스는 불가.**

2.6절의 "부팅 1회 업로드" 설계는 기각한다. UV 패치 아이디어 자체는
유효하나, 픽셀은 컨텍스트별로 올려야 한다.

### 2.9 확정 설계 (수정) — JP 검증 방식의 USA 이식

파일별 고유 음절: O14=267(엔딩 13개 합산, **엔딩당 ~20-40**),
O05=123, V0X=42~105, EXE=90.

**JP v38에서 검증된 레코드별 셀 하이재킹을 그대로 이식한다:**
- 레코드 시작(gp+0x420==0) 시 스톡 폰트 셀에 그 레코드의 글리프 업로드
  (34셀 예산, 'Z' 셀 제외 규칙 등 JP 기법 전부 재사용)
- 템플릿 CLUT/폭 패치 → 게임 드로어가 그림 → 복원
- 데이터: 파일 부가 섹션에 레코드별 아틀라스 (JP v37 파이프라인 이식)

**유일한 미검증 리스크**: USA 영상 재생 중 LoadImage가 안전한가.
- JP를 좌초시킨 GPU 웨지는 JP 엔진 특성일 수 있음 (USA는 영상 버퍼
  배치부터 다름). 실측으로만 판정 가능.
- 안전하면: 완성. 불안전하면: **엔딩 시작 시 선업로드**로 후퇴
  (엔딩당 20-40자라 스톡 셀 + 인접 여유에 수용 가능, 재생 중엔
  UV 패치만 = 메모리 쓰기 전용)

검증 순서: ① 승리 장면(비영상, 안전) → ② 영상 (DMA 리스크 판정)

  → **번역 축약 필요** (예: "간다!" 5바이트) — 사용자 결정 대기
- 섹션 형식: `K1US` + count + {token_offset, col1/col2/dig/clut off} + 블롭.
  키는 **token_offset** (프레임 번호는 파일 내 중복 있어 키 불가)
- 재배치: v37 파이프라인 이식 (디렉터리 레코드 양엔디안 패치,
  로드 테이블 8바이트 유일 매치 교체, PVD 볼륨 크기)

### 2.13 스테이지 B — 래퍼와 첫 런타임 (2026-08-02)

**갤러리 상시 해제** (b2부터): 마스크 읽기 2곳
(`0x80048268`/`0x800484CC`, `lw $v0,0x10D8`) → `addiu $v0,$zero,-1`.

### 2.14 b3 런타임 — 결정적 진단 (2026-08-02)

b3(CLUT 매 프레임 재업로드)도 한글 불가시. 라이브 판독으로 **원인이

```

gp+0x420 tick = 120
gp+0x424 rec  = 0x80086478      <- EXE 내장 테이블!
  slot+0 token ptr = 0x800A0AF8
  token bytes: "01200\0\0\0" "01500\0\0\0" "00600\0\0\0"

[0x8013D0D4] last file id = 0x5F
```

**드로어가 읽는 레코드는 파일 버퍼가 아니라 EXE 내장 테이블

실패** → 업로드 안 됨 → 한글 없음.

b2의 `" ! eady!?"`(대문자만 소실)도 이걸로 설명된다: 업로드는 실패했고,
**폭/템플릿 CLUT 패치만 적용**되어 스톡 대문자가 우리 CLUT로 그려져
투명해진 것. 소문자·특수문자는 패치 범위(엔트리 3~38) 밖이라 생존.

### 2.15 정정: 2.9절 설계의 전제 오류

2.9절은 "레코드 = 파일 섹션에서 조회"를 전제했다. 실제로는 드로어가
**두 출처**를 갖는다:
- EXE 내장 테이블 (세터 `0x8003C4D8`/`0x8003C568`/`0x8003C578`가 세팅)

### 2.16 갤러리 언락 — 마스크 패치 무효

`0x80048268`/`0x800484CC`를 `addiu $v0,$zero,-1`로 바꿔 어셈블까지
확인했으나(역어셈블 검증 완료) 갤러리는 여전히 잠김이고
`[0x800A10D8]`도 0. **이 마스크는 갤러리 항목 잠금의 실제 게이트가
아니다.** JP에서 poke가 통했던 것과 대비되므로 USA는 별도 게이트를
쓴다. 재조사 필요.

### 2.18 스테이지 B4 — 토큰 포인터 키잉 + EXE 자막 (2026-08-02)

**사전 실측 (설계 확정 근거)**

- **`work/analysis/ram_*.bin` 6종은 전부 JP 디스크 덤프다** (USA EXE 정적

- **0x80086458 = (표시 토큰 ptr, 숨김 토큰 ptr) 쌍 테이블** 확인.
  EXE 토큰 본문은 0x8001129C..0x8001157B (정적, 파일 오프셋 0x1A9C..),
  숨김 토큰은 0x800A0AE8.. ("00900","01200",... 0줄). b3 라이브 판독의
  rec=0x80086478/T=0x800A0AF8은 이 테이블의 숨김 토큰 국면이었다.
  → **토큰 포인터는 출처 불문 유일 키로 성립.**
- 파일 지문: w3(+0xC)·w4(+0x10) 2워드. V0X는 w3/w4 전부 상이,
  O05/O14는 w4가 같지만(0x80) w3(=파일 크기)이 다름 → 조합 유일.
- 디스크: EXE(LBA 24, 291섹터) 직후 **LBA 315..500 갭 185섹터** —
  EXE를 제자리 확장 가능 (재배치 불필요).

**설계**

1. **래퍼 룩업 재설계**: `T = [[gp+0x424]+0]` 기준 3경로.
   - ① EXE 엔트리 테이블(19개) 주소 정확 일치 탐색
   - ② 파일: 레코드별 `cand = T - token_offset` 역산 →
     `[cand+0xC]==w3 && [cand+0x10]==w4` 지문 검증 (레인지 가드
     `cand>>22 == 0x200`). **로더 전역 [0x8013D0EC] 의존 완전 제거**
     (b3 실패 원인 — 마지막 로드 파일이 자막 파일이라는 보장 없음).
   - ③ 전부 미스 → **무패치로 원본 드로어 호출** (페일세이프.
     b2의 '스톡 대문자 소실'은 미스 시에도 패치했기 때문).
2. **EXE 자막 19레코드**: 토큰 in-place 셀 코드 교체(전부 스팬 내) +
   **글리프 풀** (음절 dedup 92자 × 128B). 업로드는 레코드 시작
   (tick==0) 시 셀 단위 LoadImage (엔트리 {x,y,src} × n, 스크래치
   RECT에 x/y 기록). CLUT은 양 경로 모두 매 프레임 재업로드(b3 유지).
3. **풀 배치**: 모든 래퍼 데이터(RECT·폭 백업·EXE/파일 테이블·오프셋
   배열·글리프 풀) = 14,260B를 **0x801FB000**에. 운반은 EXE 이미지
   확장(+16KB, t_size 0x91000→0x95000, LBA 갭 흡수)으로, **헤더 pc를
   0x800A1000 부트 스텁으로 리다이렉트** → 풀 복사 → 케이브 피니셔가
   확장 영역(0x800A1000..0x800A5000) 전체 제로화(BSS 원상) →
   원 엔트리 0x8006F004 점프.
4. 케이브 = 코드 전용: 래퍼 884B + 피니셔(0x800121A8), 여유 301B.
5. O05 idx7 "소생, 가겠소!" → **"가겠소!"** (CSV 수정, 예산 7B 내).
   → **파일 167/167 + EXE 19/19, 스킵 0.**

**리스크 (런타임 판정 항목)**

1. **0x801FB000 밴드가 USA에서도 빈 영역인가** — JP 실측 + 동일 엔진
   유추일 뿐. 풀 끝 0x801FE7B4, 관측 스택 하한(JP)까지 여유 ~2KB.
   → USA 전투/영상 중 RAM 덤프로 0x801FB000..0x801FF000 제로 확인 요망.
2. 영상 재생 중 LoadImage 안전성 (2.9 기존 리스크, 미판정).
   불안전 시 후퇴안 동일 (엔딩 시작 선업로드).
3. BSS 확장 영역을 게임이 제로 전제로 쓰는지 — 피니셔가 제로화하므로
   원상과 동일하나, 부트 스텁 실행 자체가 신규 경로 (부팅 확인 필요).

   숨김 토큰이면 tick==0 시점 룩업 미스 → 업로드가 영영 없음 →
   CLUT/폭 패치만 적용돼 투명. (파일 경로 룩업 자체는 승리 장면
   한글 표시로 **베이스 역산·지문 검증 동작 증명**.)

**b5 수정 (`build/usa_b5`)**:

1. 업로드 게이트를 tick에서 **토큰 포인터 변화 감지**로 교체:
   풀에 last_token 1워드(0x801FB04C), 매치 시 T ≠ last이면 픽셀
   업로드 + 래치, 미스(plain) 경로에서 래치 0 클리어 (장면 재진입
   시 재업로드 보장). 래퍼 920B, 케이브 여유 265B.
2. **갤러리 게이트 해결**: 마스크 0x800A10D8 접근 지점은 총 9곳
   (0x10D8 즉치 전수 스캔 + 문맥 역어셈블). b3이 패치한 2곳은 일부
   판독일 뿐, **실제 항목별 게이트는 비트 테스트
   0x80048368(`mask&(1<<slot)`)·0x800483C4(`mask&(0x40<<slot)`)**.
   UI측 판독 7곳 전부 `li -1` 강제:
   0x80048268/0x800484CC/0x800481D4/0x80048298/0x800484FC/
   0x80048368/0x800483C4.
   **비패치 유지**: 해금 세터 RMW(0x800477B8→0x800477C8 `mask|=bit`),
   세이브 직렬화 0x80063418/역직렬화 0x800634C0 — 세이브 데이터는
   정직하게 유지.

**b5 검증 항목**: ① 승리 다중 대사 전환 ② 도입 영상 자막
③ 갤러리 전체 해제 → 엔딩 재생 ④ 엔딩 자막 (영상 중 DMA 리스크
최종 판정 — 유일 잔존 리스크).

### 2.20 b5 런타임 → b6 (2026-08-03)

**b5 런타임 결과**: 갤러리 해제 성공, **엔딩(O14) 자막 한글 성공**
(다중 레코드 포함 — 토큰 변화 감지·베이스 역산 전부 실증), 전투 대사
정상. 잔여 3건과 원인:

1. **쉼표가 셀 중앙 높이에 떠 보임** — render_glyph_fit이 잉크를
   수직 중앙 정렬. 쉼표처럼 베이스라인 아래 글리프가 중앙으로 떠오름.
2. **도입 영상(O05) 여전히 무자막** — b3 진단 재현: FMV 재생 중
   **CLUT 업로드(매 프레임)가 드롭**된다 (엔딩 O14는 66KB 소용량 =
   실시간 렌더 장면이라 통과, O05 523KB = FMV라 실패). 픽셀 스트립
   업로드는 FMV 중에도 착지함이 b3 VRAM 덤프로 확인돼 있다.
3. **CONTINUE 화면 글자 깨짐** ("당ONT.IU히? 5") — 셀 하이재킹이
   스톡 폰트 픽셀을 덮은 채 복원하지 않음. 게임의 원본 폰트 재업로드는
   장면 전환 시에만 일어나므로(JP 문서 202행) 같은 장면 내 스톡 텍스트
   (전투 사망 → CONTINUE)가 한글 글리프로 그려짐. 숫자 '5'가 멀쩡했던
   것은 그 레코드가 COL1 셀만 하이재킹했기 때문.

**템플릿 엔트리 레이아웃 해독** (0x80083774, 16B/엔트리):
`+0..3 헤더(80 80 80 2C) | +4 u0,+5 v0 | +6..7 CLUT | +8 u1,+9 v1 |
+10..11 tpage | +12 u2,+13 v2 | +14 u3,+15 v3` (4모서리 UV).
인덱스 매핑: **'0'~'9' → 3+n** (셀 = (920,400) 3×3 그리드, CLUT
0x7678), **'A'~'Z' → 13+n** (셀 = (950/954,256..) 열, CLUT 0x7838).
'.'=엔트리 0. 스톡 문자 CLUT 0x7838 실측(VRAM PNG): idx1=검정,
idx2~5=회색 계조, **idx6=흰색**.

**b6 설계·구현 (`build/usa_b6`)**:

1. **CLUT 업로드 전면 제거** (원인 2 해소): 글리프 픽셀을 스톡 CLUT
   0x7838 인덱스로 렌더 (fill=6 흰색, stroke=1 검정). 표시 중 템플릿
   CLUT 패치는 0x7838 통일(메모리 쓰기 전용) → **런타임 DMA는 레코드
   시작 시 픽셀 업로드뿐** (FMV 중 착지 확인된 유형).
2. **EXE(전투) 레코드 스톡 셀 하이재킹 폐지** (원인 3 해소): 글리프를
   실측 프리 VRAM 밴드 **(960,112) 16셀**(x=960+4k, 2.8절 실측 유일
   빈 밴드)에 업로드하고, 사용 셀의 템플릿 엔트리 UV(u=16k, v=112~127)
   ·tpage(0x3E→**0x2F** = x페이지 15·y베이스 0)를 **매 프레임 패치**.
   스톡 폰트 픽셀 무손상 → CONTINUE 정상. (JP v51에서 tpage 이동
   기법 자체는 비영상 컨텍스트 검증 완료. 전투는 비영상.)
3. **템플릿 복원 = 원본 576B(엔트리 3~38) 통복사** (풀에 베이크) —
   CLUT·UV·tpage 복원을 하나의 루프로 대체.
4. **쉼표 수정** (원인 1): usa_render_glyph_fit — 베이스라인 보존
   수직 배치 (잉크 y오프셋 유지, 클램프). v36/v37 모듈에 몽키패치해
   파일 섹션 파이프라인도 동일 적용.
5. 파일 경로는 검증된 스톡 셀 스트립 방식 유지 (엔딩 실증).
   승리/영상 후에는 장면 전환 폰트 재업로드가 셀을 원복한다.

풀 14,808B (0x801FB000..0x801FE9D8), 래퍼 956B(케이브 여유 229B).
검증: 템플릿 백업 원본 일치, EXE 글리프 엔트리(A→13, C→15, E→17,
슬롯 0..), 글리프 니블 = {0,1,6}.

**b6 검증 항목**: ① 도입 영상 자막 ② CONTINUE 화면 정상 ③ 쉼표
위치 ④ 전투 자막이 (960,112) 밴드에서 정상 표시(스톡 텍스트와 동시
표시 포함) ⑤ 기존 통과 항목 회귀 (승리·엔딩·갤러리).

### 2.18 스테이지 B4/B5/B6 — 대부분 완성, O05만 잔여 (2026-08-02)

**B4 재설계** (2.17-1 반영): 룩업 키를 로더 전역에서
**토큰 포인터 `[[gp+0x424]+0]`** 로 교체. EXE/파일 두 출처 모두 커버.
미매칭 시 **패치 없이 원본 드로어 호출**(fail-safe) — b2에서 스톡
대문자가 사라진 것은 매칭 실패인데도 CLUT을 패치했기 때문이었다.

동시에 완료된 것들:
- **EXE 내장 자막 19개 전부 교체** (전투 전 대사). 토큰 영역
  `0x8001129C..0x80011D71` 실측 확정 — 케이브(0x80011E34)와 비겹침
- **글리프 풀**: 고유 92자, 부팅 스텁이 `0x801FB000`에 1회 복사
- **스킵 0건** — "Ready!" 포함 167 파일 레코드 + 19 EXE 레코드 전부 수용
- **갤러리 게이트 7곳** 패치 (b3의 2곳으로는 무효였음).
  세이브 데이터 경로(0x800477B8/0x80063418/0x800634C0)는 미변경

**빌드 파이프라인 버그 2건 수정**:
1. EXE 뒤 여유가 **0섹터**인데(다음 extent = BIN1 디렉터리 @LBA 315)
   확장을 시도해 파일시스템 손상. → **EXE도 이미지 끝으로 재배치**
   (부트로더는 루트 디렉터리 레코드로 EXE를 찾으므로 LBA+크기 패치로 충분)
   갭 계산에서 디렉터리를 제외한 것이 원인이었다.
2. 파일 지문으로 `+0xC`/`+0x10` 워드를 썼는데, O05/O14는 **컨테이너**이고
   `+0xC`는 **파일 끝 오프셋**이다. O05는 그 값(0x7FB98)이 자기 섹션
   오프셋과 정확히 일치해 검증이 자기 자신과 충돌. → **섹션 매직
   `K1US`를 후보 base에서 직접 확인**하도록 변경 (헤더 구조 무관).

**B5/B6 런타임**: 전투 전 대사·승리 대사·엔딩·갤러리 **전부 정상 동작**.
**도입 컷신(O05)만** 셀 코드가 스톡 폰트로 표시 = 래퍼가 매칭 실패 후
fail-safe 경로로 빠짐.

정적 대조로는 O05가 O14/V00과 구조·매직·블록 레이아웃 모두 동일해
차이를 찾지 못했다. **실측 필요**: 도입 컷신 재생 중
- 토큰 포인터가 가리키는 RAM 영역
- `토큰 − 섹션오프셋` 위치의 `K1US` 존재 여부 (= 파일 전체 로드 여부)

유력 가설: O05는 523KB로 커서 **자막 블록만 부분 로드**되어 우리 섹션이
메모리에 없을 가능성. (O14=66KB, V00=221KB는 전체 로드 추정)

**현재 산출물**: `build/usa_b6` — 도입 컷신 외 전 컨텍스트 한글 표시.

### 2.19 완성 — B7 (2026-08-02)

**`build/usa_b7`에서 전 컨텍스트 한글 표시 확인.**
도입 컷신 · 전투 전 상대 대사 · 승리 대사 · 엔딩 · 갤러리 전부 정상.

#### O05만 실패했던 원인 (확정)

O05/O14는 컨테이너(`count=2` + `count+1`개 블록 오프셋 @+4)이고
**마지막 블록이 원본 파일 크기에서 정확히 끝난다.** 우리가 섹션을
파일 끝에 덧붙이면 그 블록 **밖**이 된다.

- O14(66KB)는 통째로 읽히므로 섹션도 함께 RAM에 올라와 동작
- **O05(523KB)는 자막 블록만 부분 로드** → 섹션이 RAM에 없음 →
  래퍼가 base를 버퍼 밖으로 계산 → 범위 검사에서 탈락 →
  fail-safe(원본 드로어 호출)로 빠져 셀 코드가 스톡 폰트로 표시

정적 비교로는 O05와 O14가 구조·매직·블록 레이아웃 모두 동일해
차이를 찾을 수 없었다. **파일 크기 차이(523KB vs 66KB)** 가 유일한
변수였고, 그것이 부분 로드 여부를 갈랐다.

#### 수정

컨테이너의 **종단 오프셋을 새 파일 크기로 확장**해 섹션을 마지막
블록 안으로 편입 (4바이트 변경). O05·O14 양쪽 적용, 엔딩 회귀 없음.
안전장치: 블록 수 1~8, 첫 오프셋이 헤더 크기와 일치, 종단 오프셋이
섹션 시작과 일치할 때만 적용.

| 데이터 | 167 파일 레코드 + 19 EXE 레코드 = **186개 전부 교체, 스킵 0** |
| 대상 파일 | V00~V08, O05, O14 (재배치) + SCUS_941.80 (재배치) |

### 4.1 캐릭터 선택창 이름 — 텍스트 경로 (이미지 아님)

```
  $a0 = [0x80080F18 + s0]       ; 이름 문자열 포인터 테이블
호출 함수: 0x80032728 (2곳: 0x8003294C, 0x80032AC8 경유 0x80032BB4)
```

**구현 상태**: 빌더에 문자열 교체 + EXE 레코드 등록 + 이름 스텁까지

여유 237B)를 전혀 건드리지 않는다.

- `NAME_STUB_SIZE = 0x200` 슬롯을 풀 선두에 예약, 나머지 구조체는 그만큼
  뒤로 이동 (`scratch_rect` 등 고정 오프셋도 함께 시프트)
- `POOL_BASE`를 `0x801FA000`으로 4KB 낮춤 (이름 글리프 추가로 16856B →
  한계 초과했던 것 해소; 최종 17368B / 20480B)
- 스텁 동작: `$a0`(문자열 주소)로 EXE 레코드 테이블 워크 → 글리프 업로드
  → 템플릿 UV/tpage 패치 → 렌더러 호출 → 템플릿 복원. 미매칭 시 렌더러만
  호출 (fail-safe)
- 훅: `0x8003294C`, `0x80032BB4` → `jal 0x801FA000` (검증 완료)

## 5. c 계열 — 캐릭터 선택 이름판 (2026-08-03)

### 5.1 증상과 오진
- `c1` (POOL_BASE를 0x801FA000으로 4 KB 내리고 이름 스텁을 풀 헤드에 배치):
  캐릭터 선택 화면 진입 불가(행).
- `c2` (`--no-name-stub`, 문자열만 교체): 정상 진입, 셀 코드가 스톡 폰트로
  보임 = 문자열 교체 자체는 무해. → 스텁이 범인으로 확정.
- `c3` (스텁을 풀 **꼬리**로 이동, `name_stub=0x801FE1D8`): 행은 사라졌으나
  이름이 여전히 스톡 폰트 `ACEG`. 즉 템플릿 패치가 전혀 안 걸림 = 워크 실패.

### 5.2 정적 검증으로 좁힌 결과 (c3 빌드 이미지 기준)
GDB 없이 빌드 산출물만으로 전부 확인했고, **모두 정상**이었다:
- 훅 2곳 `0x8003294C` / `0x80032BB4` 모두 `jal 0x801FE1D8` ✔
  (이름 문자열 포인터 테이블 `0x80080F18`을 읽는 코드는 EXE 전체에서
  이 두 곳뿐 — `imm 0x0F18` 전수 스캔으로 확인. `0x8001F31C`는
  `0x800A0F18`을 만드는 무관한 우연 일치.)
- 스텁 상수: `exe_table=0x801FA290`, `count=25`, 스트라이드 12 ✔
- 테이블 안에 이름 6개가 인덱스 19..24로 존재 (`0x801FA374`..`0x801FA3B0`) ✔
- 워크 루프는 인덱스 0..24를 실제로 읽음 (읽고 나서 증가, `bnez`가
  `$t2==1`에서 탈출) ✔
- 업로드/패치/그리기/복원 경로 전부 정상 디스어셈블
  (복원은 `0x801FA050`→`0x800837A4`, 144워드) ✔
- EXE 텍스트 크기 `0x95800`(끝 `0x800A5800`)이 풀 이미지 끝
  `0x800A5458`을 덮음 ✔

### 5.3 원인: 0x801FA000~0x801FB000 대역
정적으로 완벽한데 런타임에 매칭이 실패한다 → 테이블 내용이 런타임에
훼손된다는 뜻. 그 테이블(`0x801FA290`)과 템플릿 백업(`0x801FA050`)은
**c1에서 새로 내려간 4 KB 안에** 들어 있고, 이 대역은 JP 덤프가 0으로
검증한 `0x801FB000..0x801FF000` **밖**이다. c1의 행(스텁 코드가 같은
대역에 있었음)과 c3의 매칭 실패가 하나의 원인으로 설명된다.

보조 근거: USA EXE 전체에서 `lui rX,0x801F`는 **0건**이므로 게임 코드가
정적으로 그 대역을 가리키지는 않는다. 즉 훼손은 스택 또는 런타임 계산
포인터(오버레이/힙) 쪽이며, 정적 스캔으로는 안전을 증명할 수 없다.

### 5.4 조치 (`c4`)
`POOL_BASE`를 검증된 `0x801FB000`으로 되돌리고, 이름 글리프 때문에 모자란
1 KB는 **스택 여유에서** 빌렸다: `POOL_LIMIT 0x801FF000 → 0x801FF400`.
풀은 `0x801FB000..0x801FF3D8`(17368 B), 스택 top `0x801FFFF0`까지 약
3.1 KB가 남는다.

풀 구성 실측 (왜 16 KB에 안 들어가는지):
| 구간 | 크기 |
| --- | --- |
| 렉트/폭 백업/last_token | 80 B |
| 템플릿 백업 (엔트리 3..38) | 576 B |
| exe_table (25×12) | 300 B |
| 글리프 엔트리 (180×8) | 1440 B |
| 글리프 픽셀 (106개 × 128 B) | 13568 B |
| 파일 테이블 + 오프셋 배열 | 892 B |
| 이름 스텁 코드 | 512 B |
| **합계** | **17368 B** |

여유가 더 필요해지면 회수 가능한 곳(측정 완료):
- 템플릿 백업은 실제로 패치되는 엔트리가 **13..37**뿐 → 36개에서 25개로

- b6 이후 안 쓰는 `CLUT_RECT` 8 B
- 케이브 잔여 237 B (스텁 512 B를 통째로 옮기기에는 부족)

**런타임 확인 대기 중**: 캐릭터 선택 이름 6개가 한글로 뜨는지, 그리고

## 6. c4 실패와 계측 전환 (2026-08-03)

### 6.1 c4는 스택을 침범했다
`POOL_LIMIT`을 `0x801FF400`으로 올린 c4는 캐릭터 선택 화면이 거대한
빨강/주황 그라디언트 사각형 하나로 뭉개졌다. 스텁이 `0x801FF1D8`,
즉 스택 영역 안에 놓였기 때문이다.

JP RAM 덤프(`work/analysis/ram_gallery.bin`)를 4 KB 페이지 단위로 세어
확인:

| 구간 | 비영(非零) 바이트 |
| --- | --- |
| `0x801E0000`..`0x801FF000` (31페이지) | **전부 0** |
| `0x801FF000`..`0x80200000` | 1201 / 4096 |

즉 **스택은 `0x801FF000` 페이지 안까지 내려온다**. `POOL_LIMIT
0x801FF000`은 우연이 아니라 정확한 경계였고, c4는 그 선을 넘은 것이다.
→ `POOL_LIMIT`은 다시 `0x801FF000`으로 고정.

### 6.2 5.3의 대역 가설은 근거가 약해졌다
같은 덤프에서 `0x801FA000` 페이지도 **완전히 0**이다. 5.3에서 c1/c3의
증상을 "0x801FA000 대역이 안 비어 있다"로 설명했는데, 적어도 JP 기준으로는
그 대역도 비어 있다(단 JP 덤프이므로 USA 근거로 인용 불가 —
`bushido-usa-ram-dumps-are-jp` 메모 참조). c3 실패의 진짜 원인은 여전히
미확정이다.

### 6.3 그래서 계측으로 전환 (c6)
정적으로는 훅·테이블·스텁 상수·워크 루프·업로드/패치/복원 경로가 전부
정상이라 더 좁힐 수 없다. JP 트랙에서 통했던 **디버그 슬롯** 방식으로
런타임 사실을 직접 읽는다.

풀에 16바이트 디버그 블록을 추가하고 이름 스텁을 계측했다
(`build/usa_c6`, 슬롯 `0x801FA04C`):

| 오프셋 | 내용 |
| --- | --- |
| +0 | 스텁 진입 횟수 |
| +4 | 마지막으로 받은 `$a0` (이름 문자열 포인터여야 함) |
| +8 | 테이블 매칭 성공 횟수 |
| +12 | 테이블 첫 워드 (부팅 복사가 실제로 됐는지 증명) |

판정 기준:
- `+0 == 0` → 훅이 실행되지 않음. 이름은 다른 경로로 그려진다
  → 렌더러 `0x80036EF4` 진입점 트램폴린으로 전환.
- `+12`가 EXE 토큰 주소가 아님 → 부팅 복사 실패/훼손 → 풀 배치 문제.
- `+0 > 0`, `+12` 정상, `+8 == 0` → 워크만 실패.
  `+4`를 보면 실제로 어떤 키가 오는지 알 수 있다.

### 6.4 c5 = 이름 제외 완전본 (지금 쓸 수 있는 빌드)
`--no-names` 플래그를 추가해 이름판을 영문으로 두면 풀이 15320 B로
검증 대역 안에 여유 있게 들어간다. `build/usa_c5` = 자막(파일 167 +
EXE 19) + 배드엔딩 이미지 6장(재수정본) + 갤러리 상시 해제, 이름만 영문.
이름 문제가 풀릴 때까지의 기준 산출물.

## 7. c6 계측 결과와 2bpp 글리프 (2026-08-03)

### 7.1 계측이 원인을 확정했다
`build/usa_c6`(디버그 슬롯 `0x801FA04C`)로 캐릭터 선택 화면에서 RAM 덤프
(`work/analysis/ram_usa_c6_select.bin`)를 받아 읽은 결과:

| 슬롯 | 값 | 해석 |
| --- | --- | --- |
| +4 마지막 `$a0` | `0x80010EFC` | **스텁은 실행되고 키도 정확** |
| +12 테이블 첫 워드 | `0x33334444` | **테이블이 쓰레기** (글리프 픽셀 패턴) |
| +0/+8 카운터 | 거대한 난수 | 슬롯 자체가 덮인 자리에 있었음 |

빌드 이미지와 덤프를 256 B 블록 단위로 대조하니 훼손 범위가 정확히
나왔다: **`0x801FA000..0x801FAE00` (3584 B)만 덮였고 그 위는 전부 일치**.

즉 5.3의 진단이 맞았다 — `0x801FA000` 대역은 USA 캐릭터 선택 화면에서
게임이 실제로 쓴다. 6.2에서 JP 갤러리 덤프를 근거로 이 진단을 의심했던
것이 틀렸다(그 덤프는 다른 화면이라 이 대역 사용을 보여주지 못했다).

같은 덤프로 상한도 확정: 우리 풀 위 `0x801FE3E8..0x801FF000`은 비영
0바이트, 스택 최저점은 `0x801FF918`. **안전 창 = `0x801FB000..0x801FF000`
(16384 B)**, 5장의 결론 그대로다.

### 7.2 그래서 진짜 문제는 공간이었다
이름 글리프를 넣으면 풀이 17368 B로 16384 B를 984 B 초과한다. c1~c4는
전부 이 984 B를 어디선가 빌리려다 실패한 시도였다(아래로 4 KB → 게임
영역 침범, 위로 1 KB → 스택 침범).

### 7.3 해결: 글리프를 2bpp로 저장
폰트를 안티앨리어싱 없이 렌더하므로(`fill=6, stroke_width=1,
stroke_fill=1`) 글리프 픽셀이 **세 값만** 쓴다 — c6의 106개 글리프 전수
집계 `{0: 13153, 1: 8173, 6: 5810}`. 픽셀당 2비트면 **무손실**이다.

- 저장: 글리프당 128 B → **64 B** (106개 × 64 B = **6784 B 절감**)
- 복원: 512 B LUT(`packed byte(4픽셀) → 4bpp 하프워드 2바이트`) +
  128 B 스크래치 + 공유 업로더 스텁 `up_stub`
- `up_stub($a0=packed, $a1=slot)`: 64바이트를 LUT로 펼쳐 스크래치에 쓰고,
  scratch rect.x를 `960 + slot*4`로 맞춘 뒤 `j LoadImage`로 **꼬리 점프**
  (LoadImage가 호출자에게 바로 리턴)
- 워퍼(EXE 레코드)와 이름 스텁의 업로드 루프를 둘 다 이 스텁 호출로 교체
  — 케이브 코드도 같이 줄었다

검증: 빌드된 2bpp 블롭을 LUT로 되돌려 c6의 4bpp 블롭과 대조 →
**106개 전부 바이트 단위로 일치**.

### 7.4 c7 = 통합본

6장 + 갤러리 상시 해제.

## 8. c7도 동일 증상 — 범인은 "매칭 이후 경로" (2026-08-03)

### 8.1 c4 = c7, 그러므로 스택도 대역도 아니었다
2bpp로 풀을 11368 B까지 줄여 안전 창 안에 5016 B 여유를 두고 넣은 c7이
**c4와 똑같이** 캐릭터 선택 화면을 거대한 그라디언트 사각형으로 만들었다.
6.1에서 c4의 원인으로 지목한 "스텁이 스택에 깔림"은 틀렸다.

c 계열을 증상으로 정리하면 갈리는 축이 하나뿐이다:

| 빌드 | 이름 테이블 매칭 | 결과 |
| --- | --- | --- |
| c3 | 실패(테이블 훼손) → fail-safe | 화면 정상, 이름만 스톡 `ACEG` |
| c4 | **성공** | 초상화 자리가 그라디언트 사각형 |
| c7 | **성공** | 동일 |

즉 버그는 `nm_found` 이후 경로 — **글리프 업로드와 템플릿 패치** —
안에 있다. 이 경로는 c4 이전까지 한 번도 실행된 적이 없었다.

### 8.2 VRAM은 무죄
캐릭터 선택 화면 VRAM 덤프(`work/analysis/vram_usa_select.png`)에서
업로드 대상 밴드 `(960,112) 64x16`은 **0/1024 비검정** = 완전히 비어 있다.
초상화 텍스처를 덮어쓰는 것이 아니다.

### 8.3 A/B 두 빌드로 반을 가른다
업로드와 패치는 정적으로 구분이 안 되므로(둘 다 워퍼의 검증된 코드와
동일한 로직) 스텁에 스킵 점프를 넣는 스위치를 만들었다
(`--name-no-upload`, `--name-no-patch`).

| 빌드 | 하는 일 | 확인된 삽입 |
| --- | --- | --- |
| `build/usa_c8` | 템플릿 패치만 (업로드 없음) | `nm_found` 뒤 `j nm_patch` |
| `build/usa_c9` | 업로드만 (패치 없음) | `nm_patch`에 `j nm_draw` |

판정:
- c8 정상 / c9 깨짐 → **업로드(LoadImage 호출)**가 범인
- c8 깨짐 / c9 정상 → **템플릿 패치**가 범인
- 둘 다 깨짐 → 공유 구간(`nm_found`의 레지스터 사용) 문제
- 둘 다 정상 → 둘의 조합/순서 문제

두 빌드는 진단용이라 O15 이미지 재삽입은 하지 않았다.

## 9. A/B 결과와 DMA 직렬화 (2026-08-03)

### 9.1 결과: c8 정상 / c9 깨짐 → 업로드가 범인
템플릿 패치만 하는 c8은 화면이 멀쩡했고, 업로드만 하는 c9은 깨졌다.
**`LoadImage` 호출 자체가 원인**이고 템플릿 패치는 무죄다.

### 9.2 왜 워퍼는 멀쩡한가
PSY-Q `LoadImage`는 **비동기**다 — DMA를 걸어놓고 바로 리턴한다.
정상 사용법은 앞뒤로 `DrawSync(0)`를 넣는 것.

- 자막 워퍼: `last_token` 가드가 있어 **새 줄이 뜰 때만** 업로드한다
  (수백 프레임에 한 번). 게임의 DMA와 겹칠 확률이 사실상 0.
- 이름 스텁: 가드가 없어 **매 프레임** 업로드한다. 캐릭터 선택 화면이
  이미 돌리고 있는 DMA 체인에 끼어들어 체인이 망가지고, 그 결과가
  초상화 자리의 거대한 쓰레기 사각형이다.

VRAM 밴드가 무죄(8.2)인 것과도 모순되지 않는다 — 문제는 전송 대상이
아니라 전송 시점이었다.

### 9.3 조치: 전송을 DMA 유휴 구간으로 묶는다 (`up_stub`)
`up_stub`의 전송을 DMA 채널 2 busy 비트(`D2_CHCR 0x1F8010A8` bit 24)
대기로 앞뒤에서 감쌌다. `j LoadImage` 꼬리 점프는 `jal` + 복귀로 바꿨다
(뒤쪽 대기를 넣어야 하므로).

- 대기 루프는 **상한(0x100000회)** 이 있어, 비트가 안 풀려도 행이 아니라
  글리프 한 장 누락으로 degrade한다
- 자막 경로도 같은 스텁을 쓰므로 동일하게 직렬화된다(단순 직렬화라
  기존 동작을 해치지 않는다)
- `UP_STUB_SIZE` 0x80 → 0x100

## 10. 이름판이 쓰는 것은 폰트 0이 아니라 폰트 1 (2026-08-04)

### 10.1 d1: 깨짐은 사라졌고 글자만 남았다
9.3의 DMA 직렬화로 캐릭터 선택 화면이 정상 복귀했다(초상화·썸네일 모두
정상). 남은 증상은 이름이 스톡 폰트 `ACE`(= 타츠미 3셀)로 나오는 것,
즉 **템플릿 패치가 이 렌더러에 안 먹는다**는 것.

### 10.2 렌더러를 읽어보니 인덱스에 폰트 베이스가 더해진다
per-char 드로어 `0x8003727C`가 글리프를 찾는 식:

```
idx   = charindex + [gp+0x7c]          ; charindex('A') = 0x41 - 0x34 = 13
템플릿 = 0x80083774 + idx*16            ; UV/CLUT/tpage 16B를 프리미티브로 복사
advance= 0x80083D74 + idx*2
w / h  = 0x80083E34 / 0x80083EF4 + idx*2
```

그리고 `#F` 제어코드의 핸들러 `0x800371D8`:

```
arg = 다음 가변인자
if (arg == 1)  [gp+0x7c] = 0x39     ; 57
else           [gp+0x7c] = 0
```

이름 문자열은 `#X#Y#F`로 시작하고 `#X`/`#Y`/`#F`가 각각 가변인자를 하나씩
소비한다($a1=x, $a2=y, $a3=1). **두 호출부 모두 $a3=1을 넘기므로 이름판은
폰트 1**이고, 실제로 읽히는 것은 엔트리 `13+57=70` .. `37+57=94`다.
c1~d1은 내내 13..37을 패치하고 있었다.

폰트 0/1 스톡 값 비교 (모두 adv 14 / w 15 / h 15):

| | 'A' 템플릿 16B | CLUT | tpage |
| --- | --- | --- | --- |
| 폰트 0 (13) | `8080802c d8003878 e7003e00 d80fe70f` | 0x7838 | 0x3E |
| 폰트 1 (70) | `8080802c 00e0bf2b 0fe03b00 00ef0fef` | **0x2BBF** | 0x3B |

CLUT까지 다르므로 `+6`도 우리 글리프용 `0x7838`로 써야 한다(기존 스텁은
`+6`을 아예 건드리지 않았다).

### 10.3 조치 (`d2`)
이름 스텁을 폰트 1로 재조준했다:

- 패치 베이스 `USA_TEMPLATE + 57*16 = 0x80083B04` (기존 `0x80083774`)
- `+6`에 `STOCK_TEMPLATE_CLUT 0x7838` 기록 추가
- advance 테이블 `0x80083D74 + 70*2 = 0x80083E00`부터 25개를 16으로 패치
  (스톡 14로는 16px 한글이 겹친다)
- 복원도 폰트 1 범위로: 템플릿 `0x80083BD4`부터 100워드, advance
  `0x80083E00`부터 25하프워드. 풀에 전용 백업 2개 추가
  (`name_tmpl_backup` 400 B, `name_adv_backup` 50 B)
- `NAME_STUB_SIZE` 0x200 → 0x280

패치 상한 확인: charindex 37 → `0x80083B04 + 592 + 16 = 0x80083D64`
≤ 템플릿 끝 `0x80083D74` ✔ (딱 들어간다)

## 11. CLUT — 폰트 1 것을 그대로 쓴다 (2026-08-04)

### 11.1 d2 결과: 한글은 나오고 색만 틀렸다
10.3의 폰트 1 재조준으로 이름이 한글(`호타루비`)로 렌더됐다. 남은 증상은
**청록색 배경 상자**와 흰색이 아닌 글자색.

### 11.2 원인: 0x7838은 이 화면에서 폰트 CLUT가 아니다
캐릭터 선택 화면 VRAM에서 두 CLUT를 직접 읽었다:

| CLUT | VRAM | 내용 |
| --- | --- | --- |
| `0x7838` (d2가 기록) | (896,480) | 0:청록(0,230,239) 1:보라 2:연두 ... **무관한 데이터** |
| `0x2BBF` (폰트 1 스톡) | (1008,174) | 0:투명 1:검정 2~5:회색 **6:흰색** |

`0x7838`은 자막 컨텍스트에서 검증한 값이고, 캐릭터 선택 화면에서는 그
자리에 다른 것이 올라와 있다. 인덱스 0이 청록이라 글리프의 투명 픽셀이
전부 청록으로 칠해진 것이 배경 상자의 정체다.

폰트 1의 CLUT는 우리 글리프가 렌더되는 팔레트({0,1,6} = 투명/검정 외곽선/
흰색 속)와 **정확히 일치**한다. 애초에 건드릴 필요가 없었다.

### 11.3 조치 (`d3`)
템플릿 `+6`에 쓰는 값을 `STOCK_TEMPLATE_CLUT 0x7838` → **`NAME_CLUT
0x2BBF`**로 변경. 그 외 d2와 동일.

교훈: CLUT 코드는 컨텍스트마다 다른 VRAM을 가리킬 수 있으므로, **그
컨텍스트의 스톡 프리미티브가 쓰던 값을 그대로 유지**하는 것이 안전하다.
