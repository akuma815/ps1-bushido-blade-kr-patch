## 캡처 도구

`workspace/scripts/capture_duckstation_ram.py`는 DuckStation GDB 서버에
연결한다. 이 서버는 클라이언트 연결 시 게임을 자동 정지하므로 별도 Ctrl-C를
보내지 않고, 2MB RAM을 읽은 다음 `$c#63`으로 즉시 재개한다.

DuckStation 공식 GDB 서버 구현에서 지원하는 메모리 읽기 명령과 자동 정지/재개
동작을 기준으로 작성했다.

## 다음 캡처

게임에서 타츠미 스토리 모드를 진행해 음성 대사가 재생되는 순간 사용자가
알려주면 같은 도구로 RAM을 캡처한다. 비교 대상은 다음과 같다.

1. 새 `pBAV` 헤더와 VAB 속성 테이블
2. 기준 캡처에 없던 대용량 ADPCM 데이터
3. `SE4/TAT3WIN.00`의 원본 ADPCM 접두부
4. 뱅크 본문을 가리키는 RAM 포인터 후보

전체 파일명 문자열은 정적 디스크 검색에서 0건이었으므로 런타임에서도 필수
조건으로 사용하지 않는다. 가장 강한 식별자는 알려진 VAG ADPCM 바이트다.

캡처 후에는 발견된 RAM 범위에 읽기/실행 중단점을 걸어 상위 음성 재생 함수를
거슬러 올라간다.

- `work/analysis/ram_tatsumi_voice_01.bin`
- `work/analysis/ram_tatsumi_voice_01.json`
- RAM SHA-256:
  `E9572AEC3ED260A48DD0A94A85662B6E805D931ED7BD7B550AAED45CDB39A65B`

결과:

- `pBAV @ 0x80135CD4`: `SE0/START.` 헤더와 대응
- `pBAV @ 0x801368F4`: `SE2/SUZUKA.` 헤더와 대응
- 두 주소 간격: `0xC20`, 프로그램 1개짜리 VH 헤더 크기와 동일

## 자동 VAB 적재 중단점

`workspace/scripts/wait_duckstation_vab_write.py`를 추가했다. 현재 다음 두 VAB
헤더 슬롯의 첫 워드에 쓰기 중단점을 걸고 백그라운드에서 대기 중이다.

- `0x80135CD4`
- `0x801368F4`

다음 적재가 발생하면 에뮬레이터를 자동 정지해 PC, CPU 레지스터, 주변 명령어와
VAB 슬롯을 `work/analysis/vab_write_break_01.json`에 저장한 뒤 중단점을
해제하고 게임을 재개한다.

## 자동 중단점 결과

첫 중단점은 41.536초 뒤 발동했다.

- 정지 응답: `S05`
- 정지 PC: `0x8003EE90`
- 실제 직전 저장 명령: `0x8003EE8C: sw v0, 0(a1)`
- `v0`: `0x56414270`, little-endian 바이트로 `pBAV`
- 복사 목적지 `a1`: `0x80135CD4`
- transient 입력 버퍼 `a3`: `0x8014C000`
- `pBAV` 원본 위치: `0x8014C020`

`0x8003EE3C`부터의 함수는 입력 파일의 오프셋 테이블을 읽어 여러 구간을 지정된
RAM 목적지로 복사하고 후속 주소를 보정한다. VAB 전용 재생 함수라기보다 복합
음성 파일의 공통 적재/재배치 함수다.

첫 보고서는 입력 버퍼를 보존하지 않아 적재 파일을 식별하지 못했다. 두 번째
중단점에서는 `0x8014C000`부터 128KB를 정지 중에 추가 캡처했다.

- `work/analysis/vab_write_break_02.json`
- `work/analysis/vab_write_break_02.source.bin`
- 버퍼 내 `pBAV`: `0x8014C020`, `0x8014D040`, `0x8014DC60`
- 디스크 대조: 첫 128KB가 `SE0/KTKT.`와 100% 일치

따라서 이번 자동 중단점은 다음 스토리 대사가 아니라 전투 진입에 사용되는
`SE0/KTKT.` 음성/효과음 묶음을 잡았다. 공통 적재 함수와 입력 버퍼 위치는
확정했지만 `SE4/TAT3WIN.*` 재생 호출은 아직 잡지 못했다.

다음 시도는 캐릭터 선택에서 타츠미를 결정하기 직전에 중단점을 설치하고, 스토리
첫 장면으로 들어갈 때 발생하는 최초 적재를 잡는다. 부팅 전부터 설치하면
`START.`/`SUZUKA.`가 먼저 걸리므로 캐릭터 결정 직전 상태가 필요하다.

## 캐릭터 결정 시 3차 중단 결과

타츠미를 선택한 순간 쓰기 중단점은 발동했지만, 이 적재 경로에서는 앞선 전투 진입
경로와 달리 `a3`가 transient 입력 버퍼가 아니었다. 구형 캡처기는 `a3 =
0xFF000000`을 읽으려다 `E00`으로 중단되어 `vab_write_break_03.json`을 남기지
못했다. `finally` 처리로 중단점은 제거되고 게임은 자동 재개되었다.

`wait_duckstation_vab_write.py`는 다음과 같이 수정했다.

- 특정 소스 레지스터를 가정하지 않고 모든 레지스터의 PS1 2 MiB RAM 별칭을 수집
- 선택적 메모리 읽기 전에 PC와 전체 레지스터 보고서를 먼저 저장
- 각 포인터 주변 16 KiB와 모든 `pBAV` 위치를 개별 보존
- 한 포인터 읽기가 실패해도 나머지 캡처와 목적지 슬롯 캡처를 계속 수행
- `pBAV`가 확인된 포인터 페이지를 transient source 후보로 선택

따라서 다음 타츠미 재선택에서는 소스 레지스터 배치가 달라도 최소한 호출 PC,
레지스터, 유효 RAM 후보와 실패 원인이 보고서에 남는다.

## 4차 캡처 해석 정정

타츠미 재선택 직후의 4차 캡처는 정상 저장되었다.

- 보고서: `work/analysis/vab_write_break_04.json`
- 정지 PC: `0xBFC02214` (PS1 BIOS 예외/이벤트 처리 구간)
- 게임 코드 후보: `k0 = 0x800709AC`, `ra = 0x80043224`
- `0x80135CD4`: `SE0/START.`와 헤더 일치
- `0x801368F4`: `SE2/SUZUKA.`와 헤더 일치
- `TAT3WIN.*`와 일치하는 VAB 헤더/입력 버퍼: 없음

사용자 플레이 확인에 따르면 타츠미 선택 직후 재생되는 음성은 타츠미 개인 대사가
아니라 스토리 모드 공통 오프닝 멘트로 보인다. 따라서 캐릭터 선택 시점을
`TAT3WIN.*` 호출 시점으로 간주한 앞선 가정은 기각한다. 공통 오프닝이 STR/XA
스트림 음성이라면 VAB 슬롯에 타츠미 뱅크가 나타나지 않는 현상과도 일치하지만,
스트림 형식은 아직 런타임으로 확정하지 않았다.

다음 추적 지점은 공통 오프닝 종료 후 최초의 캐릭터별 전투/승리 음성 직전이다.
오프닝 음성과 캐릭터별 VAB 자막 경로는 별도 대상으로 취급한다.

## 타츠미 첫 개인 대사 5차 캡처

공통 오프닝 종료 후 타츠미 첫 개인 대사 직전에 중단점을 다시 설치했다. 설치 후
3.387초 만에 발동했으며 이번에는 transient 입력 파일을 완전히 식별했다.

- 보고서: `work/analysis/vab_write_break_05.json`
- transient 버퍼: `work/analysis/vab_write_break_05.source.bin`
- 정지 PC: `0x8003F170`
- 입력 버퍼: `0x8014C000`, `pBAV @ 0x8014C008`
- 목적지 슬롯: `0x80135CD4`
- 디스크 대조: `SE4/TAT3WIN.02` 전체 19,144바이트와 100% 일치
- 캡처 오류: 없음

상위 함수 `0x80045544`는 입력 버퍼 `0x8014C000`과 목적지 슬롯
`0x80135CD4`를 작업 구조체에 넣고 `0x8003EA00` 및 `0x8003ED90`을 호출한다.
따라서 이 함수는 타츠미 이벤트 02의 VAB 적재 경로로 런타임 확인되었다.

`TAT3WIN.02`에는 다음 두 자막 후보가 있다.

- `voice/se4/tat3win/02/p00/t00/v01` (추정 765 ms)
- `voice/se4/tat3win/02/p00/t01/v02` (추정 1,088 ms)

뱅크와 장면의 대응은 확정했다. 다음 PoC 경계는 실제 재생 호출에서 tone/VAG
인덱스를 구분하고, 해당 호출 시작/종료에 자막 표시/지우기 이벤트를 연결하는 것이다.

### tone 실행 중단 1차 시도

정적 코드에서는 `0x80045C14`가 사운드 ID `0x7B`, `0x80045CA4`가 `0x7C`를
`0x8003E798`에 전달한다. 두 주소를 tone 후보로 실행 중단했지만 다음 사용자 음성
완료 시 저장된 PC는 목표가 아닌 `0x800709F8`이었다. 이 결과는 tone 확인으로
사용하지 않는다. 다음 대사가 다른 이벤트였거나 DuckStation 일시정지 신호가 GDB
정지로 전달되었을 수 있다.

`wait_duckstation_execute.py`는 목표 주소가 아닌 정지를 `unexpected_stops`에
기록하고 자동 재개한 뒤 실제 목표 PC가 나올 때까지 계속 기다리도록 수정했다.
다음 시도는 개별 호출 위치보다 공통 음성 요청 함수 `0x8003E798` 진입을 직접
포착한다.

### 공통 음성 요청 함수 런타임 확인

`0x8003E798` 실행 중단은 즉시 발동했지만 첫 요청은 `a0 = 0x79`, 복귀 주소
`0x8005CFB4`인 효과음이었다. 따라서 실행 캡처기에 `a0` 필터를 추가하고
`0x7B`, `0x7C`만 허용했다.

필터 적용 후 다음 타츠미 대사 준비 상태에서 실제 목표 호출을 잡았다.

- 보고서: `work/analysis/tatsumi_tone_break_03.json`
- 정지 PC: `0x8003E798`
- 대기 시간: 12.124초
- 사운드 ID (`a0`): `0x7C`
- 좌/우 음량 인수: `a1 = 0x3F`, `a2 = 0x3B`
- 음성 슬롯 인수: `a3 = 0x14`
- 복귀 주소: `0x80045A9C`
- 자동 제외된 요청: `0x7A`, `0x79`, `0x7D`, `0x7E`
- 목표와 무관한 정지 두 건도 자동 재개됨

따라서 이 장면의 다음 타츠미 대사는 공통 요청 함수 `0x8003E798`에 사운드 ID
`0x7C`로 전달되는 것이 런타임 확인되었다. `TAT3WIN.02`의 래퍼 작업 구조체에는
기준 사운드 ID `0x7A`가 들어 있고 뱅크에는 VAG 두 개가 있으므로 `0x7C`는 두
번째 후보 `voice/se4/tat3win/02/p00/t01/v02`에 대응하는 것으로 판정한다.

한 줄 자막 PoC의 시작 이벤트는 `PC = 0x8003E798 && a0 = 0x7C`로 제한한다.
전체 자막 구현에서는 뱅크/장면 상태도 함께 검사해 다른 장면의 동일 사운드 ID와
충돌하지 않도록 해야 한다.

### 이벤트 판정 정정

실제 자막 PoC에서 `0x7C` 조건은 대사 위치가 아니라 대전 중에 발동했다. 위의
“다음 타츠미 대사” 판정은 잘못된 분류이며 폐기한다. `0x80045A9C` 호출 문맥은
전투 처리 경로이고 사운드 ID가 대사 고유 키가 아니었다.

실제 대사 직전 무필터 재캡처 `tatsumi_dialogue_break_01.json`은 자동 진행 직후
`a0=0x79`, `RA=0x8005CFB4`를 잡았지만, 이 조합 역시 앞서 효과음으로 제외했던
동일 경로다. 첫 호출 정지 방식은 대사 직전의 효과음을 반복해서 포착하므로 더
사용하지 않는다. 다음 캡처는 `trace_duckstation_sound_calls.py`로 여러 사운드
진입점을 짧은 시간 연속 기록하고 대사 전후 호출 묶음을 비교한다.

## 스토리 VAB 사운드 테이블 정적 해석 (2026-08-01)

번역 완료 후 기존 RAM 캡처의 사운드 큐 소비 경로를 다시 해석했다. 타입 3 로더의
완료 디스패치 `0x8003F908`은 `0x80071D1C`에 라이브러리 VAB 슬롯 `7`을 넘긴다.
사운드 큐 소비 함수 `0x8003F60C`는 `0x800A2F50`이 가리키는 2바이트 테이블에서
사운드 ID별 `(VAB 슬롯, tone)`을 얻어 `0x80070B9C`에 전달한다.

캡처 당시 테이블 `0x80088630`에서 스토리 슬롯 7은 다음과 대응한다.

| 사운드 ID | VAB 슬롯 | tone |
|---:|---:|---:|
| `0x6C` | 7 | 0 |
| `0x6D` | 7 | 1 |
| `0x6E` | 7 | 2 |
| `0x6F` | 7 | 3 |
| `0x70` | 7 | 4 |

기존 시험의 `0x7C`는 슬롯 9/tone 3이다. 따라서 대전 중 자막이 잘못 나타난 현상은
테이블과 일치하며, `0x7C` 대사 가설은 정적으로도 기각된다. 기계 판독 근거는
`work/analysis/story_sound_table_mapping.json`에 기록했다.

다음 시험본은 `TAT3WIN.02`의 tone 0, 자막 `처음으로…`에 대응하는 후보
`0x6C`를 사용한다. 이 빌드는 정적 검증만 통과했으며 실제 대사 시점 일치는
DuckStation에서 확인해야 한다. 프로그램 1을 가진 `HOT4WIN.03`의 선택 경로는
별도 미해결 항목으로 유지한다.

### `0x6C` 이벤트 PoC v1 실패와 훅 범위 수정

첫 `0x6C` 시험본에서는 첫 전투 뒤 대사에도 자막이 나오지 않았다. 원인은 사운드
ID 후보가 아니라 훅 범위였다. 빌더가 공통 함수 `0x8003E798`을 감싼 것이 아니라
전투 코드의 단일 호출 지점 `0x80045A94`만 교체하고 있었다. 따라서 스토리 대사는
조건 검사 자체를 통과하지 않았다.

v2에서는 공통 함수 진입점 `0x8003E798`의 첫 두 명령을 8바이트 점프로 교체했다.
래퍼는 `a0 == 0x6C`를 검사한 뒤 덮은 다음 명령을 그대로 재실행하고
`0x8003E7A0`으로 복귀한다.

```text
sll  v0,a3,1
addu v0,v0,a3
```

- 목표 자막: `처음으로…`
- 표시 시간: 46프레임

  `7BC3114D553A744406F59B83188D044D7E5339E8573189869373C738F16B3701`

### 글로벌 대기 함수 v4 실패와 실제 OT 연결 v5

사용자는 v4에서도 자막이 보이지 않았다고 확인했다. `0x80070838`은 호출 형태와
본문을 다시 검토한 결과 실제 프레임 제출 함수가 아니라 `VSync/DrawSync` 계열
대기 함수로 보는 것이 타당하다. 이 지점에서 전투용 고정 OT 포인터
`0x800A3010`에 프리미티브를 추가해도 전투 후 장면의 OT에는 연결되지 않는다.

v5는 공통 `AddPrim` 함수 `0x8006A368`을 감싼다. 자막 활성 중 전역 프레임
카운터 `0x800A2F3C`이 바뀐 첫 호출에서, 게임이 `a0`로 넘긴 실제 장면 OT에
자막 프리미티브를 직접 연결한다. 따라서 전투용 고정 OT 주소를 사용하지 않는다.
원래 `AddPrim`의 첫 두 명령은 래퍼에서 재실행한다.

20px 자막은 이 문장에서 더블 버퍼 프리미티브 2,048바이트가 필요해 런타임으로
0이 검증된 1,952바이트 범위를 96바이트 초과했다. v5는 18px로 낮춰
1,856바이트를 사용하며 빌더에도 상한 검사를 추가했다.

- 빌드: `build/subtitle_event_poc_v5`
- 이벤트: 현재 스토리 VAB 핸들 7, tone 0
- 렌더 훅: 실제 OT를 받는 `AddPrim 0x8006A368`
- BIN SHA-256:
  `D1B59F45CAE384CC039391613F61C39C273CD4E3F932419ADDF7DB84B9F35DF8`
- 정적 상태: expected-write, Mode2 EDC/ECC, 디스크 크기, EXE 왕복 검증 통과
- 런타임 상태: 사용자 재검증 대기

### Key On v3 실패와 자동 이중 추적 전환

사용자는 v3에서도 첫 전투 후 자막이 나오지 않았다고 확인했다. 이 결과로
`TAT3WIN.02 tone 0`이 `0x80070B9C`에 현재 슬롯 7 핸들로 들어온다는 가정도
기각한다. 추가 표시 빌드는 중단했다.

다음 조사는 원본 일본판에서 두 지점을 동시에 자동 기록한다.

- `0x80070B9C`: 게임의 VAB Key On 래퍼
- `0x8007234C`: 더 낮은 최종 SPU Key On 경로

추적기는 각 호출의 `a0-a3`, `ra`, 현재 슬롯 7 VAB 핸들과의 일치 여부를 기록하며,
사용자는 평소처럼 첫 전투 후 대사까지 진행한 뒤 완료만 알리면 된다. 중간 타이밍
조작은 필요 없다. 결과 파일은 `work/analysis/story_keyon_trace.json`이다.

### 자동 이중 추적 결과와 글로벌 렌더 훅 v4

자동 추적은 정상 종료됐고 142개 호출을 기록했다. VAB Key On과 최종 SPU Key On은
각각 71회였으며 모든 최종 Key On의 복귀 주소는 `0x80070EF4`였다. 첫 전투 후
스토리 대사는 다음 두 호출로 확정됐다.

| 추적 시각 | `a1` VAB 핸들 | 현재 스토리 핸들 | `a3` tone |
|---:|---:|---:|---:|
| 69.703초 | 7 | 7 | 0 |
| 71.267초 | 7 | 7 | 1 |

따라서 v3의 음성 조건은 정확했다. 자막이 보이지 않은 이유는 프레임 훅
`0x8004322C`가 전투 루프의 특정 호출점이며 전투 후 대사 장면에서는 실행되지
않았기 때문이다.

v4는 공통 프레임 제출 함수 `0x80070838`의 진입점 자체를 감싼다. 원래 첫 두 명령과
원래 `a0` 인수를 복원한 뒤 `0x80070840`으로 이어지므로 36개 호출 지점 전체에서
동작한다.
