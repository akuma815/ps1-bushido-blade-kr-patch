# 자막 렌더 실시간 진단

## 2026-08-01 v5 실패 후 조건부 추적

첫 전투 후 첫 대사 구간을 일본판 원본에서 자동 추적했다.

- Key On 감지: `0x80070B9C`
- 감지 조건: 현재 스토리 VAB 핸들 `7`, tone `0`
- 첫 대사 감지까지 Key On 호출: 59회
- 감지 직후 `AddPrim 0x8006A368` 호출: 145회
- 완전히 수집된 프레임: 3개, 각 프레임 48회
- 프레임 카운터: `0x4C0`, `0x4C1`, `0x4C2`, `0x4C3`
- 실제 OT 범위: `0x8012DBEC`~`0x80134050`
- 증거: `work/analysis/story_addprim_trace_v5_failure.json`

이 결과로 음성 감지 조건과 스토리 장면의 `AddPrim` 실행 여부는 확정됐다.

## 라이브 RAM 렌더 시험

실행 중인 일본판 원본 RAM에 v5의 렌더 훅만 설치하고 타이머를 900프레임으로
강제 설정했다.

- 2초 후 타이머: 900에서 841로 감소
- 마지막 렌더 프레임: `0x920`
- `0x80122000`에 TILE 패킷 생성 확인
- 사용자 화면에서 `처음으로…`가 실제로 표시됨
- 증거: `work/analysis/live_subtitle_render_probe.json`

따라서 TILE 패킷 생성과 `AddPrim` 기반 화면 표시 경로는 동작한다. 다만 라이브
시험 뒤 재기동이 발생했으므로 라이브 RAM 패치는 안정성 판정에 사용하지 않고,
클린 부팅 빌드에서 다시 검증한다.

## v6 실패 원인과 v7 수정

v6 실패 직후 RAM은 타이머, 마지막 렌더 프레임, 자막 패킷이 모두 0이었다.
훅 자체는 RAM에 설치되어 있었으므로 이벤트 조건 래퍼를 역어셈블했다.

`STORY_VAB_HANDLE_RAM = 0x8013EDD8`의 하위 16비트 `0xEDD8`은 `lw`에서
`-0x1228`로 부호 확장된다. 기존 빌더는 상위값을 보정하지 않고 `lui 0x8013`을
사용하여 실제로 `0x8012EDD8`을 읽었다. 이 때문에 `a1 == story VAB handle` 조건이
항상 실패했다.

v7은 다음 두 명령으로 정확한 주소를 읽는다.

```text
lui t0, 0x8014
lw  t0, -0x1228(t0)  # 0x8013EDD8
```

- 빌드: `build/subtitle_event_poc_v7`
- 표시 시간: 180프레임
- BIN SHA-256: `27DCC23B6D89C8E2F91F9CD0C88A1C6E175AB387D3DFE4858B9B7CD95D2EBDCB`
- 정적 검사: 전 항목 통과
- 추가 확인: 패치 EXE 역어셈블에서 위 유효 주소 확인
- 런타임 상태: 검증 대기

## v7 실패 후 상태 저장 위치 변경

v7 실패 직후에도 훅과 보정된 VAB 핸들 주소는 정확했지만 다음 값이 모두 0이었다.

- 타이머: 0
- 마지막 렌더 프레임: 0
- 생성된 자막 패킷: 없음

첫 대사 Key On은 스토리 장면 전환 직전에 발생한다. 기존 상태 주소
`0x80121FF0`은 장면 작업 RAM에 속하므로 Key On 뒤 장면 초기화에서 지워지는
가설이 현재 증거와 일치한다. 라이브 시험은 장면 초기화가 끝난 뒤 타이머를 써서
성공했다.

v8은 타이머와 마지막 렌더 프레임을 실행 파일 내부의 지속 코드 케이브로 옮긴다.

- 타이머: `0x800120C0`
- 마지막 렌더 프레임: `0x800120C4`
- 빌드 시 두 값은 0으로 초기화
- 런타임 자막 패킷: 기존 `0x80122000` 유지
- 코드 케이브 사용량: 2,068/2,076바이트
- BIN SHA-256: `8832A8FEE078F51366C49C8B58111E77A7FC011FE83C961628F27C6E3F6C4A08`
- 런타임 상태: 검증 대기

## v8 부팅 실패와 v9 안전 영역

v8은 타이머를 `0x800120C0`으로 옮기면서 패치 페이로드를 코드 케이브 끝까지
2,068바이트로 확장했다. 클린 부팅에서 PC가 BIOS `0xBFC0D8E0`에 머물러 이
영역은 지속 상태 저장에 안전하지 않다고 판정했다. v8은 사용하지 않는다.

v9은 v7에서도 이미 덮어써 정상 부팅된 996바이트 범위를 유지한다. 80바이트
이벤트 래퍼가 끝나는 `0x80011904`와 렌더 래퍼가 시작되는 `0x80011934` 사이의
48바이트 빈틈에 상태를 배치했다.

- 타이머: `0x80011920`
- 마지막 렌더 프레임: `0x80011924`
- 빌더가 래퍼와의 비중첩을 검사
- 코드 케이브 사용량: 996/2,076바이트
- BIN SHA-256: `ECB13D0C6396B8BD006F3150D2A22002B64FF2BFD7A353CFBFD969DCE56F3199`
- 클린 부팅 확인: 게임 코드 PC `0x800588DC`, 초기 상태 8바이트 모두 0
- 런타임 자막 상태: 검증 대기

## v9 실패와 v10 고정 전역 상태

v9는 정상 부팅했지만 첫 대사 후에도 타이머, 마지막 렌더 프레임, 런타임 패킷이
모두 0이었다. 이벤트 훅과 래퍼 코드는 그대로 유지됐다. 따라서 장면 전환 중
SLPM 실행 파일 구간 자체가 다시 적재되어 래퍼 사이 상태값도 초기화되는 것으로
판정한다.

v10은 실행 파일 범위와 장면 작업 RAM을 모두 피하고, 장기 프레임 전역값 인근의
`0x800A2E90`~`0x800A2E97`을 사용한다. 이 8바이트는 타이틀, 로더, 타츠미 음성,
실패 직후 라이브 RAM에서 모두 0이었으며 해당 하위 즉시값의 직접 코드 참조도
발견되지 않았다.

- 타이머: `0x800A2E90`
- 마지막 렌더 프레임: `0x800A2E94`
- 빌드: `build/subtitle_event_poc_v10`
- BIN SHA-256: `A19B0584AE8A87DF5421974FD547BC688192C29615B395F6B5988B1E34204991`
- 코드 케이브 사용량: 996/2,076바이트

## v10 실패와 v11 영구 이벤트 계수

v10 실패 후 `0x800A2E90` 상태와 런타임 패킷은 모두 0이었다. 이 주소에 진단
표식 `34120000 EFBEADDE`를 쓴 뒤 게임을 2초간 실행해도 값이 그대로 유지됐으며,
원래 0으로 복구했다. 따라서 v10 실패는 상태 영역 초기화가 아니라 이벤트 래퍼가
조건을 설정하지 않은 결과다.

## v12 최초 자동 표시 성공과 남은 문제

v12는 상태를 오디오 VAB 핸들 배열 직전 `0x8013EDA0`으로 옮겼다. 사용자 확인에서
전투 시작 시 상대방 음성이 재생될 때 `처음으로…`가 실제 화면에 나타났다.

확정된 사항:

- Key On 이벤트에서 자동 자막 활성화 성공
- `AddPrim` 기반 TILE 렌더 성공
- 한글 글리프와 검은 배경 표시 성공
- 실시간 강제 설정이 아닌 디스크 빌드의 자동 표시 성공

남은 문제:

1. 목표로 삼은 첫 대사 시점이 아니라 다음 전투 시작 상대 음성 시점에 표시됐다.
2. 첫 `AddPrim` 호출의 깊이 버킷에 연결되어 캐릭터 스프라이트/폴리곤이 자막 위를
   덮었다. 최종 전경 OT 버킷에 연결해야 한다.
3. `0x8013EDA0`은 미사용 패딩이 아니었다. 실패 직후 타이머가 설정값 180이 아닌
   522였으며 진단 바이트도 게임 데이터로 바뀌었다. 이 주소는 폐기한다.

잘못 발동한 시점의 `0x80130000`~`0x8013FFFF`를 보존했다. 첫 `pBAV` 헤더의
VAB 크기는 19,136바이트로 원본 `SE4/TAT3WIN.02`와 정확히 일치했다. 따라서 현재
게임이 실제로 해당 뱅크를 로드한 것은 맞지만, tone 0의 화면 문맥 또는 카탈로그
대사 대응을 다시 확인해야 한다.

- 상태: `work/analysis/v12_wrong_trigger_state.json`
- 오디오 RAM: `work/analysis/v12_wrong_trigger_audio_region.bin`
- VAB 비교: `work/analysis/v12_wrong_trigger_vab_matches.json`
- v12 BIN SHA-256: `BF6CAABE49D1A8DD1C99BA3317C846CEB7C0EE0152441BAB84646039EA1BA27A`

### v12 타이밍 재해석

사용자가 다시 확인한 결과 자막은 상대방 음성 자체에 반응한 것이 아니라 타츠미를
처음 조작할 때 나타났다. 따라서 Key On은 목표 대사에서 발생했지만 해당 구간에는
`AddPrim` 호출이 없어 타이머가 대기했고, 3D 전투 프레임 생성이 시작된 뒤에야
자막 패킷이 처음 연결된 것으로 해석한다. 음성 매핑보다 렌더 훅 시점이 핵심이다.

## v13 공통 OT 제출 및 최종 전경 연결

전투 프레임 루프의 제출 순서를 역어셈블해 `0x80067B54`를 완성된 OT를 받는 공통
`DrawOTag` 경로로 특정했다. v13은 `AddPrim` 진입점 대신 이 함수를 감싼다.

자막 활성 중에는 제출될 OT의 연결 리스트를 끝 태그 `0xFFFFFF`까지 순회한 뒤 그
위치에 자막 TILE 체인을 연결한다. 따라서 모든 장면 프리미티브 뒤에 그려져 캐릭터
그래픽이 자막을 가리지 않아야 한다.

- 렌더 훅: `DrawOTag 0x80067B54`
- 상태 주소: `0x800A2E90` 복귀
- 렌더 래퍼 크기: 420/640바이트
- 코드 케이브 사용량: 996/2,076바이트
- BIN SHA-256: `DF575D617B967F574B9A69B9AF70F426D2DCE4733E260A0E506B7BD6B80C7230`
- 정적 검사: 전 항목 통과
- 클린 부팅 확인: 게임 코드 PC `0x800588A8`, 초기 상태 8바이트 모두 0
