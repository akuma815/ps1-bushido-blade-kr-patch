## 1. 가장 먼저 지켜야 할 규칙

1. `original`은 절대 수정하지 않는다.
2. 일본판 조사에 미국판 주소를 그대로 쓰지 않는다. 두 실행 파일을 비교하되 일본판 대응 위치를 다시 증명한다.
3. 정적 빌드 성공, 해시 일치, EDC/ECC 통과는 런타임 성공이 아니다. DuckStation 실제 화면 결과가 최종 판정이다.
4. 새 RAM 주소를 보고 0 또는 패딩처럼 보인다는 이유로 상태 저장소로 쓰지 않는다.
5. `workspace/config/subtitle_memory_map.json`에 승인되지 않은 영구 상태 영역은 사용하지 않는다. 현재 승인된 사용자 상태 RAM은 **0개**다.
6. `build_official_glyph_poc.py`는 현재 `--scene-frame-direct` 없이는 빌드를 거부한다. 이 안전장치를 우회하지 않는다.
7. 장시간 GDB 다중 브레이크포인트 추적은 화면을 정지시킨 전력이 있다. 한 지점씩 짧게 캡처하고 즉시 재개한다.
8. 라이브 RAM 설치 상태에서 에뮬레이터를 리셋하면 패치가 사라진다. 이후 검증은 CUE 직접 부팅만 사용한다.
9. 새 검증 빌드를 만들기 전에 기존 실패 빌드의 원인을 문서와 기계식 검사에 반영한다.
10. 사용자 요청상 이전 검증 빌드는 새 빌드 생성 시 정리해야 한다. 다만 이번 세션에서는 재귀 삭제가 도구 정책에 차단되어 v26~v33이 남아 있다. 삭제 시 아래 정확한 디렉터리만 대상으로 하고 `original`, `extracted`, `workspace`, `work`, `docs`는 보존한다.

## 6. 미국판 자막 엔진에서 확정된 사실

미국판은 캐릭터 이름, 오프닝, 전투 전 상대 대사, 전투 후 대사에 공식 자막을 출력한다.

| 역할 | 미국판 RAM 주소 |
|---|---:|
| 이벤트 선택 | `0x8003C4D8` |
| 그룹/엔트리 선택 | `0x8003C578` |
| 프레임 갱신/표시 | `0x8003C5A8` |
| 표시용 렌더 데이터 생성 | `0x8003C868` |
| 섹션 포인터 배치 | `0x8003C920` |
| 공식 ASCII 렌더러 | `0x80036EF4` |

미국판 전역 상태:

- `gp+0x420`: 자막 프레임
- `gp+0x424`: 현재 자막 리소스 포인터
- `gp+0x428`: 초기화 플래그

타츠미 첫 살인 대사의 미국판 `DATA7/V00.DAT` 타임라인:

```text
00602 For the first time in my life,\0I've taken a life.\0
01800
```

- 그룹: 3
- 표시: frame 60~179
- frame 180: zero-line 종료 토큰
- 미국판 호출 위치: `0x80038DA4: jal 0x8003C5A8`

상세 분석:

- `docs/usa-subtitle-engine-comparison.md`
- `work/analysis/usa_subtitle_comparison.json`
- `work/analysis/usa_subtitle_timeline_catalog.json`

## 7. 일본판 공식 글리프 렌더러에서 확정된 사실

임시 TILE 사각형 렌더러는 PS1 해상도에서 글자가 깨져 폐기했다. 일본판 자체의 공식 텍스처 글리프 렌더러는 사용 가능하다.

- 일본판 텍스트 렌더러: `0x80038B80`
- 일본판 글리프 빌더: `0x80038F3C`
- 글리프 템플릿: `0x800858AC`, 39개 × 16 bytes
- 폭 테이블: `0x80085B1C`
- 저수준 `LoadImage`: `0x80069024`
- A 슬롯 인덱스: 13
- A 템플릿: `0x8008597C`
- 원본 A 템플릿 bytes:
  `8080802cd8003878e7003e00d80fe70f`
- 글리프 VRAM: `(950,256,4,16)` 16-bit words
- 전용 CLUT: `(1008,511,16,1)`, CLUT ID `0x7FFF`
- 사용 폰트: `G:\Downloads\Korean Traslate Project\Font\솔뫼 김대건 Medium.ttf`
- 스타일: 16×16 4bpp, 흰색 본문 + 1px 검정 외곽선

런타임으로 증명된 것:

1. 일본판 공식 렌더러 호출 가능.
2. `처` 4bpp 글리프 업로드 및 A 슬롯 교체 가능.
3. 전용 CLUT 사용 가능.
4. v28의 매 프레임 재업로드 진단에서는 `처B`가 깨끗하게 보였다.
5. 글리프/CLUT는 장면 전환 시 원본 폰트 업로드로 덮인다.
6. 완료된 폰트 업로드 훅 `0x80067864`에서 겹침을 검사하고 복구하는 경로가 동작했다.
7. 전투/전투 후 실제 대사 화면에서는 글리프 모양과 색이 정상인 경우가 확인됐다.

중요: 렌더러와 글꼴은 이미 증명됐다. 현재 미해결 문제는 **정확한 생성 시점과 호출 문맥**이다.

## 9. RAM/VRAM 침범 감사

기계식 기준 파일:

- `workspace/config/subtitle_memory_map.json`

### 거부된 CPU RAM

| 범위 | 이유 |
|---|---|
| `0x800A2E90..0x800A2E9B` | 게임 동적 데이터. 사용자 상태의 frame이 `0x4000`으로 덮임 |
| `0x80011D94..0x80011D9F` | 실제 실행 코드. v32 부팅 실패 |
| `0x80011D78..0x80011D83` | 런타임 게임 writer가 사용. v33에서 `0x4000` 재현 |

### 허용된 패치 페이로드 상한

- `0x800118B4..0x80011D84`
- 빌더 상한은 `0x80011D85` exclusive.
- v34 실제 끝: `0x80011D77`.
- 이 범위는 정적 코드/자산 삽입 한도이지 사용자 영구 상태 저장 허용 범위가 아니다.

### VRAM 충돌

- 글리프 `(950,256,4,16)`과 CLUT `(1008,511,16,1)`은 원본 `LoadImage`가 덮는다.
- 이 문제는 CPU RAM 소유권 실패와 다르다.
- 추적 증거: `work/analysis/font_loadimage_fontcell_transition_trace.json`.

## 11. v34가 실패한 뒤 가장 유력한 다음 조사

새 RAM을 할당하거나 곧바로 v35를 만들지 말 것.

### 최우선 가설: 일본판 삽입 위치가 너무 늦다

미국판은 `0x80038DA4`에서 자막 갱신 함수 `0x8003C5A8`을 호출한다. 위치는 장면 countdown을 감소·저장한 직후이고 마지막 장면 프레임 비교보다 앞이다.

일본판 구조 대응:

- countdown 저장: `0x8003A884..0x8003A888`
- 마지막 비교 시작: `0x8003A88C`
- 함수 에필로그: `0x8003A8A8`

v34는 편의를 위해 에필로그 `0x8003A8A8`을 훅했다. 미국판과 정확히 같은 렌더/OT 문맥은 `0x8003A88C` 부근일 가능성이 높다.

다음 순서:

1. 미국판 `0x80038D94..0x80038DD8`과 일본판 `0x8003A874..0x8003A8C0`을 나란히 다시 확인한다.
2. 일본판 `0x8003A88C` 진입 한 지점만 짧게 추적한다.
3. 그 시점에 다음을 캡처한다.
   - `gp+0x304` source pointer
   - source+4/source+12 서명
   - `gp+0x314` frame
   - `gp+0x318` countdown
   - `a0`, `v1`, `s0`, `ra`, `sp`
4. frame 0, 60 부근, 179에서 서명이 변하는지 확인한다. v34 서명은 장면 종료 후 캡처했으므로 초기 프레임에 달라질 수 있다.
5. 서명이 안정적이고 frame 60이 관측되면 `0x8003A88C`에 최소 래퍼를 넣는다.
6. 래퍼는 렌더 후 원본 두 명령/분기를 정확히 재현해야 한다. 원본 흐름을 에필로그로 건너뛰지 않는다.
7. 여전히 표시되지 않으면 공식 렌더러 호출 시점이 OT 제출 전인지 확인한다. 글로벌 렌더러는 증명됐으므로 글꼴 자체로 되돌아가지 않는다.

### 두 번째 가설: 목표 장면 서명이 종료 후 변형된 값이다

현재 v34 서명은 전투 후 장면을 진행한 뒤 읽었다. 원본 장면 플레이어가 source 내용을 소비하거나 덮을 수 있다. 따라서 다음 추적에서는 그룹 선택 직후와 frame 60에서 같은 source bytes를 비교해야 한다.

### 세 번째 가설: `gp+0x314`는 애니메이션 프레임이고 179에서 고정된다

목표 장면에서 179가 관측됐지만 미국판 전용 자막 프레임과 완전히 같은 카운터라고 증명된 것은 아니다. 시작 구간에서 증가 양상이 일치하는지 확인해야 한다. 종료를 음성 길이에 맞추려면 최종적으로 원본 음성 재생 상태나 미국판 zero-line 토큰에 대응하는 장면 이벤트를 사용한다.

- `0x8013E6E4`: **동영상 시작 시 0 리셋 확인**, 2히트당 +1 (15Hz).
- → **무상태 프레임 공식: `frame = [0x8013E6E4] × 2`** (30Hz 단위,
  ±1 오차는 자막 타이밍에 무의미). 컷신 래퍼는 이 값을 쓴다.

### USA 컷신 자막 블록 포맷 (2026-08-02 파싱 완료)

O05/O14의 USA판은 컨테이너에 **블록을 하나 더 붙인 것**이다
(JP: `count=1, [0xC, 0x7F784]` → USA: `count=2, [0x10, 0x7F788, 0x7FB98]`
— 영상 블록 내용은 바이트 단위로 동일, 헤더만 4바이트 늘어남).

추가된 자막 블록은 **V0X 섹션과 완전히 같은 포맷**이다:

```text
u32 group_count
u32 boundaries[group_count+1]   그룹별 시작 토큰 인덱스
u32 token_offsets[total]        이 배열 시작 기준 상대 오프셋
텍스트 블롭                      4자리 프레임 + 1자리 줄수 + NUL 종료 줄들
```

- O05 블록 `0x7F788..0x7FB98`: group_count=7, 토큰 24개
  (마지막 그룹은 종료 토큰 1개 → **실 자막 그룹 6개**)
- O14 블록 `0xF314..0x10380`: group_count=13, 토큰 126개
  (→ **실 자막 그룹 12개**)
- 기존 `build_v0x_subtitle_schedule.py`의 `parse_tokens`를 그대로 쓸 수
  있다 (offsets_base만 블록 시작으로 지정).

### 그룹 = 동영상 ID (USA 셀렉터 논리로 역산)

USA `0x8003C4D8(event_id)`의 분기가 전체 자막 인벤토리를 설명한다.

| event 범위 | 테이블 | 엔트리 수 | 대응 |
|---|---|---|---|
| `< 6` | `[0x80086458+4]` | 6 | **동영상 A계열** = O05 실그룹 6 |
| `6..0x3B` | `[0x80086458+0]` | 54 | V0X 승리 장면 54 (v38 완료) |
| `0x3C..0x47` | `[0x80086458+8]` | 12 | **동영상 B계열** = O14 실그룹 12 |
| `>= 0x48` | `[0x80086518]` 직접 | 19 | EXE 내장 전투 전/처형 대사 |

즉 **자막 그룹 인덱스 = 동영상 ID**이며, 54개 승리 장면 수와 정확히
일치하는 것이 이 해석의 강한 방증이다.

### 일본판 동영상 시작 함수 (확정)

`0x8003AA78(a0=kind, a1=buffer, a2=movie_id)`

- `kind==0` → `0x8003AAB4~` 경로 (파일 ID `0x56`/`0x57` 로드)
- `kind==1` → `0x8003AB7C~` 경로 (**미해독 — 아래 잔여 과제**)
- `s2 = movie_id`, `0x8003AB28`에서 `[0x80086A44 + id*4]`의 halfword 쌍을
  **`0x80086A3C`/`0x80086A3E`(게임 소유 전역)에 저장** — 훅 시점에
  읽을 수 있는 동영상 판별자다. JP/USA 테이블 바이트 동일.
- id 0~5의 첫 halfword는 `0x00F0,0x00DB,0x0216,0x0108,0x010E,0x012C`로
  **서로 유일** → A계열 그룹 판별에 그대로 사용 가능.

### 동영상 강제 재생 (조사 도구, 2026-08-02 런타임 검증)

- 파일 ID 해석: 로더 `0x80044AB4`가 `id*8 + 0x80088A4C`로 로드 테이블을
  인덱싱한다. **id 0x56 = O05**(공통, 버퍼 앞), **id 0x57+movie_id =
  O06..O14**. 디스크 크기 대조로 확정.
- 동영상 시작 `0x8003AA78(kind, buffer, movie_id)`의
  `0x8003AA9C: move $s2, $a2` 한 명령만 `ori $s2, $zero, N`으로 바꾸면
  **어떤 컷신이든 movie N을 강제 재생**한다 (delay slot이라 흐름 불변).
  빌더: `workspace/scripts/build_forced_movie_debug.py --movie-id N`
  (조사 전용, 배포 금지). 엔딩 조건 없이 오프닝 자리에서 확인 가능.
- 강제 movie 8 실측(`work/analysis/ending_movie_trace.json`):
  `[0x80086A3C]`=`0x00C8`(테이블 id 8 값)로 정확히 바뀌고,

### 동영상 자막 블록 내용 (정적 파싱)

- **O05 6그룹 = 캐릭터 6인의 스토리 도입 독백** (movie id 0~5 =
  O06~O11, 모두 57,784바이트로 크기까지 일치). 매핑 확정.
- **O14 12그룹 = 엔딩 시퀀스들** (그룹 0: frame 60~2055의 장편 타임라인).

### 최종 판별자: `gp+0x32C`(kind) / `gp+0x338`(movie_id)

`0x8003AA78`의 두 경로가 합류하는 `0x8003AB98`에서
`sw $s1, 0x32c($gp)`(kind), `sw $s2, 0x338($gp)`(movie_id)를 **항상**
저장한다. 파라미터 테이블(`0x80086A3C`)보다 직접적이고 두 경로 모두
커버하므로 **래퍼는 이 두 값을 쓴다** (RAM: `0x800A2DB0`, `0x800A2DBC`).

### kind 경로 구분 (강제 재생 실측으로 판명)

- `kind==0`: 파일 `0x56`(O05, 공통) + `0x57+movie_id`(O06~) 로드.
  **파라미터 테이블 `0x80086A44`는 id 0~5만 유효** — id 6~8 강제 시
  영상이 깨지고 음성만 재생됨(2026-08-02 사용자 확인). 즉 kind 0의
  유효 범위는 **movie_id 0~5 = 캐릭터 6인 도입 컷신**이며, 이는 O05
  자막 블록의 6그룹과 정확히 대응한다. **매핑 확정.**
- `kind==1`: 파일 `0x60`(O15) 고정 로드 후 `0x80027afc` 경로.
  엔딩 계열은 이쪽으로 추정된다. 강제 시험하려면 디버그 빌더로
  **kind도 함께** 고정해야 한다 (`0x8003AA80: move $s1, $a0`를
  `ori $s1, $zero, 1`로 치환 — `--kind` 옵션).

### 엔딩 구조 확정 (2026-08-02, USA 디스패치 테이블 + 사용자 확인)

미국판 엔딩 자막 트리거는 `0x80047DBC(a0 = ending_index)` 함수 안의
`0x80047DF0: jal 0x8003C4D8` (`a0 = table[index] + 0x3C`)이다.
테이블 `0x800878D0` (13바이트, USA 전용):

```text
FF 00 02 04 06 08 0A 01 03 05 07 09 0B
```

- index 0 → `-1` = **배드 엔딩(자막 없음)**
- index 1~6 → event `0x3C+{0,2,4,6,8,10}` = **캐릭터 6인 × 노멀 엔딩**
- index 7~12 → event `0x3C+{1,3,5,7,9,11}` = **캐릭터 6인 × 굿 엔딩**

→ **O14 자막 블록의 그룹 = `2×(캐릭터−1) + (0 노멀 / 1 굿)`**.
사용자 확인(엔딩은 노멀·굿 2종)과 정확히 일치하며, 12그룹의 정체가
확정됐다.

### kind==1의 정체 (강제 재생 실측)

`kind==1`(파일 `0x60`=O15, 27,304바이트)은 엔딩 컷신이 아니라
**배드 엔딩의 세로쓰기 시(詩) 화면**이다 (사용자 스크린샷 2026-08-02:
`武士の道 汚した者の あはれかな` + 서명). 자막 대상이 아니라 **정적
그래픽 번역 대상**이며 (USA 테이블에서도 index 0 = 자막 없음),
`docs/graphics-inventory.md` 계열 작업으로 분류해야 한다.

`jal 0x80022384`(파일 로더) 호출자를 전수 스캔해 O 파일 소유 코드를
확정했다 (스크립트: scratchpad `find_file_loads.py` 방식).

| 파일 | id | 로드 위치 | 용도 |
|---|---|---|---|
| O05 | 0x56 | `0x8003AAC0` | 도입 컷신 공통 (자막 6그룹 보유) |
| O06~O11 | 0x57+id | `0x8003AAF4` | 도입 컷신 6종 본편 |
| O12 | 0x5D | `0x80039F0C` | — |
| O13 | 0x5E | `0x8003C490` | — |

  (`find_callers.py 0x8004A138`) 상태 값을 상수로 고정하는 것이다.
- 부수 확정: 도입 컷신 선택 = `[0x800A30A0] % 6` (호출부 `0x80049A44`),
  배드 엔딩 시 선택 = `카운터 % 5` (호출부 `0x8004995C`) → 시 화면은
  **5가지 변형**이 있다.

### 엔딩 인덱스 전역 확정 (2026-08-02) — v40의 핵심

`0x80049840`이 엔딩 인덱스를 계산해 **`[0x800A3178]`(halfword)** 에
저장한다.

```text
a0 = [0x8013E7A0]        ; 캐릭터 인덱스 0~5
v1 = [0x800A3074]        ; 스테이지
[0x800A3178] = a0
if (v1 == 10)            ; 최종 스테이지까지 클리어했으면
    [0x800A3178] = a0+6  ; → 굿 엔딩
```

즉 **`n = [0x800A3178]`: 0~5 = 캐릭터별 노멀 엔딩, 6~11 = 굿 엔딩**.
미국판 디스패치 테이블(`index 0`=배드 제외, 1~12)과 `USA index = n+1`로
정확히 대응하므로 자막 그룹 공식이 확정된다.

**O14 자막 그룹 = `n < 6 ? 2n : 2(n−6)+1`**

- 이 전역은 게임 소유이므로 래퍼가 그대로 읽으면 된다 (영구 상태 불필요).
- `[0x800A3178]`을 소비하는 곳: `0x8004A184(a0)`가 이 값으로 엔딩 영상을
  **STR 스트리밍**한다 (`0x80065A48`/`0x80066048`/`0x800661A8`,
  파일명 테이블 `0x8012DBD8`). 즉 엔딩 본편은 스트리밍 동영상이고,
  `0x8003C950`이 로드하는 O14는 그 위에 얹히는 데이터다.
- 엔딩 상태 트리거: `gp+0x5D0` 카운터가 `0x20`에 도달하면
  `0x8004A5F0` 경로가 엔딩을 시작한다 (`0x8004A138`은 점프 테이블
  진입이라 `jal` 호출자가 없다).

### 엔딩 갤러리 해금 + 런타임 실측 (2026-08-02)

엔딩은 타이틀의 **`活劇映像上映`(활극영상상영) 메뉴 → `エンディング`**
에서 재생할 수 있다. 해금 비트마스크는 **`[0x800A30B8]`**
(비트 `s1`=노멀, 비트 `s1+6`=굿).

- EXE 패치로 해금 게이트(`0x8004A51C`, `0x8004A578`)를 nop 처리한
  빌드(`build_forced_movie_debug.py --unlock-endings`)만으로는 메뉴가
  잠긴 채로 보였다.
- **확실한 방법**: 런타임에 마스크를 직접 채운다.

  ```powershell
  python workspace\scripts\poke_duckstation_memory.py `
    --address 0x800A30B8 --value 0xFFFFFFFF
  ```

  (신규 스크립트. 리셋하면 사라지므로 필요할 때마다 재실행)

실측 결과 (엔딩 재생 중 RAM 2회 캡처, `ram_ending_t0/t1.bin`):

- `[0x800A3178] = 5` — 갤러리에서 고른 엔딩의 인덱스. 그룹 공식
  `n≤6 ? 2(n−1) : 2(n−7)+1` → **그룹 8**. O14 그룹 8 텍스트가
  "killing machine" / "Utsusemi...I did what you wanted" 계열로
  블랙 로터스 엔딩과 부합 → **공식 교차 검증됨**.
- **`[0x8013E6E4]`(도입 컷신 프레임)는 엔딩에서 증가하지 않는다** —
  엔딩은 STR 스트리밍이라 별도 카운터를 쓴다.
- 단조 증가 후보: `0x80128234`(+248/4초 ≈ 60Hz),
  **`0x80128248`(+124/4초 ≈ 30Hz)** ← 프레임 카운터 유력
  (O14 그룹 8의 마지막 프레임 1800 ≈ 30Hz에서 60초로 엔딩 길이와 부합).
  `0x8014C3xx` 대역은 스트리밍 링버퍼라 카운터가 아니다.
- **다음 확인**: 엔딩을 다시 시작한 직후 캡처해 `0x80128248`이 0으로
  리셋되는지 확인하면 프레임 공식이 확정된다.

### O14 그룹 ↔ 캐릭터 대응표 (사용자 런타임 확인으로 검증 완료)

`group = 2×char + variant` (variant 0=노멀, 1=굿), char 순서는 음성
뱅크 이름의 숫자와 동일: 0 칸누키, 1 미카도, 2 블랙로터스, 3 타츠미,
4 호타루, 5 우츠세미.

| group | char/변형 | 첫 자막 | 마지막 프레임 |
|---|---|---|---:|
| 0 | 0 노멀 | Yugiri, the cursed sword... | 2055 |
| 1 | 0 굿 | `Eyaaah..." | 1200 |
| 2 | 1 노멀 | Yugiri... but it's not the sword's fault. | 2100 |
| 3 | 1 굿 | `Mikado, are you leaving?" | 1200 |
| 4 | 2 노멀 | It's over... | 1200 |
| 5 | 2 굿 | What a waste...killing yourself like that. | 1500 |
| 6 | 3 노멀 | I won... / I even beat the Dojo Master... | 1860 |
| 7 | 3 굿 | One year later... | 900 |
| 8 | 4 노멀 | `Certainly even a killing machine like you...` | 1920 |
| 9 | 4 굿 | No matter how difficult the way may be... | 1080 |
| 10 | 5 노멀 | Yugiri... Hanzaki, is this what made you go cr... | 1950 |
| 11 | 5 굿 | Ahhh... | 1500 |

검증: 갤러리에서 `[0x800A3178]=5` 엔딩을 재생했더니 **붉은 옷 여성
캐릭터(호타루)** 영상이 나왔고, 공식이 가리키는 그룹 8 = char 4 =

### 2차 판정: 프리징은 래퍼가 아니라 **O05 확장** 때문 (2026-08-02)

`--skip cut`(컷신 훅 미패치) 빌드에서도 **프리징이 그대로** 발생했다.
컷신 재생 중에는 승리 훅(V0X 스테퍼)도 엔딩 훅(스트리밍 루프)도 돌지
않으므로, **래퍼 코드는 용의선상에서 제외**된다. 남는 원인은 v38에
없던 유일한 변화, 즉 **O05/O14의 확장·재배치**다.

가장 유력한 메커니즘 — 동영상 로더의 버퍼 배치와 충돌:

```text
0x8003AAC0: 파일 0x56(O05)을 s0 = 0x8014C000 에 로드
0x8003AAD8: v0 = [s0]              ; 블록 수 (JP는 1)
0x8003AAE8: v0 = [s0 + 4 + 4*v0]   ; = 0x7F784 (원본 파일 끝)
0x8003AAF0: s0 = s0 + v0           ; 동영상 파일을 그 뒤에 로드
```

- 게임은 **O05 바로 뒤에 동영상 파일을 이어서 적재**한다. 우리가
  붙인 한국어 섹션이 정확히 그 자리(offset `0x7F784`)를 차지하고,
  로드 크기를 키워 놓았으므로 버퍼 배치가 어긋난다.
- 따라서 컷신용 섹션은 **파일 뒤에 붙이면 안 된다.** 대안:
  1. 섹션을 O05가 아닌 **다른 파일**(예: 사용되지 않는 O16/O17,
     8,192B)에 넣고 별도로 로드하거나,
  2. O05 헤더의 블록 테이블 끝값을 섹션 크기만큼 키워 동영상이 섹션
     **뒤에** 적재되게 하거나(미국판이 실제로 한 방식 — USA는 블록을
     추가하고 헤더를 4바이트 늘렸다),
  3. 컷신 자막 데이터를 V0X 쪽 섹션에 합쳐 넣고 컷신 래퍼가 그쪽을
     참조하게 한다.
- **검증 완료 (사용자 확인)**: `--no-movies` 빌드
  (`build/subtitle_v41_v0xonly`, 페이로드 1212/1233)에서 **프리징이
  사라지고 대사 자막이 정상 출력**됐다. → **원인은 O05 확장으로 확정**,
  그리고 공유 본체 리팩터링(컨텍스트 ID 방식)은 **회귀 없음**이 함께
  입증됐다. v41의 코드 구조는 그대로 두고 데이터 배치만 고치면 된다.

### 메인 루프 발견 — 엔딩 훅의 올바른 위치 (2026-08-02)

엔딩 재생 중 PC 표본 60회(`sample_duckstation_pc.py`) 결과 `ra`가
`0x80043224`(sp=`0x801FFF00`, 최상위 스택)에 집중됐다. 그 주변이
**게임 메인 루프**다.

```text
0x800431F0: addu  $at, $at, $v0
0x800431F4: lw    $v0, ($at)        ; 상태 점프 테이블에서 핸들러 로드
0x800431FC: jalr  $v0               ; ← 현재 상태 핸들러를 매 프레임 호출
0x80043204: lui   $a0, 0xF200
0x80043208: jal   0x80078360        ; 이하 VSync 대기 스핀 루프
0x80043210: slti  $v0, $v0, 0x180
0x80043214: beqz  $v0, 0x8004322C
0x8004321C: jal   0x80066D00
0x80043224: j     0x80043208
```

- `0x800431FC`의 `jalr`이 **프레임당 1회** 상태 핸들러를 부른다.
  앞서 못 찾았던 `0x80088A00` 점프 테이블이 여기서 인덱싱된다.
- **엔딩 훅을 `0x80043204`로 옮긴다** (핸들러 복귀 직후, 프레임당 1회).
  8바이트(`lui $a0,0xF200` + `jal 0x80078360`)를 `j stub; nop`으로 바꾸고,
  스텁은 자막 처리 후 `a0 = 0xF2000001`로 `jal 0x80078360`을 재현한 뒤
  `$v0`를 살린 채 `0x80043210`으로 복귀하면 된다.
- 기존 게이트(`[0x8013E6D8]`의 word3 == `0x230`)가 그대로 엔딩 여부를
  걸러 주므로 다른 상태에서는 아무것도 그리지 않는다. 더 엄격히 하려면
  `[0x800A3178] > 0` 조건을 함께 본다(이미 스텁에 있음).
- 이 지점은 **도입 컷신에도 같은 방식으로 쓸 수 있는** 후보다. 컷신
  프리징은 O05 확장 때문이었으므로 그쪽은 별개로 고친다.

메인 루프를 건드렸는데도 게임이 완전히 정상이라는 것은 훅 자체는
정확히 삽입됐다는 뜻이다. 그런데도 엔딩 자막이 없다.

- 게이트 값(`[0x8013E6D8]`→O14, `[0x800A3178]`=인덱스,
  `[0x80128248]`=프레임)은 모두 재생 중 실측으로 확인된 값이다.
- 남은 유력 원인은 **OT(오더링 테이블) 타이밍**이다. `0x80043204`는
  상태 핸들러가 **이미 프레임을 구성·제출한 뒤**이므로, 여기서 추가한
  프리미티브는 이번 프레임 OT에 반영되지 않는다. 과거 v4가
  `0x80070838`(VSync 계열)에서 실패하고 v5에서 공통 `AddPrim`
  `0x8006A368`으로 전환했던 것과 정확히 같은 함정이다.
### OT 구조 단서 (2026-08-02, 정적)

`0x8006A368`(AddPrim) 호출자 중 자막 렌더러 근처는 `0x80038B68`이며,
그 함수(`0x80038B44`)는 다음과 같다.

```text
0x80038B44: addiu $sp, $sp, -0x18
0x80038B4C: andi  $v0, $v0, 1        ; 더블버퍼 선택
0x80038B50~58: a1 = (v0&1) * 36
0x80038B5C: lui   $v0, 0x8012
0x80038B60: addiu $v0, $v0, 0x1694   ; 프리미티브 버퍼 0x80121694
0x80038B64: addiu $a0, $a0, 0x3FFC   ; ★ OT = <컨텍스트> + 0x3FFC
0x80038B68: jal   0x8006A368
```

- **OT는 항상 `<컨텍스트 포인터> + 0x3FFC`** 형태다 (컷신 경로에서 본
  `[0x800A3010] + 0x3FFC`와 동일한 규칙).
- 중요한 점: **텍스트 렌더러 `0x80038B80` 자체는 AddPrim을 부르지
  않는다.** 즉 렌더러는 프리미티브를 만들어 두고, 그것을 OT에 거는
  주체는 호출자 쪽이다. 승리 장면에서는 그 연결이 이루어지지만 엔딩
  상태에서는 이루어지지 않는 것으로 보인다.
1차 계측(`work/analysis/ot_helper_trace.json`): `0x80038B44`는 일반
플레이 중 **초당 약 17회** 호출된다(12초에 200히트, `ending_frame`은
내내 0 = 엔딩 아님). 즉 이 헬퍼는 상시 동작하는 정상 경로다.
다만 사용하던 추적기는 메모리만 기록하고 **레지스터를 남기지 않아
`a0`(컨텍스트)를 얻지 못했다.** 다음 계측은 `a0`를 함께 저장하도록
추적기를 확장하거나(`trace_movie_frame_counter.py`에 레지스터 필드
추가), 히트 상한을 낮춘 `wait_duckstation_execute.py`로 승리 장면과
엔딩에서 각각 1회씩 잡아 비교해야 한다.

- **다음 착수점(갱신)**: 승리 장면 실행 중 `0x80038B44`에 짧게
  중단점을 걸어 `a0`(컨텍스트)와 결과 OT 주소를 캡처하고, 엔딩 재생
  중 같은 지점이 호출되는지/어떤 컨텍스트인지 비교한다. 호출되지
  않는다면 엔딩 컨텍스트의 OT를 직접 구해 `0x8006A368`을 우리가
  호출하는 방식(v5 방식)으로 전환한다.

- 예비 조사: `0x8006A368`(AddPrim) 호출자는 EXE 전역에 수십 곳
  (`0x80012C80`, `0x80012DF8`, `0x8001B26C`, …)이라 단순 목록만으로는
  좁혀지지 않는다. 글리프 빌더(`0x80038F3C`) 꼬리(`0x80039100~`)는
  폭 테이블 전진 로직이며 OT 연결부가 아니다. **렌더러가 프리미티브를
  어느 OT/버퍼에 넣는지 먼저 특정해야 한다** — 승리 장면(정상 동작)
  실행 중 `0x80038B80` 내부를 짧게 추적해 AddPrim 호출과 그때의 `a0`
  (OT 포인터)를 캡처한 뒤, 같은 값을 엔딩 재생 중에 비교하면 어긋나는
  지점이 드러난다.
- **다음 착수점**: 엔딩 컨텍스트만 `0x8006A368`(AddPrim) 훅으로 전환
  한다. 자막 활성 중 첫 `AddPrim` 호출에서 게임이 넘기는 **실제 OT**에
  프리미티브를 연결하는 방식이며, v5에 선례가 있다
  (`docs/voice-runtime-trace.md`의 "실제 OT 연결 v5" 항목).
  주의: 동굴 여유가 5바이트뿐이므로 스텁 교체 시 크기를 함께 줄여야
  한다(예: 더 이상 쓰지 않는 `0x8004A244` 관련 상수·경로 제거).

### 진짜 프레임 경로 (참고 — 인터럽트 문맥이라 비권장)

프레임 카운터 `0x80128248`을 **쓰는** 코드는 한 곳뿐이다.

```text
0x8006FBCC: lui $at, 0x8013
0x8006FBD0: sw  $v0, -0x7DB8($at)     ; = 0x80128248
```

- 위치가 `0x8006Fxxx` 라이브러리/스트리밍 영역이므로, 이 함수는
  **CD/STR 콜백(인터럽트 문맥)일 가능성이 높다.** 그렇다면 여기서
  직접 렌더러를 호출하는 것은 위험하다(ISR에서 GPU 큐 조작).
- 권장 접근: 인터럽트 문맥을 피해 **메인 루프 쪽 엔딩 상태 핸들러**에
  훅을 건다. 후보는 `0x8004A5F0`이 속한 상태 함수(엔딩 진행 중 매
  프레임 도는 상태 스테퍼)이며, 거기서 `[0x80128248]`을 프레임으로
  읽으면 된다. `0x8004A184` 호출 이후 게임이 어떤 상태로 돌아가
  프레임을 도는지 `sample_duckstation_pc.py`로 엔딩 재생 중 PC를
  표본 추출하면 바로 좁혀진다.
- 참고(폐기된 설명): 아래 "가장 유력한 설명"은 위 계측으로 확정됨.

- 확정: **훅 `0x8004A244`가 도는 루프가 프레임 단위 표시
  루프가 아니다.** 그룹 판정 프로브에서 `s7(frame)=1`이었고, 이 루프가
  재생 초반 몇 회만 돌고 이후 재생은 인터럽트/다른 경로로 진행된다면
  프레임이 45에 닿기 전에 루프가 끝나 매칭이 영원히 실패한다.
- **다음 확인**: `trace_jp_scene_catalog.py`류의 카운팅 추적으로
  `0x8004A244`의 **히트 횟수와 그때의 `[0x80128248]` 값 분포**를 기록할
  것. 히트가 소수(예: 수 회)에 그치면 위 가설이 확정되고, 엔딩용 훅을
  **실제 프레임 표시 루프**로 옮겨야 한다 (후보: `0x800661A8` 내부,
  또는 프레젠터 `0x80027afc`가 등록하는 콜백/상태 스테퍼).
- 참고: 프레임 소스 `[0x80128248]` 자체는 30Hz로 증가하고 엔딩마다
  0으로 리셋되는 것이 이미 확인됐으므로, 문제는 프레임 값이 아니라
  **훅이 그 프레임 구간 동안 실행되지 않는다는 점**이다.

- **다음 확인 순서(1차 작성)**: ① 래퍼가 렌더러까지 실제로 도달하는지
  (`wait_duckstation_execute.py --address 0x80038B80`를 엔딩 중에 걸어
  확인) ② 도달한다면 OT 문제로 확정 → 엔딩 프레젠터가 쓰는 OT를 찾아
  `0x8006A368` 훅 방식으로 전환. ③ 도달하지 않는다면 공유 본체의
  컨텍스트 분기(`$t9==2` 경로)를 GDB로 단계 확인.

## 25. 렌더 파이프라인 정적 확정 (2026-08-02) — 엔딩 미출력 재진단

이전 절의 "OT 타이밍" 진단과 `0x80038B44` 캡처 계획은 **대상 자체가
틀렸다**. 정적 분석으로 렌더 경로 전체가 확정되어 런타임 캡처가
불필요해졌다.

### 25.1 공식 텍스트 렌더러의 프리미티브 연결 경로

`0x80038B80`(텍스트 렌더러)은 `jr $ra`가 `0x80038F34`에 있는 함수이며,
내부 호출은 `0x80038F3C`(글리프 빌더) · `0x80028318` · `0x80035854`
뿐이다. 마지막 호출이 프리미티브를 OT에 건다.

```
0x80038EF0: lui $a0,0x8012 ; addiu $a0,$a0,0x16DC   ; 프리미티브 버퍼 0x801216DC
0x80038EF8: move $a1,$zero
0x80038F00: move $a2,$zero
0x80038F10: move $a3,$zero                          ; ★ OT depth = 0
0x80038F14: jal  0x80035854
```

`0x80035854`는 `s6 = a3 << 2`를 만들고

```
0x80035970: lw  $a0, 0x3010($a0)     ; a0 = [0x800A3010]  (렌더 컨텍스트)
0x80035988: jal 0x8006A368           ; AddPrim
0x8003598C: addu $a0, $a0, $s6       ; a0 = 컨텍스트 + depth*4
```

즉 **`AddPrim([0x800A3010] + 0, prim)`** — 단일 전역 컨텍스트의
**최전면(depth 0)** 레이어다. 상태별로 OT가 갈리지 않는다.

**따라서 OT 주소는 처음부터 문제가 아니었다.** "렌더러가 AddPrim을
호출하지 않는다"는 24절의 서술은 틀렸다 — `0x80035854`를 경유해 직접
건다.

### 25.2 `0x80038B44`는 무관한 함수였다

실제 함수 시작은 `0x80038B34`이고, 인자가 없는 전역 참조 함수다.

```
0x80038B34: lw $v0, 0x2F3C($v0)   ; db index = [0x800A2F3C]
0x80038B40: lw $a0, 0x3010($a0)   ; 컨텍스트 = [0x800A3010]
0x80038B64: addiu $a0,$a0,0x3FFC  ; OT 꼬리 = 최후면
0x80038B68: jal AddPrim
```

호출자는 `0x80032098` / `0x80038834` / `0x8003893C` 세 곳뿐이며 텍스트
렌더러와 무관하다. depth 0(최전면)이 아니라 `+0x3FFC`(최후면)를 쓴다.
**이 추적선은 폐기한다.**

`ClearOTagR` 방식임은 실측으로 확인했다: `[0x800A3010]=0x80131C70`일 때
`[0x80135C6C] = 0x00135C68` (직전 엔트리를 가리키는 역방향 링크).

### 25.3 메인 루프 구조와 상태 테이블

```
0x800431BC: jal 0x8003E9A4        ; 타이머 24개 감소 루프 (플립 아님)
0x800431DC: lh  $v0, 0x698($gp)   ; 상태 인덱스
0x800431E8: lui $at,0x8009 ; addiu $at,$at,-0x7690   ; 테이블 0x80088970
0x800431FC: jalr $v0              ; ★ 상태 핸들러 = 프레임 그리기 전부
0x80043204: (v41 엔딩 훅 위치)
0x80043208: jal 0x80078360        ; VSync 대기
```

- 상태 변수 = `gp+0x698` = **`0x800A311C`** (gp = `0x800A2A84`, 실측)
- 핸들러 테이블 = **`0x80088970`**
- `0x8003E9A4`는 프레임 플립이 **아니다** (24개 타이머 감소 루프).

### 25.4 엔딩 상태 확정

핸들러 테이블에서 `0x8004A184`(엔딩 함수, 구 훅 `0x8004A244`가 속함)에
도달하는 것은 **state 14 / 핸들러 `0x80049554`** 하나뿐이다.
state 15(`0x80049830`) · 16(`0x80049838`)은 `jr $ra; nop` **빈 스텁**이다.

엔딩 핸들러는 프레임마다 같은 전역 컨텍스트에 프리미티브를 건다:

```
0x80049790: lw $a0, 0x3010($a0) ; 0x80049794: jal AddPrim
0x800497B4: lw $a0, 0x3010($a0) ; 0x800497B8: jal AddPrim
0x800497C4: [0x800A309C] += 1   ; 페이드 카운터, 0xF1에서 전이
0x80049814: sh $v0, 0x311C($at) ; 다음 상태 = 0x1F
```

`0x8004A2C0`~(구 "엔딩 렌더"로 본 구간)은 `[0x800A30B8]` 언락 비트마스크를
읽는 **갤러리 메뉴**(活劇映像上映)이지 엔딩 재생이 아니다.

### 25.5 재진단

엔딩 훅 `0x80043204`는 상태 핸들러 **반환 직후 · VSync 직전**에 있다.
플립이 핸들러 안에서 일어난다면 늦고, 다음 반복 시작에서 일어난다면
타이밍은 오히려 맞다. `0x8003E9A4`가 플립이 아님이 밝혀졌으므로
"타이밍 때문"이라는 24절 결론은 **근거가 사라졌다**.

훅은 매 프레임 실행되므로(메인 루프 상주), 남은 유력 원인은
**래퍼 내부의 레코드 조회 실패**(엔딩 index/그룹/프레임 불일치)다.

### 25.6 다음 착수점 (갱신)

`workspace/scripts/poll_ending_state.py` (신규) — 중단점 없이 메모리만
읽어 화면을 멈추지 않는다. 엔딩 재생 중 실행해

- `state`(0x800A311C)가 14가 되는지

- `ending_frame`(0x80128248) 증가 여부

## 26. 엔딩 실측 (2026-08-02) — 래퍼 입력은 전부 정상, 원인은 영상 경로

### 26.1 상태 확정 정정

25.4절의 "엔딩 = state 14"는 **틀렸다**. 실측 결과 엔딩 재생 내내

### 26.2 래퍼 입력 4종 전부 정상 (실측)

| 항목 | 주소 | 실측 |
|---|---|---|
| 상태 | 0x800A311C | 50 (핸들러 0x8004A2C0) |
| 엔딩 인덱스 | 0x800A3178 | 5 → 4 (엔딩마다 갱신됨) |
| 프레임 | 0x80128248 | 0..2064, 엔딩 사이 2064→15 리셋 |
| 버퍼 베이스 | [0x8013E6D8] | 0x800AE6C0 (유효) |

**조회 체인(베이스→word3→섹션→그룹→프레임 구간)이 전 구간 통과한다.**

24절의 "레코드 조회 실패" 가설도 이로써 **기각**된다.

### 26.3 남은 원인: 영상은 OT를 쓰지 않는다

엔딩 재생 함수 `0x8003F60C`(`0x8003F784`에서 `jr $ra`)는 내부 호출이
`0x80070F38` · `0x80070B9C` 둘뿐이고 **OT 경유 그리기가 없다**.
MDEC 출력이 프레임버퍼로 직접 나가면, 공식 렌더러가 프리미티브를 거는
`AddPrim([0x800A3010] + 0)`의 OT는 그 프레임에 제출되지 않는다.

이 가설은 관측 전부를 하나로 설명한다.

- 승리 장면(비영상, OT 렌더) → 자막 정상
- 엔딩 · 도입 컷신(둘 다 영상) → 자막 없음
- 그 외 입력값은 전부 정상

### 26.4 다음 착수점 (갱신)

`poll_ending_state.py`에 `ot_head`([ctx+0x3FFC])와
`ot_depth0`([ctx+0])를 추가했다. 엔딩 재생 중 이 값이

- **변한다** → OT는 살아 있음 → 원인은 훅 시점, `0x8004A2C0` 내부
  (`jal 0x8003F60C` 직후 `0x8004A788`)로 훅 이동
- **고정이다** → OT 미제출 확정 → 자막을 OT에 걸 수 없으므로
  즉시 그리기(DrawPrim) 또는 영상 프레임 이후 프레임버퍼 합성으로
  전환해야 한다

정지 화면 기준값: `ot_depth0 = 0x00121BD4` (state 50, 재생 아님).

| DMA2 MADR (0x1F8010A0) | `0x80071A20`, `0x800721F4`, `0x8007220C`, `0x80072214`, `0x80072264`, `0x8007228C` |
| DMA2 BCR (0x1F8010A4) | `0x8003BE1C`, `0x80071AC8`, `0x800721E8`, `0x80072204`, `0x80074740` |

## 28. libgpu 즉시 전송 함수 확정 (2026-08-02)

### 28.1 27.3절 정정

27.3절의 DMA 주소 목록(`0x80071A20` 등)은 **오탐이다**. 하위 16비트만
비교해 `0x800910A0` 같은 RAM 전역을 DMA 레지스터로 잘못 집계했다.
이 게임은 GPU 포트 주소를 코드 상수로 쓰지 않고 **전역 테이블**에
담아 참조한다(Sony libgpu의 `ResetGraph` 초기화 방식).

### 28.2 GPU 포트 테이블

```
0x8008A580: 0x1F801810   GP0  (data/command)
0x8008A584: 0x1F801814   GP1  (control/status)
0x8008A588: 0x1F8010A0   DMA2 MADR
0x8008A58C: 0x1F8010A4   DMA2 BCR
0x8008A590: 0x1F8010A8   DMA2 CHCR
```

코드에서는 `lui 0x8009` + 음수 오프셋으로 참조한다
(`-0x5A80`=GP0, `-0x5A7C`=GP1, `-0x5A78`=MADR, `-0x5A74`=BCR,
`-0x5A70`=CHCR). libgpu 포트 접근은 `0x80068CCC`~`0x8006A0DC`에 몰려 있다.

참고: 엔딩 재생 중 `ot_depth0`로 관측된 `0x0008A56C`는 바로 이
libgpu 데이터 영역(`0x8008A56C`)을 가리키는 정적 잔류값이다.

### 28.3 체인 DMA 전송 함수 = `0x80069570`

MADR+CHCR을 쓰는 시퀀스는 4곳이며 CHCR 값으로 구분된다.

| 위치 | CHCR | 정체 |
|---|---|---|
| `0x80069230` | `0x01000201` | VRAM 전송 (LoadImage 계열) |
| `0x800694B8` | `0x01000200` | VRAM 회수 (StoreImage 계열) |
| **`0x800695B0`** | **`0x01000401`** | **링크드리스트 전송** |
| `0x80069F40` | (읽기) | 상태 조회 |

**`0x80069570`** 이 우리가 찾던 함수다.

```
0x80069570: lui $v1, 0x400 ; ori $v1,$v1,2
0x80069580: sw  $v1, (GP1)        ; GP1 = 0x04000002 (DMA 방향 = CPU→GPU)
0x80069590: sw  $a0, (MADR)       ; ★ $a0 = 프리미티브 체인 head
0x800695A0: sw  $zero, (BCR)
0x800695B0: sw  $v1(0x01000401), (CHCR)
```

- 인자는 **`$a0` 하나** (리스트 head)
- `jal` 호출자는 단 1곳 `0x80069000`이며, 이는 함수 진입점이 아니라
  어떤 함수의 꼬리다(에필로그가 이어짐). 바로 뒤 `0x80069024`가
  기존에 확인된 `LoadImage`이므로 주소 지도가 서로 일치한다.

### 28.4 v42 설계 방향

공식 렌더러는 프리미티브를 `0x801216DC`에 만든다. 영상 프레임에서는
OT가 죽어 있으므로, `AddPrim` 대신 **`0x80069570`을 직접 호출**해
그 체인을 GPU로 바로 쏜다.

주의할 점 두 가지:

1. **체인 종단** — 마지막 프리미티브의 next 포인터(태그 상위 24비트)를
   `0xFFFFFF`로 만들어야 한다. 그렇지 않으면 GPU가 폭주한다.
2. **DMA 경합** — 영상 스트리밍도 DMA를 쓴다. libgpu의 정상 경로는
   전송 전 대기(DrawSync 상당)를 거치므로, 원시 호출 시
   CHCR 비트31(busy)을 확인하고 기다리는 처리를 넣어야 한다.

승리 장면 경로(v38 / v41 win)는 정상 동작하므로 **분기를 분리해
그대로 둔다**. 영상 컨텍스트($t9 = 1 컷신 / 2 엔딩)에서만 새 경로를 탄다.

## 29. v42 구현 (2026-08-02) — 영상용 직접 전송 경로

`workspace/scripts/build_subtitle_v42.py`, 산출물 `build/subtitle_v42`.

### 29.1 동작 원리

렌더러는 프리미티브를 `0x801216DC`에 만들고 `AddPrim`으로 `[ctx+0]`에
**앞쪽 삽입**한다. 따라서 렌더 직전에 `[ctx+0]`을 종단자로 만들어 두면,
렌더 후 `[ctx+0]`이 곧 **완전히 종단된 체인의 head**가 된다.

```
ot_ready (렌더 전, $t9 != 0 일 때만)
    [ctx+0] = 0xFFFFFFFF      ; AddPrim은 하위 24비트만 링크로 쓰므로 종단됨
  ... 기존 line_loop (렌더러 호출) ...
ot_done (렌더 후, $t9 != 0 일 때만)
    $a0 = [ctx+0]
    bltz $a0 -> skip          ; 아무것도 안 그려졌으면 0xFFFFFFFF(음수)
    CHCR bit24(busy) 검사 -> busy면 skip
    jal 0x80069570            ; 체인 DMA 즉시 전송
```

승리 경로($t9 == 0)는 두 블록을 모두 건너뛰므로 **완전히 무변경**이다.

### 29.2 안전장치

- **체인 종단**: 사후에 꼬리를 찾아 고치는 대신 사전에 종단자를 심는
  방식이라 순회가 필요 없다.
- **head 유효성**: `bltz` 한 방으로 검사한다. 유효 프리미티브 주소는
  24비트(양수)이고 미기록 시에는 `0xFFFFFFFF`(음수)다.
- **DMA 경합**: CHCR busy면 **대기하지 않고 그 프레임을 건너뛴다.**
  대기 루프는 프리징 위험이 있으므로 채택하지 않았다. 최악의 경우
  자막 한 프레임이 빠질 뿐이다.

### 29.3 공간 확보

동굴은 확장 불가다. `0x80011D85` 바로 뒤에 libcd 문자열·포인터
데이터("CD_sync", "CD_ready" 등)가 붙어 있어 여유는 3바이트뿐이다.

**추가 케이브 후보도 전부 기각**했다. 참조 0인 영역은 `0x80083982`
(98바이트) 하나뿐이었는데, 경계를 확인하니 코드 패딩이 아니라
**12바이트 레코드 데이터 테이블 안의 0 항목들**이었다(앞뒤로
`70 e5 ff ff | 00 00 00 00 | 20 35 00 00` 형태가 반복). 여기에 코드를
넣으면 게임 데이터가 깨진다. 나머지 후보는 참조가 22~1290건이라
논외다.

그래서 **컷신 컨텍스트를 제거**해 공간을 만들었다(`--skip cut`).
컷신 스텁·디스패치·그룹 블록이 빠진다. 도입 컷신은 O05 컨테이너
재작업 전까지 어차피 동작하지 않으므로 회귀는 없다.

최종: 코드 `0x800118B4`~`0x80011CE8`, 데이터 ~`0x80011D84`,
**1232 / 1233 바이트 (여유 1바이트)**.

### 29.4 정적 검증 결과

- 후크 2곳만 기록됨: `0x8003A88C`(승리), `0x80043204`(엔딩).
  컷신 후크 `0x8003B334`는 **미패치**(스텁이 없으므로 필수).
- `assert_no_load_delay_hazard` 통과.
- 빌드 산출 EXE를 역어셈블해 지연 슬롯 실물 확인:
  `bltz`/`bnez`/`jal` 모두 keystone이 nop을 채우고 다음 명령을 뒤로
  밀었다. 엔딩 스텁의 `jal 0x80078360` → nop → `j 0x80043210`도 정상.
- 파일 재배치 10건 LBA/크기 일치, EXE 라운드트립 통과.
- `output_sha256=696C49AE66D2A1ECDC906403A3B87AC0DC4981BF1732CC109BE3150CC654C106`

### 29.5 남은 것

**런타임 미검증이다.** 정적 통과는 런타임 성공이 아니다(이 프로젝트의
구속 조건). DuckStation에서 클린 CUE로 부팅해

1. 전투 승리 자막이 여전히 정상인지 (회귀 확인 — 최우선)
2. 메뉴·CONTINUE 화면이 정상인지
3. 갤러리에서 엔딩 재생 시 자막이 나오는지

를 확인해야 한다. 특히 (1)이 깨지면 즉시 되돌리고 원인을 봐야 한다.

## 30. v42 1차 런타임 결과와 수정 (2026-08-02)

### 30.1 관측

| 항목 | 결과 |
|---|---|
| 전투·메뉴 등 기존 기능 | **정상 (회귀 없음)** |
| 엔딩 재생 중 자막 | 안 나옴 |
| 엔딩 종료 후 | 선택 화면 대신 **엔딩 첫 대사가 화면에 고착**. 선택 효과음은 정상 |

### 30.2 원인 — 29절 압축 과정에서 넣은 버그

동굴 23바이트를 줄이려고 종단자 적재를 `lui/ori`(2워드)에서
`addiu $t4, $zero, -1`(1워드)로 바꾼 것이 원인이었다.

`AddPrim`은 OT 엔트리의 **상위 바이트를 보존**하고 하위 24비트만
교체한다.

```
AddPrim(ot, p):
  p->tag = (p->tag & 0xFF000000) | (*ot & 0x00FFFFFF)
  *ot    = (*ot & 0xFF000000) | ((u32)p & 0x00FFFFFF)
```

`*ot = 0xFFFFFFFF`로 두면 렌더 후 `*ot = 0xFF000000 | prim`이 된다.
결과는 두 가지다.

1. `$a0`가 **음수**가 되어 `bltz $a0, ot_done`이 항상 성립 →
   `jal 0x80069570`이 **한 번도 실행되지 않음** (재생 중 자막 없음).
2. OT 엔트리에 워드 카운트 `0xFF`가 남는다. DMA 체인 노드는
   `(count<<24) | next` 형식이므로, 게임이 나중에 정상 렌더로 돌아와
   그 엔트리를 통과할 때 **255워드의 쓰레기를 GPU로 밀어넣는다.**
   GPU만 죽고 CPU는 살아 있어 **효과음은 나는데 화면은 고착**되고,
   그때 우리 프리미티브가 함께 그려져 첫 대사가 보인 것이다.

관측 3가지가 이 하나로 전부 설명된다.

### 30.3 수정

종단자를 **`0x00FF0000`** (`lui $t4, 0xFF` 한 워드)으로 바꿨다.

- 상위 바이트 = 0 → OT 엔트리의 워드 카운트가 정상(0)
- 하위 24비트의 비트23이 세트 → DMA 체인은 정상 종단
- 워드 수는 그대로라 동굴 예산도 유지

`bltz` 가드는 제거하고 **빌드 타임 검증**(`validate_records`)으로
옮겼다. `sltiu $a0, 0x200000`은 16비트 즉시값을 넘어 어셈블러가
확장해 버려 동굴에 들어가지 않는다. 출하 데이터는 고정이므로
빌드 시점 검사가 오히려 더 강한 보증이다 — 텍스트가 없는 레코드가
있으면 빌드가 실패한다.

### 30.4 산출물

`build/subtitle_v42b` — 동굴 1224/1233 (**여유 9바이트**),
`output_sha256=7D07AEC8F0298085CC789FB73C69692D45A108E4B6C4C3BA83275659AECF9E84`

역어셈블 확인:
```
PRE  0x80011B1C: lui $t4, 0xff ; sw $t4, ($t7)
POST 0x80011BA0: lw $a0, ($t7)          ; 체인 head
     0x80011BB8: and $t5, $t5, $t4      ; CHCR busy
     0x80011BC4: jal 0x80069570
```

여전히 런타임 미검증이다. 확인 순서는 29.5절과 동일하되,
**엔딩 종료 후 갤러리 화면이 정상 복귀하는지**를 반드시 함께 본다.

## 31. v42b 런타임 결과 (2026-08-02) — 전송은 성공, 드로잉 영역이 문제

### 31.1 관측

| 항목 | v42 (1차) | v42b (종단자 수정) |
|---|---|---|
| 재생 중 자막 | 없음 | 없음 |
| 재생 종료 후 화면 | **첫 대사** 고착 | **후반부 대사** 고착 |
| 전투·메뉴 | 정상 | 정상 |

### 31.2 해석 — 30절 수정은 유효했다

고착되는 문구가 **첫 대사 → 후반부 대사**로 바뀐 것이 결정적이다.

- v42: 첫 전송에서 워드 카운트 `0xFF` 때문에 GPU가 죽어, 그 시점의
  프리미티브(첫 대사)가 그대로 남았다.
- v42b: 재생 내내 전송이 계속 성공했고, **마지막으로 그린** 대사가
  남았다. 즉 `jal 0x80069570`이 매 프레임 정상 실행되고 GPU도 살아 있다.

따라서 30절의 종단자 수정은 목적을 달성했다. 남은 것은 **어디에
그리는가**다.

### 31.3 남은 원인

DMA 체인 전송은 GPU의 **현재 드로잉 영역**에 그린다. 영상 재생 중
그 영역은 게임의 통상 백버퍼이고, 영상은 별도의 VRAM 영역을
표시한다. 그래서 재생 중에는 보이지 않다가, 영상이 끝나고 게임이
통상 표시로 복귀하면서 그 버퍼가 화면에 나와 **누적된 마지막 대사**가
보인다.

즉 자막이 영상 위에 뜨려면 **전송 직전에 드로잉 영역을 영상이
표시 중인 버퍼로 맞춰야 한다**. 훅 위치를 옮기는 것으로는 해결되지
않는다(드로잉 영역은 시점이 아니라 GPU 상태다).

### 31.4 다음 착수점

1. **영상의 표시 영역 실측.** 게임의 드로잉 환경 구조체는
   `0x80121BBC`(12바이트 스트라이드, `PutDrawEnv` 상당
   `0x80068330`에 `a0 = 0x80121BBC + 12*db`로 전달)와 `0x80121BA4`가
   후보다(`0x8003C384` / `0x8003C3F8` 참조). 엔딩 재생 중과 통상
   플레이 중 이 구조체들을 `poll_ending_state.py`로 비교해, 영상이
   어느 좌표를 표시하는지 확정한다.
2. 확정되면 체인 앞에 드로잉 영역/오프셋 프리미티브
   (GP0 `0xE3`/`0xE4`/`0xE5`)를 붙여 전송한다.

**제약**: 동굴 여유가 9바이트뿐이다. 드로잉 환경 프리미티브를 붙이려면
데이터(프리미티브 워드)와 코드가 더 필요하므로, 공간을 추가로
회수하거나 데이터 배치를 재설계해야 한다. 컷신 컨텍스트는 이미
제거된 상태다.

## 32. 미국판 대조 (2026-08-02) — 영상 자막 출력 방식

`extracted/SCUS_941.80` 추출 (LBA 24, 595968바이트, text 0x80010000+0x91000).
원칙은 유지한다: **미국판 주소를 그대로 쓰지 않고 메커니즘만 참고**하고
일본판에서 재증명한다.

### 32.1 libgpu는 동일, 오프셋 고정

GPU 드로잉 환경 명령(GP0 E1/E3/E4/E5/E6) 생성 지점의 개수가
**7/2/2/2/5로 양쪽 완전 일치**하고 주소가 일정하게 어긋난다.

```
JP 0x80068980  =  USA 0x80067168      델타 = +0x1818
```

즉 라이브러리 코드는 동일하고 **JP = USA + 0x1818**로 매핑된다.
차이는 게임 코드에 있다.

### 32.2 텍스트 렌더러 호출자 수가 다르다

렌더러 프롤로그(`sw $a0,($sp)` … `addiu $sp,$sp,-0x28`) 패턴으로 찾았다.

| | 렌더러 | 호출자 수 |
|---|---|---|
| JP | `0x80038B80` | **10** (전부 `0x80039xxx`) |
| USA | `0x80036EF4` | **19** |

미국판에만 있는 군집이 **`0x8003C890` / `0x8003C8CC` / `0x8003C8FC`**
— 셋 다 같은 함수 `0x8003C868` 안에 있고, 이 함수는 렌더러를 3회
호출하는 것 외에 **다른 호출이 전혀 없다**. 호출자는 `0x8003C7A8`
한 곳뿐이다.

### 32.3 시사점 — 드로잉 환경을 따로 설정하지 않는다

`0x8003C868`은 드로잉 환경을 건드리지 않고 그냥 렌더러만 부른다.
즉 **미국판은 영상 자막을 위해 특별한 draw env를 세팅하지 않는다.**

그렇다면 31절의 "드로잉 영역을 맞춰야 한다"는 결론은 방향이 다르다.
미국판이 아무것도 안 하고도 영상 위에 자막이 나온다는 것은, 그
호출 지점이 **영상 프레임의 드로잉 환경이 이미 유효한 시점**이라는
뜻이다. 우리 훅(`0x80043204`, 메인 루프에서 상태 핸들러 반환 직후)은
그 시점이 아니다.

### 32.4 다음 착수점

1. `0x8003C7A8`(및 그 상위)를 따라가 **미국판이 어느 루프에서
   자막을 그리는지** 확정한다. 영상 디코드 루프 내부일 가능성이 높다.
2. 그 지점의 일본판 대응 위치를 찾는다. 게임 코드 델타는 라이브러리
   델타(+0x1818)와 다를 수 있으므로, 함수 시그니처 패턴 매칭으로
   재증명한다(주소 직접 이식 금지).
3. 훅을 그 지점으로 옮긴다. 드로잉 환경 프리미티브를 추가할 필요가
   없어지므로 **동굴 9바이트 제약도 해소**될 가능성이 크다.

### 32.5 미국판 자막 호출 사슬 (추적 완료)

```
0x80036EF4  텍스트 렌더러
   ^ 3회
0x8003C868  렌더러만 3회 호출, 그 외 아무 것도 안 함 (draw env 미설정)
   ^
0x8003C5A8  자막 그리기 진입점 — 호출자 4곳
   ^
   +- 0x80038DA4 (fn 0x80038AC8)  <- 0x800463C8 (fn 0x800463A0, jal 호출자 0 = 테이블 디스패치)
   +- 0x8003989C (fn 0x80039180)  <- 0x8003914C
   +- 0x80045700 (fn 0x80045314)  <- **jal 호출자 0 = 테이블 디스패치 상태 핸들러**
   +- 0x80064B00 (fn 0x800649F0)  <- 0x80047F9C
```

**핵심**: 자막을 그리는 지점들이 모두 **상태 핸들러 내부**다.
특히 `0x80045314`는 jal 호출자가 없어 상태 테이블로 디스패치되는
핸들러이며, 그 안에서 `0x80045700`으로 자막을 그린다.

일본판의 우리 훅은 메인 루프에서 **상태 핸들러가 반환한 뒤**
(`0x80043204`) 실행된다. 미국판은 **핸들러 안에서** 그린다.
이것이 31절에서 관측한 "영상 위에는 안 보이고 끝난 뒤에 보인다"의
직접적 원인으로 보인다 — 핸들러 안에서는 영상 프레임의 드로잉
환경이 살아 있고, 반환 후에는 아니다.

참고: 라이브러리 델타 +0x1818은 **전 구간에 적용되지 않는다.**
JP `0x80070F38`/`0x80070B9C`에 대응하는 USA 주소(-0x1818)에는 호출자가
없다. 델타는 32.1절의 draw env 군집에서만 확인된 것이므로,
**주소 이식 금지 원칙을 그대로 지켜 패턴 매칭으로 재증명해야 한다.**

### 32.6 다음 착수점 (갱신)

일본판 엔딩 상태 핸들러는 **state 50 / `0x8004A2C0`** 로 이미 실측
확정돼 있다(26.1절). 미국판 `0x80045700`에 해당하는 지점을 이 핸들러
안에서 찾아 훅을 옮긴다. 재생 분기는 `0x8004A614: j 0x8004A780` →
`jal 0x8003F60C` 경로이므로, `0x8004A780` 전후가 1차 후보다.

성공하면 드로잉 환경 프리미티브가 불필요해져 동굴 9바이트 제약도
함께 풀린다.

### 32.7 32.3/32.6절 정정 — 훅 이동만으로는 해결되지 않는다

두 핸들러의 jal 목록을 대조한 결과, **32.3절의 추론은 성립하지 않는다.**

일본판 `0x8004A2C0`의 재생 분기는 `0x8004A614: j 0x8004A780` →
`0x8004A780: jal 0x8003F60C` → 에필로그(`0x8004A788`)로 끝난다.
즉 핸들러 내부의 `0x8004A788`과 메인 루프의 현재 훅 `0x80043204`
사이에는 **레지스터 복원과 `jr $ra`밖에 없고 GPU를 건드리는 코드가
없다.** 두 지점의 드로잉 환경은 동일하므로 훅을 옮겨도 변화가 없다.

또한 두 핸들러는 대응 함수가 아니다. USA `0x80045314`는 jal이 34개인
큰 함수로 자막 호출(`0x80045700`)이 중간에 있고 뒤로도 계속 그리는
반면, JP `0x8004A2C0`은 jal 20개이고 재생 분기가 곧바로 끝난다.
**구조가 다르므로 위치 대응으로 이식할 수 없다.**

### 32.8 다시 세운 가설

미국판이 영상 위에 자막을 그릴 수 있는 이유는 호출 "시점"이 아니라
**영상을 화면에 올리는 방식 자체가 다르기 때문**일 가능성이 크다.
미국판이 영상 프레임을 OT 경유 텍스처 프리미티브로 그린다면
드로잉 환경이 항상 유효하고, 자막도 같은 OT에 얹으면 그만이다.
일본판은 27절에서 확인했듯 재생 중 OT가 아예 비어 있다.

### 32.9 다음 착수점 (재갱신)

추론을 더 쌓지 말고 **드로잉/표시 영역을 실측**한다.

1. 게임의 DRAWENV/DISPENV 구조체 후보 `0x80121BBC`, `0x80121BA4`
   (12바이트 스트라이드, `0x80068330`에 `a0 = base + 12*db`로 전달)를
   `poll_ending_state.py`에 추가한다.
2. 통상 플레이 중과 엔딩 재생 중의 값을 비교해, 영상이 표시하는
   VRAM 좌표와 우리가 그리는 드로잉 영역이 실제로 다른지 확정한다.
3. 다르면 전송 직전에 드로잉 영역을 맞추고(GP0 E3/E4/E5),
   같으면 원인은 다른 데 있으므로 가설을 다시 세운다.

이 측정 전에는 v43을 만들지 않는다. 근거 없는 빌드는 이번 세션에서
이미 두 번(29절 압축 버그, 32.3절 오추론) 비용을 치렀다.

### 32.10 DRAWENV 측정 실패 — 주소 추정이 틀렸다

`work/analysis/drawenv_during_ending.json`. `0x80121BA4` / `0x80121BBC`는
**24바이트 전부 0**이었고 상태가 바뀌어도 변하지 않았다. 측정은 질문에
답하지 못했다.

원인은 32.9절의 주소 추정 오류다. `0x8003C384` 근방을 다시 읽으면

```
0x8003C3A0: jal 0x80068330
0x8003C3A4: addu $a0, $a0, $s0     ; 0x80121BBC + db*12
0x8003C3C8: jal 0x8006A368         ; AddPrim
0x8003C3CC: addu $a1, $a1, $s0     ; 같은 주소를 프리미티브로 전달
```

같은 주소가 **AddPrim의 프리미티브 인자로도** 쓰인다. 즉
`0x80121BBC`는 DRAWENV가 아니라 12바이트 프리미티브 버퍼이고,
`0x80068330`은 PutDrawEnv가 아니라 프리미티브 설정 함수다.
해당 경로가 이번 세션에 실행되지 않아 0으로 남아 있었다.

부수 확인: `ot_depth0`는 상태마다 다르다.

| state | 핸들러 | ot_depth0 |
|---|---|---|
| 8 | - | `0x00104940` |
| 49 | `0x8004A138` | `0x0008A56C` |
| 50 | `0x8004A2C0` | `0x00121BD4` |

27절에서 엔딩 재생 중 관측한 `0x0008A56C`가 **state 49** 값과 일치한다.

### 32.11 DRAWENV를 제대로 찾는 방법 (다음 착수점)

추정하지 말고 libgpu에서 역으로 찾는다. 32.1절에서 GP0 드로잉 영역
명령 생성 지점이 확정돼 있다.

```
JP  E3(area TL) 0x80068A6C / 0x80068EA4
    E4(area BR) 0x80068B38 / 0x80068F54
    E5(offset)  0x80068B84 / 0x80068EA8
```

`0x80068EA4`/`0x80068EA8`은 서로 4바이트 간격이므로 같은 함수에서
E3와 E5를 연달아 쓴다 — **PutDrawEnv 본체**일 가능성이 높다.
그 함수의 시작점을 찾고 `$a0`로 전달되는 구조체가 진짜 DRAWENV다.
호출자를 역추적하면 게임이 어느 전역에 DRAWENV를 두는지 확정된다.

그 주소를 폴러에 넣어 통상 화면 vs 엔딩 재생 중을 비교하면
32.9절의 질문에 비로소 답할 수 있다.

### 32.12 드로잉 환경 확정 — 게임 구조체가 아니라 libgpu가 적용한 값을 읽는다

| 주소 | 정체 |
|---|---|
| `0x80068330` | 드로잉 영역 설정 진입점. fall-through로 `0x8006836C` → `0x800689B8`(GP0 E3/E4/E5 기록). 게임 호출자 4곳: `0x8003C3A0`, `0x8003C40C`, `0x8003C884`, `0x8003C8F0` |
| `0x80068DC8` | libgpu draw env 본체. E3(`0x80068EA4`)와 E5(`0x80068EA8`)를 연달아 쓰고, **`0x801280D8`에 env 프리미티브를 조립해 `0x80069570`으로 전송**한다. jal 호출자 0 = 간접 호출 |

`0x801280D8`은 28.3절에서 `jal 0x80069570`의 `$a0`로 확인된 바로 그
주소다(`lui $a0,0x8013 ; addiu $a0,$a0,-0x7F28`).

32.10절이 0만 읽은 이유도 이걸로 설명된다 — `0x80121BBC`를 쓰는 4개
호출자가 그 세션에 실행되지 않았을 뿐이다.

**따라서 추측할 필요가 없다.** `0x801280D8`은 libgpu가 GPU에 마지막으로
적용한 드로잉 환경 그 자체이므로, 이 24바이트를 통상 화면과 엔딩
재생 중에 비교하면 32.9절의 질문에 바로 답이 나온다.
`poll_ending_state.py`의 `DRAW_ENV_A`를 이 주소로 교체했다.

블록은 GP0 명령 워드들(E1 draw mode / E3 area TL / E4 area BR /
E5 offset / E6 mask)이 나열된 형태이므로, 각 워드의 상위 바이트로
명령을 식별하고 하위 비트에서 좌표를 읽으면 된다.

### 32.13 드로잉 환경 실측 결과 — 영역이 아니라 오프셋이 문제다

`work/analysis/drawenv_live.json`. `0x801280D8` 24바이트를 state 8 / 49 / 50에서
읽었고 **세 상태 모두 완전히 동일**했다.

```
raw: fc801208 000000e3 ffffffe4 000000e5 000000e6 400200e1
dec: (tag: 8워드, next=0x1280FC)
     areaTL(0,0)  areaBR(1023,511)  offset(0,0)  mask=0  drawmode=0x000240
```

**확정**: 드로잉 영역은 **VRAM 전체**이고 오프셋은 **(0,0)** 이다.
31절의 "영상이 드로잉 영역 밖을 표시한다"는 가설은 **기각**된다.
영역 제한으로 잘리는 것이 아니다.

**한계**: 이 블록은 상태가 바뀌어도 변하지 않았고 8워드 고정
체인 노드다. 즉 초기화 시 1회 적용되는 고정 env이지 프레임마다
갱신되는 값이 아니다. 더블버퍼 전환 자체를 이 값으로 판정할 수는 없다.

### 32.14 재정의된 원인 가설

오프셋이 `(0,0)`이라는 것은 우리 프리미티브가 화면 좌표를 **VRAM 절대
좌표로** 사용한다는 뜻이다. 자막은 y≈190이므로 항상 VRAM 원점 쪽
버퍼에 그려진다.

그런데 `db_index`(`0x800A2F3C`)는 재생 중에도 계속 교대한다(27절 실측).
영상이 표시하는 버퍼가 원점 버퍼가 아니라면, 자막은 표시되지 않는
버퍼에 누적되다가 재생 종료 후 게임이 원점 버퍼를 표시할 때 비로소
보인다 — **31절의 관측(재생 중 없음 / 종료 후 마지막 대사)과 정확히
일치한다.**

즉 문제는 드로잉 **영역**이 아니라 드로잉 **오프셋**이다.

### 32.15 다음 착수점

1. **표시 중인 버퍼의 원점을 알아낸다.** GP1(0x05) = display start를
   설정하는 libgpu 함수(PutDispEnv 상당)를 32.12절과 같은 방식으로
   찾고, 게임이 쓰는 DISPENV 전역을 확정한다.
   `0x80068DC8`가 draw env를 조립하듯, disp env를 조립하는 짝이 있을 것.
2. 확정되면 우리 체인 **맨 앞에 GP0 E5(드로잉 오프셋) 프리미티브**를
   붙여 표시 중인 버퍼 원점으로 맞춘 뒤 전송한다.
   `db_index`로 두 버퍼 중 하나를 고르면 된다.
3. 동굴 여유는 9바이트뿐이므로, E5 프리미티브(태그+명령 = 8바이트
   데이터)와 조립 코드를 넣을 공간을 함께 계획해야 한다.

### 32.16 원인 확정 — 드로잉 오프셋과 표시 버퍼 불일치

**PutDispEnv = `0x80067E20`** (GP1 05 표시시작 / 06 수평 / 07 수직 /
08 모드를 모두 이 함수가 기록). 호출자는 2곳이고 그 중 하나가
**메인 루프 `0x80043260`** 이다.

```
0x80043260: jal   0x80067E20
0x80043264: addiu $a0, $s1, 0x5C      ; DISPENV = $s1 + 0x5C
```

메인 루프 앞부분에서 `$s0 = $s1 + 0x70`이 렌더 컨텍스트로 쓰인다
(`0x800431A4`, `sw $s0, 0x58C($gp)`). 실측 컨텍스트 `0x8012DBEC`가
`0x8012DB7C + 0x70`과 일치하므로

> **DISPENV = [0x800A3010] − 0x14**

이미 쓰고 있는 전역 하나에서 유도된다. 새 전역이 필요 없다.

**실측 (DuckStation, state 50)**

```
context = 0x8012DBEC   db = 0
DISPENV @0x8012DBD8 = 0000 f000 8002 f000 ...
   표시 영역: x=0  y=240  w=640  h=240
```

**표시 중인 버퍼는 VRAM (0,240)인데 드로잉 오프셋은 (0,0)이다**
(32.13절 실측). 자막은 y≈190이므로 원점 버퍼에 그려지고 화면은
240~480을 보여준다. 재생 중 안 보이다가 나중에 게임이 원점 버퍼를
표시할 때 나타나는 31절의 관측이 완전히 설명된다.

### 32.17 수정 방안 (v43)

전송 체인 **맨 앞에 GP0 E5(드로잉 오프셋) 프리미티브**를 붙이고,
값은 DISPENV에서 읽은 표시 좌표로 채운다.

```
offset_word = 0xE5000000 | (y << 11) | x        ; x,y = [ctx-0x14] 의 u16 2개
```

- DISPENV에서 읽으므로 더블버퍼 전환을 자동으로 따라간다.
- 체인 노드 형식: `tag = (1<<24) | next` + 명령 워드 1개 = **8바이트**.
  우리 체인의 head 앞에 끼우면 되고, 텍스트 프리미티브들은 그대로 둔다.
- 그린 뒤 오프셋을 되돌릴 필요는 없다. 게임은 매 프레임 자체 draw env를
  다시 적용하며, 승리 경로($t9 == 0)는 이 블록을 타지 않는다.
  다만 첫 빌드에서는 **승리 자막·메뉴 회귀를 반드시 재확인**한다.

**공간**: 동굴 여유 9바이트. E5 노드용 8바이트 데이터와 조립 코드
(대략 8~10워드)가 필요하므로 **추가 회수가 필수**다. 후보는
`restore_punct`/`restore_letters` 병합, 폭 백업 데이터 축소 등.
정 안 되면 데이터 배치를 재설계한다.

## 33. v43 구현 (2026-08-02) — 표시 버퍼로 Y 이동

`build/subtitle_v43`,
`output_sha256=C4A0DA4A6E5808C71AC2B8F19C9968F0ECA421CBB4419E82455893DCC12C7244`

### 33.1 32.17절 설계 변경 — E5 프리미티브를 쓰지 않는다

GP0 E5(드로잉 오프셋) 프리미티브는 체인 노드 8바이트와 조립 코드가
필요해 동굴에 들어가지 않는다. 대신 **자막 Y 좌표에 DISPENV.y를 더한다.**
드로잉 영역이 VRAM 전체(1023,511)이므로 y=430도 유효하다.
데이터가 전혀 필요 없고 코드도 2워드면 된다.

```
PRE  (렌더 직전)
  move $s7, $zero              ; 승리 경로는 오프셋 0
  beq  $t9, $zero, ot_ready
  lui  $t7, 0x800A
  lw   $t7, 0x3010($t7)        ; 컨텍스트
  lui  $t5, 0xFF
  lhu  $s7, -0x12($t7)         ; DISPENV.y  (ctx-0x14+2)
  sw   $t5, 0($t7)             ; 체인 종단자
ot_ready:

line_loop
  addu $a2, $a2, $s7           ; 자막 Y += 표시 버퍼 y
```

`$s7`은 프레임 값이지만 `record_hit` 이후로는 쓰이지 않으므로 재사용했다
(스택 슬롯과 `sw $zero` 초기화가 불필요해져 2워드 절약).

### 33.2 추가 공간 확보

`line_loop`에서 `$a3`와 `$t5`가 모두 15로 중복 설정되고 있었다.
`ori $t5, $zero, 15` / `sw $t5, 0x10($sp)`를 `sw $a3, 0x10($sp)`로
합쳐 1워드 회수했다. 최종 **1232 / 1233 (여유 1바이트)**.

### 33.3 정적 검증

역어셈블 확인 (`0x80011B0C`~, `0x80011B58`) — 지연 슬롯 정상,
`lw $t7` → `lui $t5`(필러) → `lhu $s7`, `lhu $s7` → `sw $t5`(필러) 순서로
로드 지연 위험 없음. 후크는 승리/엔딩 2곳만.

### 33.4 확인 필요 (런타임)

1. **전투 승리 자막 회귀** — `$s7` 재사용과 `$a3` 통합이 승리 경로에
   영향을 주지 않았는지. 최우선.
2. 메뉴·CONTINUE 화면.
3. **엔딩 재생 중 자막이 영상 위에 뜨는지.**
4. 엔딩 종료 후 갤러리 정상 복귀.

**남은 위험**: DISPENV.y를 실측한 것은 db=0인 순간 1회뿐이다(y=240).
더블버퍼가 교대하면 y가 0/240을 오갈 수 있고, 그 경우 매 프레임
DISPENV에서 읽으므로 자동으로 따라가지만, 만약 자막이 **깜빡이거나
절반만 보이면** 표시 버퍼와 그리기 시점이 어긋난 것이므로
`db_index`와 DISPENV.y의 관계를 다시 실측해야 한다.

### 33.5 v43 런타임 결과 — 실패, 그리고 32.16절 전제 오류

증상은 v42b와 **완전히 동일**하다. 재생 중 자막 없음, 엔딩을 중간에
종료해도 그 뒤에 자막이 표시된다.

**32.16절의 전제가 틀렸다.** "드로잉 오프셋 = (0,0)"의 근거였던
`0x801280D8` 블록은 32.13절에서 이미 "상태가 바뀌어도 변하지 않는
8워드 고정 체인 노드 = 초기화 1회용"이라고 스스로 기록해 두었는데,
32.16에서 그것을 살아있는 per-frame 오프셋인 양 사용했다.

논리적 모순도 있었다. 게임이 정말 항상 (0,0)에 그리면서 y=240을
표시한다면 **메뉴와 승리 자막도 보이지 않아야 한다.** 실제로는 정상이다.

또한 DISPENV.y=240을 읽은 시점은 `frame=2064`, 즉 **엔딩이 끝난 뒤**였다.
재생 중 값이 아니다.

### 33.6 다음 착수점 — 재생 "중" 값을 잡는다

지금까지의 측정은 전부 재생이 끝난 뒤이거나 정지 화면이었다.
`--only-changes`가 프레임 진행 행을 접어버려 재생 구간이 비었다.

1. `poll_ending_state.py`를 **`--only-changes` 없이** 돌려
   `ending_frame`이 증가하는 구간의 DISPENV(ctx-0x14, 20바이트)와
   `db_index`를 함께 남긴다.
2. 통상 플레이 중 DISPENV와 비교한다.
3. 재생 중 DISPENV가 통상과 다르면 그 좌표가 영상 버퍼이고, 자막을
   그 버퍼로 보내야 한다. 같으면 표시 버퍼는 원인이 아니므로
   "영상이 매 프레임 화면 전체를 덮어쓴다"(우리가 그린 뒤 영상이
   다시 덮는 순서 문제) 쪽으로 가설을 옮긴다.

v43은 **되돌릴 필요가 없다**(승리 경로 무영향, 여유 1바이트).
다만 Y 이동 코드는 근거가 사라졌으므로, 위 실측 결과에 따라
값을 바꾸거나 제거한다.

## 34. 재생 중 DISPENV 실측 (2026-08-02) — 원인 완전 확정

`work/analysis/dispenv_during_playback.json`, 429샘플.

### 34.1 실측값

| 구분 | DISPENV (표시 영역) |
|---|---|
| 통상 (state 8/49/50, 재생 아님) | `(0,0) 640x240` / `(0,240) 640x240` |

  **DISPENV만이 유효한 출처다.**
- `context`도 재생 내내 `0x80131C70`으로 고정.

### 34.2 v43 실패 원인

v43은 **Y만** DISPENV.y로 이동시켰다. `(0,0)` 버퍼일 때는 맞지만
`(480,240)` 버퍼일 때는 **X가 480만큼 어긋나** 화면 밖으로 나간다.
프레임마다 버퍼가 바뀌므로 결과적으로 한 프레임도 보이지 않는다.

**X와 Y를 모두 이동시켜야 한다.**

### 34.3 다음 착수점 — 공간이 관건

필요한 것: 자막 좌표에 `DISPENV.x`, `DISPENV.y`를 모두 더한다.

- 방법 A: `$s7 = (x << 16) | y`로 묶고 `line_loop`에서 풀어 쓴다.
  PRE +3워드, line_loop +3워드 = **약 24바이트 추가**.
- 방법 B: GP0 E5(드로잉 오프셋) 프리미티브를 체인 앞에 붙인다.
  데이터 8바이트 + 조립 코드. Y 이동 코드(3워드)는 제거된다.

현재 동굴 여유는 **1바이트**다. 어느 쪽이든 20바이트 이상 회수해야
한다. 회수 후보:

- `restore_punct`/`restore_letters` 병합 (~16워드 중 일부)
- `width_backup` 데이터 36바이트 축소 또는 폭 패치 방식 변경
- 데이터 배치 재설계

**주의**: `--skip cut`으로 컷신은 이미 제거된 상태이므로 그쪽에서
더 회수할 것은 없다.

## 35. v44 결과 (2026-08-02) — 좌표는 원인이 아니었다

`build/subtitle_v44` (동굴 1228/1233, 여유 5바이트,
`sha256=E0FF4FF506210774FF195974F04A412CC47683567A870A24C8D849892CD00E0D`).
X·Y를 모두 DISPENV로 이동시켰다.

**결과**: 스토리 모드 정상(회귀 없음). 그러나 엔딩 자막은 **여전히
재생 중 안 보이고 종료 후에 표시**된다. 중간 취소 시 자막만 따로 뜬다.

### 35.1 좌표 가설 기각

34절 실측대로 X·Y를 모두 맞췄는데도 증상이 동일하다.
따라서 **표시 버퍼 좌표는 원인이 아니다.** 32.16 이후 두 번의 빌드
(v43 Y만, v44 X+Y)로 이 축은 소진됐다.

### 35.2 남은 가설 — 덮어쓰기 순서

`0x8003F60C`(영상 스텝)는 MDEC 디코드 결과를 VRAM으로 **DMA 전송**한다.
이 전송은 비동기이므로 함수가 반환한 뒤 — 즉 우리 훅
`0x80043204`가 도는 시점에도 — 진행 중일 수 있다. 우리가 자막을
그려도 곧이어 영상 DMA가 같은 영역을 덮어쓴다.

이 가설은 관측 전부와 일치한다.

- 재생 중: 매 프레임 덮여서 보이지 않음
- 재생 종료: 덮어쓰는 주체가 사라져 마지막 자막이 남음
- 중간 취소: 동일

또한 우리 POST는 CHCR busy면 전송을 건너뛴다. 영상 DMA가 상시
바쁘면 상당수 프레임에서 전송 자체가 스킵되고 있을 수도 있다.

### 35.3 다음 착수점

1. **훅이 실제로 몇 번 전송하는지 계측한다.** busy 스킵률을 모른다.
   `0x80011BC4`(v44의 `jal 0x80069570`)에 짧게 중단점을 걸어 재생 중
   히트 수를 세고, 프레임 수와 비교한다. 히트가 거의 없으면
   busy 스킵이 주원인이므로 대기 방식을 재검토한다.
2. **덮어쓰기라면 훅을 영상 DMA 이후로 옮겨야 한다.** 후보는
   VSync 대기(`0x80078360`) **직후**, 즉 `0x80043210` 이후 지점.
   현재 훅은 VSync **직전**이다. 한 프레임 늦게 그리는 셈이지만
   영상 전송이 끝난 뒤가 되므로 덮이지 않는다.
   메인 루프는 `0x80043208: jal 0x80078360` → `0x80043210: slti` →
   `0x8004321C: jal 0x80066D00` → `0x80043224: j 0x80043208` 루프이므로,
   이 대기 루프 안쪽이 후보다.

**주의**: 두 방향 모두 실측 없이 빌드하지 않는다. 32.16(고정 env를
live로 오인)과 33.5의 실패가 모두 미실측 전제에서 나왔다.

## 36. 전송 히트 계측 (2026-08-02) — busy 게이트가 전부 막고 있었다

`work/analysis/v44_send_hits.json`. v44의 전송 호출 `0x80011BD4`에
중단점을 걸고 엔딩 한 편을 재생했다.

> **hits = 0.** 전체 재생 동안 `jal 0x80069570`이 한 번도 실행되지 않았다.

렌더링 자체는 동작한다(재생 종료 후 자막이 표시됨). 따라서
`items_done`까지는 도달하며, **내가 안전장치로 넣은 CHCR busy 검사가
매 프레임 걸려 전송을 전부 막고 있었다.**

이것은 진작 확인했어야 했다. 게임 자신도 `0x80069570`을 busy 검사 없이
호출한다(PutDrawEnv 경로 `0x80069000`). 원본에 없는 게이트를 추가해
놓고 그 부작용을 좌표 쪽에서 찾고 있었다. **v42b·v43·v44에서 좌표를
맞춘 시도들은 전송이 0인 상태에서 이뤄져 애초에 검증이 불가능했다.**

DuckStation의 GDB 스텁은 메인 RAM만 매핑하므로 `0x1F8010A8`을 읽어
비트값을 확인할 수는 없었다(E00).

### 36.1 v45 — busy 게이트 제거

`build/subtitle_v45`, 동굴 여유 **33바이트**(게이트 제거로 20바이트 회수),
`sha256=50D49C71D3F7159791C2FE9642E052900BF8054A3BB6839A03261D41F6E9346D`

```
beq $t9, $zero, ot_done
lui $t7, 0x800A
lw  $t7, 0x3010($t7)
nop
lw  $a0, 0($t7)
nop
jal 0x80069570
ot_done:
```

**결과**: 증상 동일. 재생 중 자막 없음, 중간 취소 시 해당 부분 자막만 표시.
프리징·화면 깨짐은 없었다(busy 게이트 제거의 부작용은 관측되지 않음).

### 36.2 다음 착수점 — 먼저 전송 여부부터 재계측

v45에서 전송이 **실제로 일어나는지** 아직 확인하지 않았다.
추정하지 말고 같은 방법으로 센다.

```
python workspace/scripts/trace_movie_frame_counter.py \
  --address <v45의 jal 0x80069570 주소> --max-hits 400 --timeout 120 \
  --output work/analysis/v45_send_hits.json
```

- **여전히 0** → `items_done`에 도달하지 못하는 것. POST 진입 전
  (`beq $t9, $zero`) 또는 그 이전 경로를 다시 봐야 한다.
- **0이 아님** → 전송은 되는데 화면에 없다 = **영상이 매 프레임
  덮어쓴다.** 훅을 영상 DMA 완료 이후로 옮긴다. 현재 훅
  `0x80043204`는 VSync(`0x80043208`) **직전**이므로, 대기 루프
  (`0x80043208`~`0x80043224`) 이후로 옮기는 것이 후보다.

**교훈**: 이번 세션의 실패 3건(32.16 고정 env 오인, 33.5 Y만 이동,
35 X+Y 이동)은 모두 "전송이 되고 있다"는 미검증 전제 위에 있었다.
빌드 전에 그 전제를 먼저 계측한다.

## 37. 미국판 갤러리 검증 (2026-08-02) — 목표가 유효함을 확인

### 37.1 미국판 언락

USA 갤러리 언락 비트마스크 = **`0x800A10D8`**.
일본판(`0x800A30B8`)과 동일한 비트 추출 패턴(`srav`→`andi 1`→`sll 1`→
`srav`→`andi 1`→`or`)이 `0x80048270`·`0x800484D4`에 있고 둘 다 이
전역을 읽는다. `0x00000000` → `0xFFFFFFFF` 기록으로 언락 확인.

### 37.2 결과 — 미국판 갤러리는 자막이 나온다

영상 위에 자막이 정상 표시된다(스크린샷 확인).
따라서

- **우리가 겨냥한 대상은 유효하다.** 갤러리 재생에도 자막이 나오는 것이
  정상 동작이며, 없는 기능을 만들려던 것이 아니다.
- **원 개발사의 구현이 존재한다.** 그 경로를 찾아 방식을 이식하면 된다.

### 37.3 27절의 논리 오류 정정

27절은 "재생 중 `ot_depth0` 불변 → OT 미사용"이라고 결론지었다.
그러나 **[ctx+0]이 변하지 않는다는 것은 아무것도 AddPrim되지 않았다는
뜻이지, OT가 제출되지 않는다는 증명이 아니다.** 빈 OT를 매 프레임
제출하고 있었을 가능성이 남아 있다.

그렇다면 직접 DMA 전송(28~36절의 전체 작업 방향)은 불필요했을 수도
있고, 렌더러를 부르기만 해도 AddPrim이 OT에 걸어 그려졌을 수 있다.
**이 가정을 실측으로 확정하기 전에는 v42~v46 노선을 계속 밀지 않는다.**

### 37.4 다음 착수점

1. **미국판 갤러리 재생 경로 추적.** 갤러리 핸들러는

3. 확정 후 일본판에서 같은 지점을 패턴 매칭으로 재증명하고 훅을 옮긴다.

## 38. v47 (2026-08-02) — 영상 전용 코드 제거, 그리고 결정적 반증

### 38.1 미국판도 OT를 쓴다 (37.4 확인 완료)

```
USA 렌더러 0x80036EF4
  └ 0x80037254: jal 0x80033DBC        (프리미티브 링커)
        └ 0x80033ED8: lw  0x800A1028   ← 렌더 컨텍스트 전역
          0x80033EF0: jal 0x80068B50   ← AddPrim
```

| | 렌더러 | 링커 | 컨텍스트 | AddPrim |
|---|---|---|---|---|
| JP | `0x80038B80` | `0x80035854` | `0x800A3010` | `0x8006A368` |
| USA | `0x80036EF4` | `0x80033DBC` | `0x800A1028` | `0x80068B50` |

미국판 자막 함수 `0x8003C868`은 렌더러만 3회 호출하고 끝난다.
전송 코드도 draw env 설정도 없다. **영상 위 자막은 평범한 OT 렌더링이다.**

### 38.2 v47 — 영상 전용 코드 전부 제거

`build/subtitle_v47`, 페이로드 1120, **동굴 여유 113바이트**,
`sha256=E0B83F4EBC0B19E4F7A5FD0B2AC6452A870081B5F4BB15E7E510303C515495AD`.
직접 DMA 전송·체인 종단자·X/Y 이동·`$t9` 스필을 모두 걷어냈다.
역어셈블로 `jal 0x80069570`이 없음을 확인.

### 38.3 결과 — 아무것도 안 나온다 (지연 표시조차 사라짐)

이것이 결정적이다.

v42b~v46에서 **종료 후 자막이 보였던 원인은 직접 전송이 아니라
종단자 쓰기**였다(전송 히트는 0이었다). `[ctx+0]`에 `0x00FF0000`을 써서
OT 엔트리를 리셋해 두면 우리 프리미티브가 살아남았고, 나중에 게임이
그것을 그렸다.

v47에서 그 쓰기를 없애자 프리미티브가 **매 프레임 `ClearOTagR`에
지워진다.** 즉

> **영상 재생 중에도 OT는 살아서 매 프레임 클리어·제출된다.**

27절의 "영상 중 OT 미사용" 결론은 확실히 반증됐다.

### 38.4 확정된 원인 — OT 제출 순서

훅 `0x80043204`는 상태 핸들러가 **반환한 뒤**다. 핸들러 안에서 이미
`DrawOTag` 제출이 끝난 뒤에 프리미티브를 추가하므로 그려지지 못하고
다음 프레임 클리어에 지워진다.

승리 자막이 동작하는 이유도 같다 — 승리 훅 `0x8003A88C`는
**핸들러 내부, 제출 전**에 있다.

32.7절에서 "훅을 핸들러 안으로 옮겨도 소용없다"고 한 것은 **드로잉
환경** 기준의 판단이었다. **OT 제출 순서**는 전혀 다른 문제인데 그
구분을 하지 못했다.

### 38.5 다음 착수점

엔딩 경로에서 **OT를 제출하는 지점을 찾고 그 직전에 훅을 건다.**

- 갤러리/엔딩 핸들러는 `0x8004A2C0`(state 50). 재생 분기는
  `0x8004A614: j 0x8004A780` → `0x8004A780: jal 0x8003F60C` → 에필로그.
- 제출이 `0x8003F60C` 안에서 일어나는지, 아니면 그 이전 공통 지점에서
  일어나는지 확정해야 한다. `0x8003F60C`는 `0x80070F38`/`0x80070B9C`만
  호출하므로 그 안쪽을 봐야 한다.
- 확정되면 훅을 제출 직전으로 옮긴다. 동굴 여유가 113바이트로
  넉넉하므로 공간 제약은 없다.

**참고**: v47은 `$t9` 스필도 제거했다. 훅을 핸들러 내부로 옮기면
새 스텁이 필요하고, 그때 `$t9` 보존 여부를 다시 검토해야 한다
(36절의 실제 버그였다).

### 38.6 38.4 보류 — 제출 지점을 아직 못 찾았다

엔딩 핸들러가 부르는 두 함수를 확인했다.

- `0x8003C588` (`0x8004A490`, `0x8004A778`에서 호출) — **화면 전체를
  그리는 함수**다. 프리미티브 링커 `0x80035854`를 12회,
  드로잉 영역 설정 `0x80068330`을 2회, `AddPrim`을 2회 호출한다.
  제출 함수가 아니다.
- `0x8003F60C` — `0x80070F38` / `0x80070B9C` 두 개만 호출. 제출 없음.

**두 함수 어디에도 DrawOTag가 없다.** 제출이 상태 핸들러 밖에서
일어난다면 우리 훅 `0x80043204`도 제출 **전**이므로, 38.4의
"제출 뒤라서 지워진다"는 설명은 성립하지 않는다. 승리 훅과 엔딩 훅의
차이가 순서만으로 설명되지 않는다.

**38.4는 가설로 되돌린다.** 제출 지점을 실측/정적으로 확정하기 전에는
그 위에 빌드하지 않는다(27절→28~36절에서 같은 방식으로 여섯 빌드를
낭비했다).

### 38.7 제출 지점을 찾는 방법

DrawOTag는 libgpu 함수이며 OT head를 인자로 받는다. 28.3절에서 확인한
체인 DMA 전송 `0x80069570`이 그 실체일 가능성이 높다
(MADR=$a0, CHCR=0x01000401). 지금까지 확인된 `0x80069570` 호출자는
`0x80069000`(PutDrawEnv 경로) 하나뿐이었다.

따라서 다음 중 하나다.

1. 프레임 제출도 `0x80069570`을 쓰는데 **간접 호출**(함수 포인터)이라
   정적 스캔에 안 잡혔다.
2. 제출은 다른 libgpu 함수가 한다.

**권장 계측**: `0x80069570`에 중단점을 걸고 **통상 플레이 중** 히트
빈도를 센다. 초당 60회 수준이면 프레임 제출 경로가 맞고,
그때 `$ra`를 함께 기록하면 호출자가 바로 드러난다
(`trace_movie_frame_counter.py --register ra`가 이미 지원한다).
그다음 엔딩 재생 중 같은 계측을 반복해 비교한다.

## 39. 프레임 제출 경로 실측 (2026-08-02)

`work/analysis/submit_probe_normal.json` — `0x80069570`에 중단점,
`$ra`/`$a0` 기록, 통상 플레이 중 200히트.

```
200히트 / 12.04초 = 16.6회/초   (중단점 오버헤드로 게임이 느려진 상태)
$ra = 0x80069724  — 단일 호출자, 200회 전부
$a0 = 0x80131C1C(50) 0x80135C80(50) 0x8012DB98(50) 0x80131BFC(50)
```

컨텍스트 두 값(`0x80131C70`, `0x8012DBEC`) 기준으로 정리하면
**프레임당 2회 전송**이고 head는

| | 컨텍스트 기준 |
|---|---|
| 첫 번째 | **ctx − 0x54** |
| 두 번째 | **ctx + 0x4010** |

### 39.1 25.2절 정정 필요

25.2절은 OT를 `ctx+0 .. ctx+0x3FFC`로 보고 head를 `ctx+0x3FFC`
(= `0x80135C6C`)로 판단했다. 그러나 **실제 제출 head는 `ctx+0x4010`**,
즉 0x14만큼 다르다. OT의 실제 위치·크기가 가정과 다르다.

렌더러가 AddPrim하는 `ctx+0`이 제출되는 체인에 실제로 포함되는지
확인해야 한다. 포함되지 않는다면 승리 자막이 동작하는 이유도
다른 경로에 있는 것이고, 엔딩과의 차이도 거기서 갈린다.

### 39.2 다음 착수점

1. **`0x80069724` 주변을 역어셈블**해 제출 함수의 정체와, 두 head
   (`ctx−0x54`, `ctx+0x4010`)를 어떻게 만드는지 확인한다.
   그 함수가 프레임 제출(DrawOTag 상당)이다.
2. 거기서 **실제 OT의 base와 엔트리 수**를 확정한다.
3. 렌더러의 링크 지점(`0x80035854`의 `AddPrim(ctx + a3*4)`)이 그 OT
   범위 안인지 대조한다.
4. 그다음 엔딩 재생 중 같은 계측을 반복해 `$a0`가 통상과 같은지 본다.
   - 같으면 제출은 정상 → 우리 프리미티브가 체인에 안 걸리는 이유를 본다
   - 다르면 엔딩은 별도 OT를 쓴다 → 그쪽에 걸어야 한다

**주의**: 39.1이 맞다면 25절 이후의 OT 관련 서술 상당수가 영향을 받는다.
확정 전까지 새 빌드를 만들지 않는다.

### 39.3 제출 구조 확정 — libgpu 큐 실행기

```
0x80069610  GPU 큐 실행기 (jal 호출자: 0x800695F8 하나)
  0x800696FC: lw  GP1 포트 (-0x5A7C)
  0x80069704: lw / and 0x04000000 / beqz -> 준비 대기 폴링
  0x80069718: move $a0, $s0        ; 큐 항목의 체인 head
  0x8006971C: jalr $s3             ; ★ 간접 호출 = 0x80069570
  0x80069728: lw  -0x5A44 -> 0x8008A5BC  (큐 전역)
```

**`jalr $s3` 간접 호출**이라 정적 `jal` 스캔에서 `0x80069570`의 호출자가
`0x80069000` 하나로만 보였던 것이다(28.3절의 "호출자 1곳"은 이 때문).

따라서 `DrawOTag` 상당 함수는 **큐에 넣기만 하고**, 이 실행기가 나중에
DMA를 수행한다. 39절에서 측정한 head 두 개(`ctx−0x54`, `ctx+0x4010`)는
게임이 그 enqueue 함수에 넘긴 값이다.

### 39.4 다음 착수점 (갱신)

**게임 코드에서 enqueue를 호출하는 지점**을 찾아야 한다. 그 직전이
우리가 프리미티브를 걸어야 할 시점이다.

1. `0x8008A5BC` 및 인접 큐 전역을 참조하는 코드에서 enqueue 함수를
   식별한다(실행기 `0x80069610`이 소비하는 쪽의 반대편).
2. 그 enqueue 함수의 게임 코드 호출자를 찾고, `$a0`가
   `ctx−0x54` / `ctx+0x4010`인 곳을 특정한다.
3. 승리 장면과 엔딩에서 그 호출자가 각각 어디인지 비교한다.
   승리 훅 `0x8003A88C`는 그 호출 **전**에, 엔딩 훅 `0x80043204`는
   **후**에 있을 가능성이 높다 — 그렇다면 38.4 가설이 확증된다.
4. 확증되면 엔딩 훅을 해당 enqueue 직전으로 옮긴다.

동굴 여유는 113바이트(v47)로 넉넉하다.

### 39.5 정적 추적 한계 — enqueue는 게임 코드에서 직접 안 보인다

큐 전역(`0x8008A5A0`~`0x8008A5D8`)을 만지는 함수는 7개이고 전부
libgpu 내부다. **게임 코드에서 `jal`로 부르는 곳이 하나도 없다.**

| 함수 | 큐 참조 | 게임 코드 호출자 |
|---|---|---|
| `0x800698F0` | 23 (sw 포함) | 없음 |
| `0x80069EB4` | 14 | 없음 |
| `0x80069BDC` | 7 | 없음 |
| `0x80069E80` | 2 (sw) | 없음 |
| `0x80069610`(실행기) | 20 | 없음 |
| `0x80069D38` / `0x80068CE0` | 4 / 1 | 없음 |

간접 호출(함수 포인터)로만 도달하므로 **정적 스캔으로는 여기서 더
진행할 수 없다.** 39.4의 1~2단계는 이 방법으로는 불가능하다.

### 39.6 방향 전환 — 더 직접적인 질문부터 실측한다

enqueue 호출자를 쫓는 대신, **엔딩 재생 중 우리 프리미티브가 실제로
AddPrim되는지**를 먼저 확인한다. 이것이 더 앞단이고 더 단순하다.

**계측**: 렌더러의 프리미티브 링커 `0x80035854`에 중단점을 걸고
`$ra`와 `$a3`(OT depth)를 기록한다.

```
python workspace/scripts/trace_movie_frame_counter.py \
  --address 0x80035854 --register ra --register a3 \
  --max-hits 200 --timeout 90 \
  --output work/analysis/linker_probe_ending.json
```

- **엔딩 중 히트가 있고 `$ra`가 우리 케이브(0x800118B4~)** →
  프리미티브는 정상 등록됨. 그러면 문제는 등록 이후(제출/클리어 순서)다.
- **히트가 없음** → 엔딩에서 렌더러 자체가 호출되지 않는 것.
  그러면 훅~렌더 경로를 다시 봐야 하며, 38.3의 해석
  (종단자 때문에 살아남았다)도 재검토 대상이다.

승리 장면에서 같은 계측을 하면 `$ra`와 `$a3`의 정상값 기준을 얻는다.
두 경우를 비교하면 차이가 바로 드러난다.

## 40. 이탈 지점 확정 (2026-08-02) — 프레임 카운터가 원인

훅 내부에 단일 중단점을 걸어 이분 탐색했다. **전투를 하지 않고
엔딩만 재생**해 승리 경로가 섞이지 않게 했다.

| 탐침 | 주소 | 히트 | 판정 |
|---|---|---|---|
| 우리 렌더러 호출 | `0x80011B58` | **0** | 렌더 미도달 |
| `record_hit` | `0x80011A34` | **0** | 레코드 매칭 실패 |
| 엔딩 인덱스 로드 | `0x80011948` | **60** | 분기 진입 성공 |

즉 이탈은 **엔딩 분기 진입 이후, 레코드 매칭 이전**이다.

### 40.1 원인 — `[0x80128248]`이 증가하지 않는다

60히트 전부에서 `ending_frame = 2064` 고정이었다(이전 엔딩의 잔류
최대값). 그룹 6의 레코드 구간은 최대 `1710-1860`이므로 **프레임 2064는
모든 구간을 벗어난다.** 따라서 매칭이 항상 실패하고, `record_hit`에
도달하지 못하며, 렌더러가 호출되지 않는다.

`last_file_id = 95`(0x5F) = movie_id 8.

### 40.2 26절 판정이 틀린 이유

26절은 폴러로 `[0x80128248]`이 0→2064로 증가하는 것을 관찰하고
"프레임 정상"으로 판정했다. 그러나 그것은 **폴러가 본 값**이고,
**래퍼가 훅 시점에 읽는 값**과 같은지는 확인하지 않았다.
이 미검증 전제가 27절 이후 전체를 잘못된 방향으로 끌고 갔다
(OT 사용 여부 → 직접 DMA → 드로잉 좌표 → 제출 순서, v42~v47 여섯 빌드).

### 40.3 다음 착수점

**갤러리 재생의 올바른 프레임 소스를 찾는다.**

1. `watch_ending_counters.py`로 **재생 중** 0에서 증가하는 후보를 찾는다
   (기존에 쓰던 도구가 그대로 있다).
2. 후보를 찾으면 훅 시점의 값이 실제로 그것인지 `--register` 계측으로
   교차 확인한다 — 폴러 관찰만으로 판정하지 않는다(40.2의 교훈).
3. `END_FRAME_RAM`을 교체해 재빌드한다.

카운터만 맞으면 나머지 체인(베이스·word3·인덱스·그룹)은 이미 통과가
확인됐으므로 바로 자막이 나올 가능성이 높다.

### 40.4 현재 빌드

- `build/subtitle_v38` — 승리 자막 기준선(보존)
- `build/subtitle_v47` — 최신. 승리 경로 무회귀, 동굴 여유 113바이트.
  구조가 깨끗하므로 `END_FRAME_RAM` 상수만 바꿔 재빌드하면 된다.

### 40.5 40절 전체 무효 — 재생 중 데이터가 아니었다

**사용자가 해당 계측 동안 엔딩을 재생하지 않았음이 확인됐다.**
따라서 40절의 표와 결론은 전부 무효다.

- `0x80011948` 60히트는 **평상시(메뉴/대기)** 히트다. 엔딩 훅
  `0x80043204`는 메인 루프에 있어 상태와 무관하게 매 프레임 돌므로,
  엔딩 분기 진입은 당연한 결과다.
- `ending_frame = 2064`는 재생 중 값이 아니라 이전 엔딩의 잔류 래치다.
- 따라서 **"프레임 카운터가 증가하지 않는다"는 결론은 근거가 없다.**

`record_hit`(0히트) · 렌더러 호출(0히트) 계측도 **재생 여부가 확인되지
않았으므로** 같은 이유로 보류한다.

**절차 규칙(추가)**: 계측 결과를 해석하기 전에 **재생이 실제로
있었는지 먼저 확인한다.** 판별 가능한 신호(예: `ending_frame`이
0에서 증가하는 구간)가 데이터에 없으면 해석하지 않고 재계측한다.

## 41. 계측 방법론 문제 확인 (2026-08-02)

재생을 **확인한 상태**에서 `0x80011948` 600히트를 잡았다.

```
distinct frames: 1   min/max: 2064 2064   rising steps: 0
```

### 41.1 중단점 계측이 영상 재생을 막는다

26절에서는 **폴러(중단점 없음)** 로 같은 주소가 0→2064로 증가하고
엔딩 사이에 2064→15로 리셋되는 것을 관측했다. 두 결과의 차이는
계측 방식뿐이다.

따라서 유력한 해석은 **계측 아티팩트**다. 매 프레임 걸리는 중단점의
GDB 왕복 비용 때문에 CD/MDEC 스트리밍이 진행되지 못해 프레임
카운터가 돌지 않는다. 화면상 재생이 끝난 것처럼 보여도 실제 디코드는
일어나지 않았을 수 있다.

**결과적으로 우리 훅 지점에 중단점을 거는 방식으로는 실제 재생 중
상태를 관측할 수 없다.** 이번 세션의 `record_hit`(0히트) ·
렌더러 호출(0히트) 탐침도 같은 이유로 무효일 가능성이 높다.
40절과 40.5절의 결론은 모두 보류 상태로 둔다.

### 41.2 대안 — 래퍼가 스스로 기록하게 한다

중단점 없이 관측하려면, 래퍼가 자기가 본 값을 RAM에 남기고
**폴러로 나중에 읽는** 방식이 필요하다.

조사 전용 빌드에 한해 소량의 디버그 슬롯을 두는 것을 검토한다
(`build_forced_movie_debug.py` 선례가 있다). 예:

- `+0`: 훅 진입 횟수
- `+4`: 마지막으로 읽은 프레임 값
- `+8`: 마지막 그룹 인덱스
- `+12`: `record_hit` 도달 횟수
- `+16`: 렌더러 호출 횟수

이 5개만 있으면 이번 세션 내내 중단점으로 얻으려 했던 정보를
**게임 속도에 영향 없이** 한 번에 얻는다.

**주의**: 출하 빌드에는 넣지 않는다(사용자 상태 RAM 0 정책).
조사 전용 빌드로만 만들고, 위치는 기존 동굴 여유(113바이트) 안에서
잡아 정책 위반을 피한다.

### 41.3 다음 착수점

## 42. 계측 확정 (2026-08-02) — 프레임 소스가 유일한 결함

`build/subtitle_v47dbg` (조사 전용, 디버그 슬롯 `0x80011D54`,
동굴 여유 33바이트, `sha256=CF4B73D673F9ABBAB95C4F2B9EC885EF0E7FE11C95D12ACBE8C241CD0A555C73`).
**중단점 없이** 정상 속도로 갤러리 엔딩을 재생한 뒤 슬롯을 읽었다.

```
+0  진입 횟수      = 784
+4  마지막 프레임  = 2064      <- 고정
+8  마지막 그룹    = 8
+12 record_hit     = 0
동시 확인: [0x800A3178] = 5,  [0x80128248] = 2064
```

### 42.1 확정 사항

- **훅·베이스·word3·인덱스·그룹 공식은 전부 정상.**
  인덱스 5 → `(5-1)*2 = 8`로 그룹 공식도 검증됐다.
- **`[0x80128248]`은 갤러리 재생 중 증가하지 않는다.**
  41절에서 의심한 중단점 아티팩트는 배제됐다(이번엔 중단점이 없다).
  40절의 원래 결론이 옳았다.
- 그룹 8의 레코드 구간은 최대 `1620-1800`이므로 프레임 2064는 모든
  구간 밖이다. 그래서 `record_hit = 0`이다.

**유일한 결함은 프레임 소스 하나다.**

### 42.2 26절 관측과의 차이

26절 폴러 측정에서는 이 주소가 0→2064로 증가하고 엔딩 사이에
2064→15로 리셋되는 것이 보였다. 이번 결과와 상충한다. 가능한 설명:

- 그때 관측한 증가 구간이 갤러리 재생이 아니라 다른 경로(스토리 엔딩
  등)였다.
- 또는 그 카운터는 특정 조건에서만 돈다.

어느 쪽이든 **갤러리 재생용 프레임 소스를 새로 찾아야 한다.**

### 42.3 다음 착수점

1. `watch_ending_counters.py`(중단점 없음)로 **갤러리 엔딩 재생 중**
   0 부근에서 증가하는 32비트 전역을 탐색한다.
   기대 범위: 0 → 1800~2100, 30Hz.
2. 후보를 찾으면 `v47dbg`의 `END_FRAME_RAM`만 바꿔 재빌드하고,
   디버그 슬롯 `+4`가 증가하는지 **같은 방식으로** 확인한다
   (폴러 관찰만으로 판정하지 않는다 — 40.2의 교훈).
3. `+12 record_hit`이 0에서 벗어나면 조회 완성. 그다음 출력 확인.

### 42.4 방법론 성과

디버그 슬롯 방식은 이번 세션 내내 중단점으로 얻지 못한 정보를
한 번에 주었다. **게임 속도에 영향이 없어 관측 대상을 바꾸지 않는다.**
앞으로 재생 중 상태를 볼 때는 이 방식을 기본으로 한다.
출하 빌드에는 넣지 않는다(사용자 상태 RAM 0 정책).

## 43. 미국판 자막 모델 (2026-08-02) — 이벤트 구동, 프레임 검색 아님

### 43.1 표시 상태는 전역 2개

```
gp+0x424 = 표시할 문자열 포인터
gp+0x420 = 표시 타이머 (세터가 0으로 리셋)
```

세터 3종이 문자열 테이블에서 포인터를 꺼내 위 둘을 세팅한다.

```
0x8003C568: sw $a0, 0x424($gp) ; sw $zero, 0x420($gp)      (포인터 직접)
0x8003C54C: lw $v0, [0x80086518 + v0*4] -> 0x424($gp)      (테이블 인덱스)
0x8003C588: lw $v0, [[0x80086458 + a0*4] + a1*4] -> 0x424  (2단 테이블)
```

그리기 함수 `0x8003C5A8`은 `gp+0x420`/`gp+0x424`만 읽는다.
**f0/f1 프레임 구간을 검색하지 않는다.**

### 43.2 호출 지점

```
0x800456F0: lh   $v0, 0x5CC($gp)   ; 자막 활성 플래그
0x800456F8: beqz $v0, skip
0x80045700: jal  0x8003C5A8
0x80045704: move $a0, $zero
```

매 프레임 플래그만 보고 그린다.

### 43.3 우리 구조와의 차이

우리 래퍼는 **매 프레임 프레임값을 읽어 f0/f1 구간을 직접 검색**한다.
미국판은 **이벤트 시점에 세터를 호출**해 표시 내용을 바꾼다.

구조가 반대이므로, 프레임 카운터를 못 찾는 것이 당연할 수 있다.
42절에서 `[0x80128248]`이 갤러리 재생 중 안 도는 것도 이와 일관된다 —
그 카운터는 이 경로의 타이밍 소스가 아닐 가능성이 높다.

### 43.4 다음 착수점

**세터를 호출하는 쪽**에 타이밍 로직이 있다. 세터 3종
(`0x8003C520` 부근 / `0x8003C568` / `0x8003C578`)의 호출자를 찾고,
영상 재생 중 레코드를 어떤 기준으로 넘기는지 확인한다.

그 기준이 밝혀지면 두 갈래다.

1. 일본판에도 같은 기준값이 존재 → 우리 래퍼의 프레임 소스를 교체
2. 존재하지 않음 → 우리가 직접 타이밍을 만들어야 한다.
   훅이 매 프레임 도는 것은 확인됐으므로(42절, 진입 784회),
   **자체 프레임 카운터를 조사용 슬롯처럼 케이브에 두는 방식**도
   가능하다. 다만 출하 빌드의 사용자 상태 RAM 0 정책과 충돌하므로
   승인이 필요하다.

`[0x800A3178]` 인덱스, 그룹 공식(`(n-1)*2`), 버퍼 베이스, word3 모두 통과.

27절의 "OT 미사용"은 렌더러가 호출되지 않던 상태를 본 것이었다.

### 44.2 VRAM 캡처가 답을 줬다

재생 중 VRAM 뷰어 캡처에서 노이즈 블록 두 개의 위치가

```
(0,0)   480x240      <- 영상 버퍼 1
(480,240) 480x240    <- 영상 버퍼 2
```

DISPENV 실측(34절: `(0,0)` / `(480,240)`, 320x240)과 일치한다.
320x240 24비트 영상은 16비트 VRAM 단위로 480x240을 차지한다.

**우리 글리프 셀이 전부 영상 버퍼 2 안에 있다.**

| 블록 | 좌표 | 판정 |
|---|---|---|
| `RECT_COL1` | (950, 256, 4, 208) | **덮임** |
| `RECT_COL2` | (954, 256, 4, 192) | **덮임** |
| `RECT_DIG` | (920, 400, 12, 48) | **덮임** |
| `CLUT_RECT` | (1008, 511, 16, 1) | 안전 (x ≥ 960) |

팔레트만 살아남고 픽셀이 0이 되므로 **깨진 그림이 아니라 아무것도
보이지 않는다.** 모든 관측과 일치한다.

덤: 그 좌표는 **게임 원본 폰트 셀**이다. 그래서 일본판은 영상 중에
텍스트를 아예 그리지 않는다 — 폰트가 덮이기 때문이다.

### 44.3 다음 착수점 — 셀 재배치

양쪽 모두에서 안전한 영역에 글리프를 두어야 한다.

- 승리 장면: 통상 표시 `(0,0)`/`(0,240)` 각 640x240 → x 0~640 사용
- 엔딩: 영상 버퍼 `(0,0)`/`(480,240)` 각 480x240 → x 0~960 사용

교집합을 피하면 **x ≥ 960** 영역이 후보다(64 halfword 폭 × 512행).
다만 그 안에도 게임 아트가 있다(캡처에서 x≈964~1015, y≈244~381의
서예 이미지, 상단 x≈964~1024, y≈0~50의 로고 텍스트).

필요 용량: COL1 4×208, COL2 4×192, DIG 12×48.
**빈 곳을 정확히 골라야 하며, 셀 레이아웃은 렌더러의 템플릿 주소 방식
(V=0..191 연속 열)을 유지해야 한다.** 재배치 시 `RECT_*` 상수와
템플릿 테이블(`0x800858AC`) 좌표를 함께 갱신한다.

### 44.4 VRAM 배치 실측 (덤프 3종)

`work/analysis/vram_ending.png` · `vram_win.png` · `vram_usa_ending.png`
(모두 1024x512, DuckStation VRAM 뷰어).

MDEC 노이즈 위치로 영상 버퍼를 판별한 결과:

| 덤프 | 영상 버퍼 |
|---|---|
| JP 엔딩 | x 0~512 / y 0~256, **그리고** x 512~1024 / y 256~512 |
| USA 엔딩 | x ≥ 640 / y ≥ 256 만 |

**양 판본의 영상 버퍼 배치가 다르다.** 일본판은 `(0,0)`과 `(480,240)`
두 장으로 x 0~960을 쓴다(34절 DISPENV 실측과 일치).

### 44.5 안전지대 계산

- 승리 장면: 통상 프레임버퍼 640x240 x2 → **x 0~640** 사용
- 엔딩: 영상 버퍼 480x240 x2 → **x 0~960** 사용

합집합이 x 0~960이므로 **양쪽 모두에서 안전한 영역은 `x >= 960`** 뿐이다
(64 halfword 폭 x 512행). `CLUT_RECT (1008,511)`이 무사한 것이 이 계산을
뒷받침한다.

필요 용량은 COL1 4x208 + COL2 4x192 + DIG 12x48 = 20열. **공간은 충분하다.**
다만 그 영역에 게임 아트가 있어(로고·서예 이미지), 실제로 화면에 쓰이지
않는 행을 골라야 한다. 양쪽 덤프 모두에서 완전히 검은 구간은 최대 70행
(x 988~1000, y 60~130 부근)이었다.

### 44.6 미국판 원본 배치 추적은 보류

미국판 폭 테이블은 `0x80083D74`(0xC0 간격 4블록)로 확인됐으나,
템플릿 테이블은 시그니처 검색(`80 80 80 2C`)이 338건 오탐이라
특정하지 못했다. 결론이 같은 영역으로 수렴하므로 더 파지 않는다.

### 44.7 다음 착수점

`RECT_COL1` / `RECT_COL2` / `RECT_DIG`를 `x >= 960`으로 옮기고,
템플릿 테이블(`0x800858AC`)의 U/V를 함께 갱신한다.

- 연속 208행이 필요하면 게임 아트를 덮게 되므로, 먼저 **덮어도

  현재 업로드 방식의 제약**이다.

### 45.1 tpage 이동 기법

템플릿 엔트리의 tpage 필드(+10)는 64 halfword 단위 페이지를 고른다.
`0x003E`(페이지 x=14 → VRAM 896)를 `0x003F`(페이지 x=15 → VRAM 960)로
바꾸면 **U/V를 건드리지 않고 모든 셀이 정확히 +64 이동**한다.
CLUT 패치 루프에 tpage 패치를, 복원 루프에 tpage 복원을 얹었다.
승리 장면·CONTINUE 화면 모두 무회귀이므로 이 기법 자체는 안전하다.

### 45.2 덤프 관측 (엔딩 재생 중)

| 항목 | v52 캡처 | v53 캡처 |
|---|---|---|
| 글리프 COL1 (1014,256) | 84% | 83% |
| 글리프 COL2 (1018,256) | 36% | 56% |
| CLUT | **1/16 존재** | **0/16 없음** |

글리프 픽셀은 두 캡처 모두 존재한다. CLUT만 캡처마다 다르다.

`clut_off`는 항상 0이 아니므로(`build_group_blob`) 업로드 분기는 매
`record_hit`마다 실행된다. 따라서 CLUT 부재는 **캡처 시점이 자막
공백 구간이었을 가능성**이 높다. 이 덤프만으로는 판정 불가.

메인 루프 훅(0x80043204)은 재생 중 실행 자체가 안 된다.
옛 훅 0x8004A244가 엔딩당 1회만 걸린 것도 같은 이유(영상 함수 반환 직후).

v51~v55의 모든 수정(VRAM·CLUT·좌표·카운터)이 "안 나온" 진짜 이유.
승리/메뉴에서 카운터가 오른 것이 조회 완주라는 착시를 만들었다.

### 46.2 정정

- 25.4/26절의 "핸들러는 매 프레임 반환" 추정 폐기.
- `0x8003F60C`는 영상 재생 함수가 아니라 **사운드 채널 24개 틱 함수**.
- 42절의 "0x80128248이 증가하지 않는다"는 **훅이 안 돌아서 관측 못한 것**.
  이 전역은 영상 엔진이 매 프레임 갱신하는 진짜 프레임 카운터가 맞다.
  **v41의 원래 설계가 옳았고 훅 위치만 틀렸다.**

### 46.3 v56 — 영상 엔진 내부 훅

프레임 카운터 기록자: `0x8006FBD0` (fn `0x8006FB74`), 유일 호출자
**`0x8006F858`** (영상 엔진 `0x8006EF00` 내부, 조건부 per-frame).

호출부가 이상적: 딜레이 슬롯 nop, 직후 에필로그(caller-saved 미사용).
`jal` 1워드만 `j end_stub`으로 교체. 스텁: 원 호출 재생 → $t9=2 →
공유 본체 → 0x8006F860 복귀.

추가: 프레임 소스 `[0x80128248]` 복원, 자체 카운터 제거,
PRE 종단자+DISPENV 읽기 통합, POST 직접 전송(0x80069570) 복원
(재생 중 블로킹 핸들러는 OT를 제출하지 않으므로).

`build/subtitle_v56`, 여유 21바이트,
`sha256=611237AD1CA339B05CD237A487DD487A69D08FDD48C1649EF4F10E8B8E5468A1`
훅 2곳: 0x8003A88C(승리), **0x8006F858**(영상, `ddbe010c`→`29470008`).

## 47. 영상 루프 내 훅 검증과 GPU 충돌 (2026-08-02) — v57~v59 정리

### 47.1 훅 자체는 성공했다

`0x80066330`(영상 루프 `0x800661A8`의 VSync 호출부, 플립 직후) 훅으로
**재생 중 매 프레임 래퍼가 실행됨을 처음으로 확인**했다 (v57dbg 슬롯):

```
훅 진입 45 = 프레임값 45  (매 프레임, [0x80128248] 정상 작동 확인)
record_hit 24, 렌더러 호출 24  (프레임 21~45, 구간 15~180 매칭)
```

조회·타이밍·레코드 매칭·렌더러 호출까지 재생 중 전부 동작한다.
**v41의 프레임 소스([0x80128248])가 처음부터 옳았다** — 메인 루프
훅이 재생 중 정지한다는 것(46절)이 유일한 문제였다.

### 47.2 그러나 GPU가 죽는다 — 3단 분리 실험

| 빌드 | 매 프레임 하는 일 | 결과 |
|---|---|---|
| v57dbg | 업로드4 + 렌더러 + AddPrim + 원시 DMA 전송 | ~24렌더 후 영상 정지, 소리 지속, 재생 중단 |
| v58dbg | 원시 전송 제거 | 영상 정지, 소리 지속, **엔딩은 계속 진행**(다음 엔딩 소리) |
| v59dbg | + 업로드 4종도 제거 (명시적 DMA 전무) | **동일하게 정지** |

v59dbg에서 남는 것은 템플릿 CLUT/tpage 패치 → **렌더러 호출** →
AddPrim → 복원뿐이다. 명시적 DMA 없이도 죽는다.

### 47.3 남은 용의자 — 공식 렌더러 자체

유력: **렌더러 내부의 글리프 빌더(`0x80038F3C`)가 자체적으로 GPU
작업(셀 합성/업로드)을 한다.** 이전 세션의
`trace_font_loadimage*.json`이 폰트 렌더 중 LoadImage 추적 기록이다.
영상 루프 한가운데서 이것이 실행되면 엔진의 GPU 사용과 충돌해
디스플레이 파이프라인이 웨지된다(소리·스트리밍은 CPU/SPU라 생존).

차순위: 템플릿 테이블 패치/복원이 영상 중 다른 코드와 경합할 가능성
(낮음 — 메모리 쓰기뿐).

### 47.4 다음 세션 착수점

1. **최종 분리**: 렌더러 호출까지 뺀 빌드(패치+복원만)로 영상 생존
   확인. 생존하면 렌더러가 범인으로 확정.
2. 렌더러가 범인이면 두 갈래:
   a. **자체 프리미티브 조립**: 렌더러를 호출하지 않고 케이브 코드가
      SPRT/POLY_FT4 프리미티브를 직접 만들어 AddPrim. 셀 업로드는
      레코드 변경 시 1회로 줄인다(업로드 단독의 유해성은 미분리 —
      v59dbg에서 렌더러와 함께 제거됐으므로 재검증 필요).
      제출 경로는 여전히 미해결(재생 중 OT 제출 여부 미확인).
   b. **GP0 직접 기록**: DMA 없이 GPU 상태(비트 0x04000000) 폴링 후
      GP0 포트에 CPU로 프리미티브 워드를 직접 쓴다. 프레임당 수십
      워드라 부하 무시 가능. 완전 자립적이라 엔진과 충돌 여지가
      가장 적다. 포트 주소는 전역 테이블 0x8008A580(28.2절).
3. v59dbg 슬롯(`0x80011CA8`~) 판독은 에뮬레이터 종료로 미수행.
